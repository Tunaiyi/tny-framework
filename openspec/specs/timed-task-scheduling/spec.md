# timed-task-scheduling Specification

## Purpose
定时任务调度承载服务端周期型工作（重置、活动开关、结算等）的触发方案计算、待执行任务队列与驱动二者的调度线程。本能力钉死其行为契约：队列的排序方向、满员驱逐、同刻合并与恢复保留方向，触发器排序的全序性与同刻共存，无未来触发点方案的受控失败与按方案隔离，宕机追赶下的逐格推进，挂起/恢复/延长/停止的完整时长与返回值语义，以及调度器生命周期操作的互斥与执行池跨实例隔离——所有错误方向 MUST 显式失败或显式返回，不得静默丢任务或挂死线程。

## Requirements

### Requirement: 待执行任务队列按执行时间降序迭代并按容量驱逐最旧
任务队列对外迭代暴露的条目顺序 MUST 为执行时间降序。当队列容量上界为正数且已达上界时，新任务入队 MUST 驱逐执行时间最小的最旧任务，保留较新任务。读取"执行时间晚于给定水位"的任务时，MUST 仅返回晚于水位的任务，且返回结果 MUST 按执行时间升序排列（最先该执行者在前）。

#### Scenario: 乱序入队后按降序迭代且满员驱逐最旧
- **WHEN** 向容量上界为 2 的队列依次入队执行时间为 3000、1000、2000（毫秒）的三个任务
- **THEN** 队列快照按降序输出 3000 与 2000 两条，最旧的 1000 被驱逐

#### Scenario: 晚于水位的任务升序返回
- **WHEN** 从含执行时间 2000 与 3000 两任务的队列读取晚于水位 1500 的任务
- **THEN** 返回两条任务且顺序为 2000 在前、3000 在后；不晚于水位的任务不出现在结果中

#### Scenario: 水位覆盖全部任务时返回空
- **WHEN** 从非空队列读取晚于一个不小于全部任务执行时间的水位的任务
- **THEN** 返回空结果且不抛异常、不死循环

### Requirement: 容量上界非正数的队列入队不死循环且全量保留
队列容量上界为 0 或负数时 MUST 视为不限容量：每次入队 MUST 在有限时间内正常结束并保留全部任务（BREAKING：原实现在此配置下入队无限循环，调度线程永久挂死）。

#### Scenario: 零上界队列正常入队
- **WHEN** 向容量上界为 0 的队列入队一个任务
- **THEN** 入队在有限时间内返回，任务被保留（回归原死循环挂死）

#### Scenario: 负上界同样视为不限容量
- **WHEN** 向容量上界为 -5 的队列入队任务
- **THEN** 入队正常结束且任务被保留，不因上界取负而丢弃任务

### Requirement: 同执行时间再入队合并处理器而非整批丢弃
入队新任务时若队列中已存在执行时间完全相同的任务，新任务携带的处理器名单 MUST 合并进存量任务，MUST NOT 因按执行时间去重而将新任务整批静默丢弃（BREAKING：原实现后到批次整体丢失），存量任务亦 MUST NOT 被覆盖消失。

#### Scenario: 同刻批次处理器合并保留
- **WHEN** 执行时间同为 5000、处理器分别为 A 与 B 的两个任务先后入队
- **THEN** 队列仅存一条执行时间 5000 的任务，其处理器名单同时包含 A 与 B

#### Scenario: 合并时同名处理器不叠加
- **WHEN** 存量任务处理器名单为 [A, B]，新批次携带 [B, C] 被合并
- **THEN** 合并后名单为 [A, B, C]，同名处理器只保留一份，不引发重复执行

### Requirement: 从降序快照恢复队列时超上限保留最新
队列恢复操作接收的快照按执行时间降序排列（队首为最新）。快照条目数超过正数容量上界时，MUST 保留快照前 N 条即最新的 N 个任务、丢弃最旧的超额部分（与入队驱逐最旧的方向一致；BREAKING：原实现保留最旧、丢失最新）；容量上界非正数时 MUST 保留快照全部任务。

#### Scenario: 超限恢复保留最新
- **WHEN** 含执行时间 3000、2000、1000 三条任务的降序快照被恢复到容量上界为 2 的队列
- **THEN** 恢复后队列含 3000 与 2000 两条，最旧的 1000 被丢弃

#### Scenario: 非正上界恢复不吞快照
- **WHEN** 两条任务的快照被恢复到容量上界为 0 的队列
- **THEN** 两条任务全部入队，恢复后条目数等于快照条目数（原实现此情形清空吞任务）

### Requirement: 触发器定序全序反对称且同刻触发不判等
触发器实例之间的排序 MUST 构成全序：先按下次触发时间升序比较；下次触发时间相同时，不同触发器实例 MUST NOT 判为相等（以稳定身份次序区分），且比较结果 MUST 反对称（一方在前则另一方必在后）。由此待触发集合中同刻触发器的实例数 MUST 等于实际加入数，"取最早"与"取出最早"MUST 返回全局最早触发下次时间的实例。不同频率方案（每秒与每小时）混排时按各自下次触发时间定序。

#### Scenario: 同刻两方案共存且互不判等
- **WHEN** 两个下次触发时间完全相同但源自不同方案的触发器先后加入待触发集合
- **THEN** 集合保留两个实例，二者互比均不为 0 且结果互为反号，取最早返回其中下次触发时间全局最早的实例

#### Scenario: 不同频率方案按下次触发时间排序
- **WHEN** 每秒触发方案与每小时触发方案在同一基准时刻参与排序比较
- **THEN** 下次触发时间更早者排前，反向比较结果符号相反

### Requirement: 无未来触发点方案受控失败且单方案失败不连坐
方案表达式不存在未来触发时间（如指定年份已经过去）时，计算其下次触发时间 MUST 抛出含该方案标识与表达式内容的受控异常（BREAKING：原实现暴露裸空指针）。调度器初始化方案集合时，单个方案构建失败 MUST 仅跳过该方案并记录含方案标识的错误日志，其余有效方案 MUST 照常进入调度；存在至少一个有效方案时，调度器 MUST NOT 呈现"启动成功但永不产出任务"的状态。

#### Scenario: 过期方案抛出受控异常
- **WHEN** 为一个固定年份已过期的方案计算下次触发时间
- **THEN** 抛出显式说明该方案无未来触发时间的受控异常，调用方无需面对裸空指针

#### Scenario: 坏方案仅跳过自身
- **WHEN** 调度器启动时方案列表含一个无未来触发点的坏方案与多个有效方案
- **THEN** 坏方案被跳过并记录错误日志，其余有效方案按下次触发时间照常全部调度

#### Scenario: 有效方案存在时调度持续产出
- **WHEN** 含一个坏方案的调度器启动完成后，时钟到达某有效方案的触发时刻
- **THEN** 该有效方案的任务被正常产出，调度器不出现"启动成功但永不产出"的静默失效

### Requirement: 周期计算的确定性与小时级触发点不随zone漂移
定长周期方案的下次触发时间 MUST 等于基准时间加周期长度。小时级方案的触发点 MUST 与部署时区设置无关，恒落在整小时边界（不早于基准的下一个整点）。

#### Scenario: 定长周期等于基准加步长
- **WHEN** 以 500 毫秒定长周期从某一基准时刻计算下次触发时间
- **THEN** 结果为基准时刻加 500 毫秒

#### Scenario: 小时级触发点与时区无关
- **WHEN** 在任意时刻（含非整点）为"每小时整点"方案计算下次触发时间
- **THEN** 结果恰为下一个整小时边界，不随服务器时区配置发生偏移

### Requirement: 触发推进一次调用一格且加速与强制触发语义明确
检查时刻（叠加累计加速量后）越过当前下次触发时间时，一次检查推进 MUST 仅前进一格——下次触发时间移到相邻的下一个周期点；更久未执行（宕机追赶）由调用方反复调用逐格追平，MUST NOT 在一次调用内跳越多格。未到期时检查 MUST NOT 推进并返回未触发。加速量 MUST 可累加且参与到期检查。强制触发 MUST NOT 受"未到期"约束，存在下次触发时间即推进一格并返回已触发。推进出的下一触发点越过停止时间时，触发器 MUST 进入结束态（下次触发时间为空）。

#### Scenario: 越过两格半时每次调用仅推进一格
- **WHEN** 周期 1000 毫秒、起始下次触发为基准+1000 的触发器以基准+2500 的检查时刻被连续检查三次
- **THEN** 第一、二次检查返回已触发并分别推进到 +2000、+3000，第三次因未到期返回未触发且不再推进

#### Scenario: 加速量累加并计入到期判断
- **WHEN** 同一触发器先后累计 1500 与 1000 毫秒加速量，随后以真实尚未到期的时刻执行检查
- **THEN** 加速总量 2500 毫秒计入检查，有效时间越过下次触发点，本次检查推进一格

#### Scenario: 强制触发不受未到期约束
- **WHEN** 在检查时刻早于当前下次触发时间时执行强制触发
- **THEN** 返回已触发且下次触发时间推进一格

#### Scenario: 越过停止时间后结束
- **WHEN** 带停止时间的触发器经多次到期推进使下一触发点晚于停止时间
- **THEN** 该次推进后下次触发时间变为空，后续检查与强制触发均返回未触发

### Requirement: 恢复按完整挂起时长后移且不截断
挂起后以晚于挂起点的时刻恢复时，下次触发时间与停止时间（若存在）MUST 各自后移"恢复时刻与挂起时刻之差"的完整时长；超长挂起（超过 32 位毫秒上限的时长，如 30 天）MUST 同样保持完整偏移（BREAKING：原实现按 32 位截断，超长挂起使日程回退数周）。恢复时刻早于挂起时刻时，恢复 MUST 返回未生效。

#### Scenario: 短挂起按实际时长后移
- **WHEN** 周期 1000 毫秒的触发器在基准+300 挂起、基准+600 恢复
- **THEN** 下次触发时间等于原触发点（基准+1000）再加 300 毫秒

#### Scenario: 超长挂起完整偏移不截断
- **WHEN** 触发器挂起 30 天（超过 32 位毫秒上限）后恢复
- **THEN** 下次触发时间与停止时间均后移完整 30 天，不出现截断后的回退

#### Scenario: 恢复时刻早于挂起时刻无效
- **WHEN** 以早于已记录挂起时刻的时间请求恢复
- **THEN** 恢复返回 false，触发时间轴保持原状

### Requirement: 结束态挂起请求返回假且停止清理挂起态
对未启动或已结束（无下次触发时间）的触发器请求挂起，MUST 返回 false 且 MUST NOT 抛出异常（BREAKING：原实现暴露裸空指针）；对已越过触发点的运行中触发器请求挂起同样返回 false。停止运行中的触发器 MUST 清除挂起状态并返回已停止；停止后重新进入新周期的触发器 MUST 正常推进，MUST NOT 被陈旧挂起锚点整体拖后。

#### Scenario: 挂起成功与停止清理挂起态
- **WHEN** 运行中且未到期的触发器挂起成功后执行停止
- **THEN** 挂起时返回已挂起；停止后挂起状态被清空，停止返回已停止

#### Scenario: 结束态挂起返回假不抛异常
- **WHEN** 对一个已停止的触发器再次请求挂起
- **THEN** 返回 false，不抛出任何异常

#### Scenario: 停止后重启进入干净周期
- **WHEN** 触发器挂起后停止，再以新基准时刻重新启动并在到期时刻检查
- **THEN** 新周期下次触发时间按新基准计算并正常推进，不被旧挂起锚点拖后

### Requirement: 延长成功返回真且完整后移
对未结束触发器以正数时长执行延长：MUST 返回 true，下次触发时间与停止时间（若存在）MUST 各后移完整的请求时长；超长时长（超过 32 位毫秒上限）MUST NOT 被截断，同样完整后移（BREAKING：原实现成功路径也恒返回 false 且时长截断）。对已结束触发器或以零、负时长请求延长 MUST 返回 false。

#### Scenario: 正常延长返回真并后移
- **WHEN** 运行中触发器（下次触发基准+1000、停止基准+10000）被延长 5000 毫秒
- **THEN** 返回 true；下次触发时间变为基准+6000，停止时间变为基准+15000

#### Scenario: 超长延长不截断
- **WHEN** 触发器被延长 30 天（超过 32 位毫秒上限）
- **THEN** 返回 true 且下次触发时间后移完整 30 天

#### Scenario: 非法延长返回假
- **WHEN** 以时长 0、负数，或在已结束触发器上请求延长
- **THEN** 返回 false，触发时间轴保持原状

### Requirement: 调度器重配置与关闭和任务派发互斥
调度器的重新配置、启动装配与关闭操作 MUST 与任务派发及任务入队互斥：接收者派发期间读取的队列内容 MUST NOT 被并发重配置/改写成半新半旧的混合状态；重配置/关闭 MUST 等待进行中的入队或派发完成后再改写队列与触发器集合（原实现的排他操作被误归为共享操作，互不排斥）。

#### Scenario: 派发与重配置不交错
- **WHEN** 一个接收者的任务派发与一次重配置请求并发发起
- **THEN** 两操作串行执行，派发读取到的是完整一致的队列快照，重配置基于该快照一致地完成

#### Scenario: 重配置后队列与新方案一致
- **WHEN** 调度线程正将新产出的任务写入队列时重配置请求到达
- **THEN** 写入与重配置互斥完成，重配置结束后的队列不残留半改写状态，后续按新方案继续调度

### Requirement: 关闭置终态、取消待执行任务并终止本实例执行池
调度器关闭 MUST 将运行状态置为终态（对外"是否运行中"的观察翻为否）、取消已排期但未执行的产出任务，并终止本实例的执行池；关闭后 MUST NOT 再产生新任务入队或任务事件回调（原实现仅终止执行池而不改状态位，进行中的内部逻辑会向已终止的池排任务而静默炸链）。

#### Scenario: 关闭后终态可观察且不再产出
- **WHEN** 调度器被关闭后，等待越过其原本最近的触发时刻
- **THEN** 运行状态查询返回未运行，无新任务进入队列，无监听回调发生，执行池处于终止状态

#### Scenario: 关闭取消待执行任务
- **WHEN** 存在一个已排期尚未到点的产出任务时调度器被关闭
- **THEN** 该排期任务被取消不再执行，关闭流程正常完成不抛异常

### Requirement: 多调度器实例各自持有执行池互不影响
每个调度器实例 MUST 持有自己独立的执行池：任一实例的重启（重配置）或关闭 MUST NOT 影响其他运行中实例的调度线程与任务产出（BREAKING：原实现共享单一静态执行池，一个实例的重启/关闭会杀掉其他实例的调度能力）。

#### Scenario: 一个实例重配置不中断另一个
- **WHEN** 实例 B 正常运行期间实例 A 执行重配置重启
- **THEN** B 的触发器调度与任务产出全程不中断，其执行线程保持存活

#### Scenario: 一个实例关闭只终止自身
- **WHEN** 实例 A 关闭而实例 B 仍在运行
- **THEN** 仅 A 的执行池终止，B 继续按其方案产出与派发任务
