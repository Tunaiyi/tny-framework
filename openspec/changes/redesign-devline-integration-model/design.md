# Design

## Context

现行三层模型（openspec 规格 release-versioning 七条需求，2026-10-04 生效）的实际运行数据与两轮对抗评审判决构成本设计的输入：每次发布产生一枚永久 `.release` 容器分支；main 上已实际发生 7 枚整线收编合并（与线性铁律矛盾）；仓库远端 48 条分支中约 46 条为 2016 至 2023 年历史遗留；用户于 2026-10-05 至 10-06 的多轮探索中拍板切换模型并逐词定名术语表。git 级可行性已由 `drill/model4-sim/simulate.sh` 全场景沙箱验证（52 项断言，两次重跑退出码 0，经对抗复核修复四处假绿后定稿）。动机详见 proposal.md 的 Why 节。

约束：本变更不触碰任何 tny-game-* 运行时模块（无公共 API 变更）；构建文件书写形态受 gradle-build-style 能力约束（约定插件两百五十行上限、程序性行为只进任务动作块或插件脚本）；下游快照坐标供给在迁移期不得中断（2026-10 契约变更声明的承诺）。

爆炸半径摘要：codegraph 对 Groovy 解析到类粒度（GitFlow 类直接受影响计数 1），以 grep 枚举为准——`parseBranchVersion`/`parseProjectVersion`/`branchName` 的消费方为 `tny.release.gradle`、`tny.publish.gradle`、`tny.publications.gradle`、`tny.central.gradle` 四个约定插件，加上三个 GitHub 工作流的分支枚举。本仓库既有先例检索：模式卷与原则卷无同型先例（分支模型属工程流程而非运行时对象设计）；最接近的先例是 2026-10-04 `revise-release-branch-flow` 的 D 系列决策结构，本设计沿用其"每条决定附否决备选"的格式并按其 P5 依据（一个对象一种变更原因）重新划分分支职责。

## Goals / Non-Goals

- 目标：分支种类从五种降到四种（main、开发版本分支、release 维护分支、feat 与 fix 分支）；发布任务从三个减到两个；补丁到达主干的通路合法化且可机器对账；全部新纪律有机械门禁兜底而非仅靠约定。
- 非目标：不在本变更内实现 GitHub 服务端保护规则与 pre-receive 钩子（属平台配置，由用户另行执行，词表变更同步给出建议项）；不处理主版本（6.0）并行开发的既有结构缺口的最终答案（新模型以"高编号开发版本分支在低编号集成前不得集成"缓解了排队问题，但 6.0 断代重构与 5.x 长期共存的对账细节留待 6.0 开线时的后续变更）；不清理 46 条历史死分支（按退役条款分批执行，本变更只建立机制与登记表）。

## Decisions

### D1 分支职责按"变更原因"四分（P5 直接应用）
main 的变更原因只有一种：记录已发布事实的汇合（接收集成与向上合并）。开发版本分支的变更原因：孕育一个次系列的特性与首发前修复。release 维护分支的变更原因：为一个已发布系列滚动补丁。feat 分支与 fix 分支的变更原因：单次工作的暂存。
否决备选："main 继续兼任特性工厂"（现行模型）——被否决，因为特性工厂与维护回流两种变更原因在 main 上冲突，正是 7 枚偷偷收编合并的根源。

### D2 分支形态即发布资格的推导规则保持"名字派生"公理，形态改为前缀式
`dev/N.M.x` 派生快照坐标 `N.M.x-SNAPSHOT`（坐标字符串与现行完全一致，前缀 `dev/` 不参与坐标）；`release/N.M.x` 派生发布前两段与下一补丁号校验。版本派生的解析入口收敛在 GitFlow 的两个纯函数内，四个消费插件只读结果。
否决备选：坐标改用版本文件记载（Maven 常见做法）——违反本仓库"零版本文件改动"既有公理（docs 设计公理一），且引入每次发版改文件、旧提交重建漂移的问题，P13 可验证性倒退。

### D3 集成到主干采用"先同步、后整体合并、产生合并提交"的固定顺序
集成 = main 合入开发版本分支（同步）→ 开发版本分支整体合入 main（--no-ff，合并提交说明固定格式 `integrate dev/<N.M.x> to main: <版本>`）→ 删除开发版本分支。main 的 first-parent 日志由此成为集成事件账本，一行命令可枚举。
否决备选 A：rebase-merge 逐笔上收（现行特性进 main 的方式）——特性在开发版本分支上可能数十笔，逐笔上收失去"一次集成一个事件"的账本粒度，也无法原子化集成顺序检查。否决备选 B：fast-forward 集成——静默窗口里可行，但同步合并之后 dev 与 main 已交错，ff 不总成立；且无合并节点则集成事件不可枚举，与 D3 的账本目标冲突（沙箱模拟实测：补丁向上合并在静默窗口天然 ff，本决定只把"集成"这一类事件钉死为合并提交，向上合并不钉）。
依据：P13（集成事件可机器枚举）、P12（行为契约先于实现）。

### D4 补丁传播的默认机制是整条分支合并（向上合并），cherry-pick 降为例外
向上合并把源分支头整体 merge 进目标（更新的维护分支，最后到 main）。核心收益："该补丁是否已到达"退化为祖先判定（`git log 目标..源` 为空），彻底摆脱 cherry-pick 孪生导致的 patch-id 分叉——对抗复核与压力测试实测 cherry-pick 加人工解冲突后 `git cherry` 出现无法判读的真/假阳混合（判决代价项二）。例外通道按 branch-integration-gates 规格的登记制度执行。
否决备选：维持"逐笔 cherry-pick -x 重放"（现行 mergeBack 与参考模型补丁梯的做法）——孪生副本使对账永久依赖启发式命令与人工点名，假绿事故（压力测试致命项一）在纯 cherry-pick 体系内无解。
代价如实登记：跨系合并的冲突率高于逐笔复制（代码位置分叉时），由例外通道与完整性检查承接。

### D5 合并结果完整性检查钉在"提交之前"，以缺陷编号为检索键
任何向上合并与集成在产生提交前，对搬运批次内的每个缺陷编号在合并结果内容中检索；缺失即中止。缺陷编号进提交信息从本变更起为修复类提交的强制格式（`feat(...)` 系列不受此限，由 commit-msg 钩子与 CI 校验强制），这是完整性检查可行的前提。
否决备选：事后靠回归测试全量重跑发现丢失——反馈太晚且失败定位难；完整性检查是第一道，回归重跑是发布前的第二道（沿用既有门禁时序），两者互补不互斥。
依据：P13；沙箱场景 8 实测该检查能拦住"历史绿、树红"事故。

### D6 发布门禁谓词按"版本形态"判定，白名单按"形态加登记表"双层判定
签名强制：版本串不以 `-SNAPSHOT` 结尾即必须签名（现行按分支名匹配 `.release` 形态，废除该形态后谓词失锚）；Central 准入：裸三段号且前两段与所在维护分支编号一致；两处均 fail-closed（查询失败按拒绝处理）。发布分支白名单：`dev/*.*.x` 与 `release/*.*.x` 形态之外，仅登记表内的历史资产（首条即 `5.7.x`）按登记身份获得对应资格。
否决备选：纯形态正则一刀切——会把祖父条款里的 `5.7.x`（无 `release/` 前缀）拒于门外，切断其快照供给，违反下游契约承诺；纯登记表无形态——重蹈 13 枚裸版本号历史分支穿透白名单的覆辙（压力测试迁移维度实锤）。双层是压力测试判决的原话（"形态加登记表"）。
依据：P4（不变量由门禁守护）、P11（下游坐标合同不因工程改名而违约）。

### D7 现状迁移采用祖父条款：`5.7.x` 不重切、不改名、不断供
`5.7.x` 原样续跑（同时承担维护与快照生产，登记为豁免资产），新形态自下一个次系列（预计 5.8）起启用。5.7 系列终止维护时按退役检查流程删除，届时 `5.7.x-SNAPSHOT` 供给的停止作为公开的系列退役事件处理（发布说明与 Central 退役声明先行）。
否决备选：把 `5.7.x` 改名 `dev/5.7.x` 或从 main 重切 `release/5.7.x`——两者都会中断当日就在流动的快照坐标或维护连续性，构成对下游的第二次整体改约（压力测试判决第 17 条明确此为信任事件）。
代价如实登记：一段时间内仓库同时存在新旧两套分支形态，词表与文档需给出"历史形态身份映射表"；`dev/` 前缀的规范红利推迟到 5.8 系列才完整兑现。

### D8 持续集成的分支枚举改为显式前缀路径并加非空断言
快照触发与逐线镜像的过滤器改为 `dev/*.*.x`（旧形态豁免线在过滤器与登记表两处并列放行，实现细节归 apply）；工作流开头 MUST 断言匹配集合非空（压力测试实锤：`*-*.*.x` 写错命中零条而无告警）。GitHub Actions 通配对斜杠的精确语义在 apply 阶段以一次探测工作流实测，不凭文档记忆下结论。

### D9 术语表以本文件为权威定义位置，落进 release-process.md 头部
定稿词表（完整定义句）：开发版本分支（`dev/N.M.x`）、release 维护分支（`release/N.M.x`，每系列唯一）、集成到主干（D3 的固定顺序动作）、向上合并（D4 的整体合并动作，英文注记 merge-forward 只表方向不表机制）、补丁影响清单（完整行文"该补丁影响到的 release 维护分支清单"，修复类 PR 必填）、release 标签（发布流程经 releaseTag 创建的 `v<主>.<次>.<补丁>` git 附注标签对象；历史 `-RELEASE` 后缀标签称"历史遗留标签"不入此定义；提及平台功能一律写全称 GitHub Releases）、release 标签核验（门禁动作；"存证"保留为标签的身份描述词，两个角色不混用）、分支头（指顶端指针）与"该分支的最新提交"（指提交对象；git 符号引用一律写 HEAD）、下一补丁号校验、开发版本分支集成顺序检查、合并结果完整性检查、退役（动作句按 gates 规格定稿，"未集成提交"指分支上已提交但 main 尚未包含的提交）、cherry-pick 例外登记、允许强制推送（范围仅 feat 与 fix 分支且必须带 `--force-with-lease`）、release 维护分支快照（指 `N.M.x-SNAPSHOT` 字面坐标形态）、源分支（补丁最初落位的分支）。
词表纪律（承接用户"第四类不得使用比喻"的批示）：电梯、工位、登车、早切晚锁、发布容器、清账、补账、硬锚、编年史、断代、基取、落点、上合、下传、在役、让位、坟场类修辞——全部禁止进入文档、代码注释与对用户汇报。

### D10 "合并patch"与已删除的"合回"划界成文，防混同
releaseMergeBack 任务删除后，历史文档释义中的"合回"一词整体退役；新词表里上行动作只有两个："集成到主干"（开发版本分支到 main，D3）与"向上合并"（维护分支向更新分支与 main，D4），英文 cherry-pick 例外单列。docs 头部加"何人把何内容经何机制移到何处"三行判定表。
否决备选：让"合并补丁"成为第三个正式动作名——与"向上合并"所指完全重叠，且"补丁"二字与旧"合回"释义（按补丁内容去重）字面纠缠，QC 判决明确警告混同风险。

## Risks / Trade-offs

- [跨系整条合并的冲突率上升] → 例外通道（cherry-pick 加登记）承接机械不可解场景；补丁影响清单在 PR 阶段即声明目标分支，冲突在工作日消化而非发布日。
- [新旧形态并存的祖父期认知负担] → 身份映射登记表唯一化；祖父豁免只减不增（`5.7.x` 退役后登记表清空旧形态条目）。
- [缺陷编号纪律执行不严导致完整性检查空转] → commit-msg 钩子与 CI 校验强制修复类提交携带编号；无编号修复 PR 直接拒合。
- [main 放弃线性宣称的观感回退] → 用户已拍板"承认收编、修铁律"；first-parent 合并节点即集成账本，对账口径同步改为祖先判定加编号点名。
- [GitHub 平台侧配置（分支保护、Squash 开关、pre-receive）与仓库纪律脱节] → 本变更 tasks 列出平台配置核对清单，由用户在 GitHub 设置面执行；文档如实区分"构建系统兜底"与"平台兜底"两层。
- [Actions 通配对 `dev/` 前缀的匹配语义误判] → D8 的探测任务先行，任何过滤器改动先在探测工作流验证命中集，后进生产工作流。

## Migration Plan

1. 规格与文档先行（P12）：合并本变更的规格增量、重写 release-process.md（含词表节与身份映射表初版）、更新两份 HTML。
2. buildSrc 改造：GitFlow 形态解析、releaseCut 语义改为"切维护分支（每系列一次）"、releaseTag 守卫与下一补丁号校验、releaseMergeBack 删除、门禁谓词版本形态化、登记表读取。
3. CI 改造：D8 过滤器与断言；探测工作流先行验证。
4. 钩子与登记：commit-msg 编号强制、补丁影响清单模板、cherry-pick 例外登记表、豁免与身份映射登记表落地。
5. 演练序列（真实周期取证，压力测试判决的前置要求）：下一个 5.7 补丁（如 5.7.9）在祖父轨上按旧流程完成，同时新工具链以 `-PdryRun` 全程陪跑对照；首个新形态系列（5.8）从开 dev 线、集成、切 release、发 5.8.0、打补丁、向上合并到退役检查走完整生命周期，逐事件记账入本变更验证卷宗。
6. 回退策略：改造期任一环节不可用，回退顺序=停用新任务、恢复旧 releaseMergeBack 的 git tag 与分支保护快照、祖父轨继续供给——5.7 线在演练期内保持旧流程为主通道，回退不产生数据迁移损失。

## Open Questions

- 6.0 断代重构开线时，开发版本分支的编号策略（直接 `dev/6.0.x` 并让 5.x 各系列自然退役，还是设过渡整合分支）——留待 6.0 开线变更处理，本设计的排队规则已为其预留。
- GitHub Releases 页面条目与 release 标签的双向自动化程度（发布工作流是否同步创建 Release 页）——不影响规格达成，apply 期由用户定夺。
