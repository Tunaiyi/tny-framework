# Proposal

## Why

现行三层分支模型（2026-10-04 制度化）在实际使用的头两天暴露出两个结构性痛点。第一，每次发布都要切出一次性 `<主>.<次>.<补丁>.release` 版本发布分支且永久保留，分支清单随发布次数单调增长，这正是用户反馈"分支管理太乱"的直接来源之一（仓库现存 48 条远端分支中约 46 条为历史遗留，而新模型自身还在继续生产 `.release` 分支）。第二，版本开发分支向 main 的回流没有合法通路：main 上已经实际发生 7 枚"merge 5.7.x"合并提交（提交信息自述"采用合并收编"），与"main 线性、禁止整线合并进 main"的铁律直接矛盾，纪律与仓库现实脱节。经三轮对抗评审（其中参考模型切换议题、第四模型压力测试各一轮，判决共计数十条发现）与 git 级沙箱模拟全场景通过（drill/model4-sim，52 项机器断言两次重跑退出码 0），用户于 2026-10-06 拍板切换分支模型。

## What Changes

- **BREAKING** 开发版本分支形态从 `N.M.x` 改为 `dev/N.M.x`。开发版本分支成为唯一的特性开发场所：特性分支（`feat/…`）rebase 合入开发版本分支；开发版本分支在首发之前持续接收特性，不再有"切线即特性冻结"语义。快照坐标字符串保持字面形态 `N.M.x-SNAPSHOT`（由分支名去掉 `dev/` 前缀推导），下游构件消费者的坐标声明无需任何修改，2026-10 契约变更声明中的承诺继续有效。
- **BREAKING** 废除一次性版本发布分支（`<V>.release` 形态），改为常驻的 release 维护分支（形态 `release/N.M.x`）：在开发版本分支集成到主干之后从主干切出，此后只接收补丁修复，滚动发布 `N.M.0、N.M.1、N.M.2……`，每个版本一个 release 标签。
- **BREAKING** 发布任务改造：`releaseMergeBack` 整个删除；`releaseCut` 改为"切维护分支"（每个系列仅执行一次）；`releaseTag` 的分支守卫改为 `release/N.M.x` 形态，并新增下一补丁号校验（发布号必须恰为该维护分支已发布最大补丁号加一，拒绝错号与同号复用）。
- **BREAKING** 补丁传播方向反转：修复提交产生在最老的仍在接收补丁的 release 维护分支（称为源分支），通过**向上合并**进入更新的 release 维护分支与 main。向上合并的默认机制是整条分支合并（git merge，源分支头整体并入目标分支），目标分支因此完整包含源分支历史，"该补丁是否已到"退化为精确的祖先判定；整条合并不可行时（代码位置分叉）改用 cherry-pick 复制单个修复提交，提交说明记录来源提交与判定人，并随目标分支下一版发出。不再采用"修复原型先落 main、逐线向下复制"的现行方向。
- 新增机械门禁三件（详见新能力 branch-integration-gates）：开发版本分支集成顺序检查（低编号开发版本分支未完成集成之前，高编号不得集成；集成完成后删除该开发版本分支）、合并结果完整性检查（向上合并解决冲突之后、提交之前，检索本次搬运的缺陷标记在合并结果中全部在位）、退役检查（删除 release 维护分支之前检查该分支有无未集成到主干的提交，有则先完成向上合并）。
- 发布门禁谓词重锚：分支形态白名单改为 `dev/N.M.x`（可发快照）与 `release/N.M.x`（可发裸号）两形态，main 与其他形态一律拒绝；签名强制与 Central 准入的判定从"分支名匹配 `<V>.release`"改为按版本形态判定并以 fail-closed 为默认（版本不以 `-SNAPSHOT` 结尾即必须签名；Central 要求裸三段号且与该维护分支前缀一致）。
- main 的角色改为集成主干：main 不接收任何直接开发提交，内容只有两个来源——开发版本分支的集成到主干，与 release 维护分支的向上合并；main 禁止 rebase 与强制推送。允许强制推送的范围仅为 feat 分支与 fix 分支。
- release 标签（git 对象形态必须是附注标签）一经推送永不移动，成为版本号、构件与提交位置三者对账的权威依据；既有各 `<V>.release` 容器分支与其标签的历史身份登记映射，不动历史。
- 术语表成文：本变更带来的全部正式名词（开发版本分支、release 维护分支、集成到主干、向上合并、合并patch、release 标签、release 标签核验、分支Head、下一补丁号校验、开发版本分支集成顺序检查、合并结果完整性检查、退役、受patch影响release维护分支清单、允许强制推送、release 维护分支快照、源分支）以 design.md 词表节为权威定义，全套文档与动画按词表改写。

## Capabilities

### New Capabilities
- `branch-integration-gates`: 分支流转的三道机械门禁与 cherry-pick 例外登记——开发版本分支集成顺序检查、合并结果完整性检查、退役检查、例外复制登记制度；以及 main 与开发版本分支、release 维护分支的改写禁止规则（允许强制推送的范围仅限 feat 分支与 fix 分支）。

### Modified Capabilities
- `release-versioning`: 需求一到需求三按新形态重锚（分支形态、快照坐标推导、白名单枚举）；需求四扩展为"凡已建 release 标签的版本号不得复用"；需求五保留并升格（release 标签为唯一权威对账依据，标签先于制品）；需求七拆分改写（删除"一次性容器不可移动"，新增"release 维护分支只追加不改写、发布后滚动补丁"，"标签永不移动"并入需求五管辖）；"切线即特性冻结"语义删除。
- `central-publishing`: "快照构件多目的地并行发布"需求下"发布分支误走快照通道被拒绝"场景中的分支形态锚点 `<主>.<次>.<补丁>.release` 改为新形态表述（release 维护分支形态不得执行快照发布，开发版本分支形态不得发布裸号）。

## Impact

- 构建与发布链路（本变更不触碰任何 tny-game-* 运行时模块的公共 API，无下游业务模块牵连）：
  - buildSrc：`tny.git.gradle`（守卫与分支名解析）、`tny/convention/GitFlow.groovy`（parseBranchVersion、parseProjectVersion 的形态推导）、`tny.release.gradle`（三任务改两任务）、`tny.publish.gradle`（门禁白名单与标签核验）、`tny.publications.gradle`（签名强制谓词）、`tny.central.gradle`（Central 准入谓词）。
  - 持续集成：`.github/workflows/build.yml`（快照触发通配改为 `dev/*.*.x` 并加匹配集合非空断言）、`publish.yml`、`snapshot-mirror.yml`（逐线镜像的分支枚举形态）。
  - 账本与登记：`gradle/released-legacy.txt` 保留；线谱系登记表新增"开发版本分支与对应 release 维护分支"两列语义；历史资产身份映射（现存 `5.7.8.release`、`4.1.0.release`、`5.5.0.release` 容器分支，main 上 7 枚收编合并提交，24 枚 5.7.x 线内旧时代合并，6.0.x 死线处置）。
  - 文档：`docs/release-process.md` 全文按新模型与词表重写；`docs/branch-model.html`、`docs/branch-flow-animation.html` 重绘；`drill/model4-sim/simulate.sh` 作为已通过的 git 级验证材料随卷归档。
- 现状迁移采用**旧形态祖父条款**（不重切、不改名、不断供）：现存 `5.7.x` 分支原样续跑至 5.7 系列终止维护，以登记表豁免保留其发布资格（它同时承担维护与 `5.7.x-SNAPSHOT` 快照生产，改名或重切会切断下游快照供给，构成对 2026-10 契约声明的第二次整体改约——术语质检与压力测试判决均判定此路不通）；新形态（`dev/` 与 `release/` 前缀）自下一个特性系列（5.8 或更高）起启用；历史资产身份映射登记表成文（旧形态各线、`5.7.8.release` 等容器分支、main 上 7 枚收编合并、`6.0.x` 死线处置）。
- 已定稿但等待本次成文的既有拍板：main 收编合并的合法性表述并入"集成到主干"与"向上合并"两个正式动作；3 枚变 7 枚的账本失实随文档重写一并修正。
