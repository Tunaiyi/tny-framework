# branch-integration-gates 变更增量

## ADDED Requirements

### Requirement: 开发版本分支集成到主干前必须完成顺序检查与主干同步
低编号的开发版本分支未完成集成到主干之前，高编号的开发版本分支不得集成。集成到主干 MUST 按以下顺序执行：先把 main 分支头合并同步进该开发版本分支（冲突在开发版本分支上解决），再以产生合并提交的方式将该开发版本分支整体并入 main，合并提交说明 MUST 采用固定格式记录被集成的分支与该系列的首发版本号；集成完成后删除该开发版本分支。顺序检查与同步合并任一环节不通过或未执行时，集成 MUST 被拒绝。

#### Scenario: 首发系列按序集成并留下可检索的账本记录
- **WHEN** `dev/5.8.x` 达到发布标准，执行集成到主干（此时不存在其他未集成的更低编号开发版本分支），随后切出 `release/5.8.x` 并发布 `5.8.0`
- **THEN** main 上出现一条固定格式说明的合并提交，可经一行命令枚举全部集成事件；`dev/5.8.x` 分支被删除；`v5.8.0` 标签指向维护分支头

#### Scenario: 高编号线抢跑被拒绝
- **WHEN** `dev/5.8.x` 尚未集成删除时，`dev/5.9.x` 尝试执行集成到主干
- **THEN** 顺序检查拒绝该集成，错误信息列出阻塞它的低编号开发版本分支

#### Scenario: 跳过主干同步直接集成被拒绝
- **WHEN** 开发版本分支未先合入 main 最新内容就尝试整体并入（main 不是该分支的祖先）
- **THEN** 集成被拒绝，错误信息要求先执行主干同步合并并解决可能的冲突

### Requirement: 向上合并执行整条分支合并并强制通过合并结果完整性检查
补丁从源分支向更新的 release 维护分支与 main 的向上合并，默认机制 MUST 为整条分支合并；每次向上合并在解决冲突之后、产生提交之前，MUST 执行合并结果完整性检查——对本次搬运的每一个缺陷修复，以缺陷编号（或等价的成对标记）在合并结果的全部文件内容中检索，任一标记缺失时提交 MUST 被中止，分支保持合并前状态，操作者收到缺失标记清单与处置指引（重新解决冲突，或判定该修复在目标分支结构中不存在、转登记豁免并在目标结构重做）。检查通过后方可提交并推送。

#### Scenario: 冲突解决弄丢修复内容时检查拦截
- **WHEN** 把 `release/5.7.x` 向上合并进 `release/5.8.x` 时，冲突解决选择了保留 5.8 的重构结构，导致 `BUG-102` 的修复内容在合并结果中检索不到
- **THEN** 合并结果完整性检查中止提交，列出缺失标记 `BUG-102`；`release/5.8.x` 保持合并前状态；处置指引给出两个出口（重新解决以覆盖该修复，或按豁免登记并在重构结构中重做）

#### Scenario: 修复内容在位时检查放行
- **WHEN** 同一合并重新解决后，各缺陷标记均可在合并结果中检索到
- **THEN** 检查通过，合并提交产生并推送，`git log <目标>..<源>` 为空成为该补丁已到达的判定依据

### Requirement: 删除 release 维护分支之前执行退役检查
删除 release 维护分支之前 MUST 检查该分支上已提交但尚未进入 main 的提交；存在此类提交时，逐笔处置齐全方可删除——确需保留的补丁完成向上合并并在合并记录中可追溯，判定无需保留的提交逐笔写明废弃理由并登记。删除后该系列的历史发布 MUST 仍能经 release 标签账本逐版还原。

#### Scenario: 未清账的分支删除被拒绝
- **WHEN** `release/5.7.x` 尚有 2 笔已进入维护分支但未合并进 main 的补丁提交，操作者发起分支删除
- **THEN** 退役检查拒绝删除，列出这 2 笔提交并要求先完成向上合并或逐笔登记废弃理由

#### Scenario: 处置齐全后删除且历史可还原
- **WHEN** 上述 2 笔提交完成向上合并（或一笔合并、一笔登记废弃且理由成文）后再次发起删除
- **THEN** 删除执行；`v5.7.8`、`v5.7.9` 等标签仍各自指向发布时的构建提交，逐标签解引用可完整还原该系列发布史

### Requirement: 补丁整条合并不可行时的 cherry-pick 例外必须成对登记
当源分支与目标分支代码位置分叉导致整条分支向上合并无法机械解决时，允许改用 cherry-pick 复制单个修复提交；该例外 MUST 满足：提交说明记录来源提交的完整哈希（沿用 git 的 `cherry picked from` 尾注）并追加判定记录（判定人、判定日期、整条合并不可行的原因）；例外复制的补丁 MUST 随目标分支的下一版本发布（发版即入账，不允许例外提交长期滞留分支头）。此后对账以该登记为权威，`git cherry` 的输出（含因内容改写而产生的假阳性未移植报告）仅作辅助信号。

#### Scenario: 例外复制随版入账且可检索
- **WHEN** `BUG-104` 补丁因 keepalive 模块在 `release/5.8.x` 中被重写而无法整条合并，操作者经判定改用 cherry-pick 复制并提交，随后发布 `5.8.2`
- **THEN** `v5.8.2` 的历史可追溯到该例外提交（含来源哈希与判定记录）；对该补丁的到达核对以登记记录为准，`git cherry` 的假阳性报告不阻断发布

#### Scenario: 未登记的复制提交被核对拦下
- **WHEN** 目标分支存在一笔无来源记录、无判定登记的复制提交，且该补丁尚未随任何版本发出
- **THEN** 发布前核对拒绝通过，错误信息指出该提交缺少例外登记，要求补齐登记或完成正式向上合并

### Requirement: release 维护分支仅接收补丁不接收特性
release 维护分支 MUST 仅接收缺陷修复类提交（经 fix 分支合入或向上合并承接）；特性类提交合入 release 维护分支的尝试 MUST 被拒绝。由此，"该补丁影响到的 release 维护分支清单"仅对修复类合并请求有意义：修复类 PR 的描述 MUST 声明该清单（哪些维护分支需要收到这笔补丁，判定不需要时写明理由），后续向上合并与退役核对以该清单为准；特性类 PR 不声明该清单，因为特性只进入开发版本分支并随其首次发布到达下游。

#### Scenario: 特性提交合入维护分支被拒绝
- **WHEN** 有人把新模块特性提交合入 `release/5.7.x` 并尝试发布 `5.7.10`
- **THEN** 该合入在评审或门禁层被拒绝，错误信息指出维护分支仅接收补丁，特性应经对应开发版本分支随下一系列发布

#### Scenario: 修复 PR 清单缺失被拦下
- **WHEN** 修复类 PR 描述未声明补丁影响清单即请求合入
- **THEN** 合入被拒绝，提示补全清单或写明不受影响的逐线理由
