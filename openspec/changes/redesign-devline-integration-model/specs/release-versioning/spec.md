# release-versioning 变更增量

## MODIFIED Requirements

### Requirement: 正式版版本串为裸三段号
在 release 维护分支（形态 `release/<主>.<次>.x`）上执行构建与发布时，仓库内全部制品的版本串 SHALL 为不带任何限定符后缀的裸三段号 `<主>.<次>.<补丁>`；补丁号 MUST 通过下一补丁号校验——目标版本号的前两段与该维护分支编号一致，且第三段恰为该分支已发布 release 标签的最大补丁号加一（首发为 0）。不符合以上任一条的发布请求，门禁 MUST 拒绝并在错误信息中给出该分支当前已发布的最大补丁号。

#### Scenario: 发布分支产出裸号版本
- **WHEN** 在 `release/5.7.x` 维护分支上以 `-PreleaseVersion=5.7.9` 执行构建与发布，且该分支已有的最大发布标签为 `v5.7.8`
- **THEN** 全部制品的版本串为裸号 `5.7.9`，推送至制品库的正式发布仓，发布后该分支产生 `v5.7.9` 标签

#### Scenario: 非法发布分支形态被拒绝
- **WHEN** 在 `release/5.7.x` 维护分支上以 `5.7.11` 执行发布而该分支当前最大发布标签是 `v5.7.9`
- **THEN** 下一补丁号校验拒绝该发布，错误信息说明允许的下一补丁号为 `5.7.10` 并列出拒绝原因（跳号需按规格例外程序另行成文，当前未设立）

#### Scenario: 编号前缀不符被拒绝
- **WHEN** 在 `release/5.7.x` 维护分支上以 `5.8.0` 执行发布
- **THEN** 发布被拒绝，错误信息说明版本号前两段必须与维护分支编号一致，`5.8.0` 应由 `release/5.8.x` 发布

### Requirement: 快照坐标形态跨发布期保持稳定
在开发版本分支（形态 `dev/<主>.<次>.x`）上执行构建时，制品版本串 SHALL 为 `<主>.<次>.x-SNAPSHOT`（快照坐标字符串与迁移前的 `N.M.x-SNAPSHOT` 完全一致，不含 `dev/` 前缀）；该坐标形态在该开发版本分支存续期间 MUST NOT 因任何正式发布的发生而改变。开发版本分支执行裸号正式版发布的尝试 MUST 被拒绝。

#### Scenario: 连续构建产出同一快照坐标
- **WHEN** `dev/5.7.x` 开发版本分支在一周内先后两次构建并发布快照
- **THEN** 两次产物均归属坐标 `5.7.x-SNAPSHOT`，由制品库的时间戳版本号区分先后；下游按迁移前坐标 `5.7.x-SNAPSHOT` 书写的依赖声明无需修改即可持续取得最新构建

#### Scenario: 开发线发布裸号被拒绝
- **WHEN** 在 `dev/5.7.x` 开发版本分支上尝试以裸号 `5.7.9` 形态执行发布
- **THEN** 发布被拒绝，错误信息说明开发版本分支只能发布快照形态，裸号正式版必须由 release 维护分支产生

### Requirement: 发布资格由分支形态白名单决定
构建系统 MUST 仅允许两种分支形态执行发布任务：开发版本分支形态 `dev/<主>.<次>.x`（可发 `<主>.<次>.x-SNAPSHOT`）与 release 维护分支形态 `release/<主>.<次>.x`（可发该编号系列的裸号）。其余任何分支（包括 main、feat 分支、fix 分支、以及不带 `dev/` 或 `release/` 前缀的旧形态分支）执行发布任务时 MUST 被拒绝，并在错误信息中给出当前分支名与两种合法形态。

#### Scenario: 白名单内分支发布成功
- **WHEN** 在白名单任一形态的分支上执行发布任务且其余门禁检查全部通过
- **THEN** 发布正常执行，产物进入与版本形态匹配的目标仓库

#### Scenario: 名单外分支发布被拒绝
- **WHEN** 在 `dev/5.0.x.net`、`feat/5.7.x-search`、main 或旧形态 `5.0.x` 分支上执行发布任务
- **THEN** 发布均被拒绝，错误信息包含当前分支名并说明发布仅允许在 `dev/<主>.<次>.x` 或 `release/<主>.<次>.x` 形态的分支上执行

### Requirement: 历史后缀形态占用的版本号不得复用
凡是历史上已正式发布过的版本号 SHALL 视为不可复用，占用来源分两类：其一为记录于版本库历史清单文件中的 `-RELEASE` 后缀形态占用号，其二为已在本仓库远端建立过 release 标签（`v<主>.<次>.<补丁>`）的裸号。任何发布任务的目标版本号命中以上两类记录时 MUST 被拒绝，错误信息说明该号的占用来源与占用形态。

#### Scenario: 未被占用的版本号正常发布
- **WHEN** 发布目标版本号 `5.7.9` 既不在历史清单中，远端也不存在 `v5.7.9` 标签
- **THEN** 门禁该项检查通过，发布继续

#### Scenario: 命中历史清单的版本号被拒绝
- **WHEN** 发布目标版本号 `5.5.0` 命中历史清单（该号曾以 `5.5.0-RELEASE` 发布）
- **THEN** 发布被拒绝，错误信息说明 `5.5.0` 已被历史后缀形态占用，禁止同号复用

#### Scenario: 已建标签的裸号被拒绝
- **WHEN** 发布目标版本号 `5.7.8`，远端已存在指向已发布提交的 `v5.7.8` 标签
- **THEN** 发布被拒绝，错误信息说明该号已有 release 标签存证，纠正只能发布更高补丁号

### Requirement: 发布标签是正式版发布的前置存证
裸号正式版发布执行前，构建系统 MUST 校验远程仓库已存在与目标版本号同名、且指向当前构建提交的 release 标签 `v<主>.<次>.<补丁>`（git 对象形态 MUST 为附注标签）；标签不存在、为轻量标签或指向不符时发布 MUST 被拒绝。校验先于任何目标仓库的网络传输执行——正式版同时发布至内网发布仓、Maven Central 与 GitHub Packages 镜像时，release 标签核验对全部通道共用且 MUST 在推送任一通道之前完成。发布成功后产生的每一个正式版，都 SHALL 能在远程标签账本中查到对应 release 标签；版本号、制品内容与代码提交位置三者的对账 MUST 以该标签的解引用记录为权威依据（标签即发布事实的存证，核验是门禁对该存证执行的动作）。

#### Scenario: 先建标签后发布成功
- **WHEN** 发布者已在 release 维护分支头创建附注标签 `v5.7.9` 并推送到远端，随后执行发布
- **THEN** 核验通过，`5.7.9` 各制品发布到正式发布仓，标签与制品成对存在

#### Scenario: 缺标签的发布被拒绝且孤儿标签可自愈
- **WHEN** 未创建 `v5.7.9` 标签直接执行发布；发布被拒绝后发布者补建标签并重新执行
- **THEN** 第一次执行被拒绝且正式发布仓不出现 `5.7.9` 制品；补建标签后的第二次执行通过核验完成发布，先前失败的发布未留下无存证的孤儿制品

#### Scenario: 轻量标签被核验拒绝
- **WHEN** 发布者误以 `git tag v5.7.9`（轻量标签）代替附注标签推送后执行发布
- **THEN** release 标签核验因对象形态非附注而拒绝发布，错误信息说明必须为附注标签并给出纠正指引（未推送的错标删除重建；已推送的错标按标签不可移动规则处置，提高补丁号重发）

#### Scenario: Central 通道共用同一前置校验
- **WHEN** release 标签缺失或指向不符时执行面向 Maven Central 的正式发布（GitHub Packages 镜像通道同样共用本前置，按其能力契约执行）
- **THEN** 推送在发生任何网络传输之前被拒绝，错误信息与内网通道的拒绝一致，公共仓库不出现缺存证版本

## REMOVED Requirements

### Requirement: 发布容器与标签一经创建不可移动
**Reason**: 一次性发布容器分支（`<主>.<次>.<补丁>.release` 形态）随本变更整体废除，"容器与标签成对冻结"的语义失去载体；补丁发布改为在常驻 release 维护分支上滚动进行。
**Migration**: 标签永不移动的约束由修改后的需求"release 标签是正式版发布的前置核验与权威对账依据"承接并加强（新增形态要求与权威对账地位）；维护分支自身的历史完整性由新增需求"主干与版本分支只追加不改写"承接；原"合回"动作（releaseMergeBack）由新增能力 branch-integration-gates 的"向上合并"及其配套检查取代。现存容器分支（如 `5.7.8.release`）保留为只读历史资产并在身份映射登记表标注退役状态。

## ADDED Requirements

### Requirement: 主干与版本分支只追加不改写
main、开发版本分支（`dev/N.M.x`）与 release 维护分支（`release/N.M.x`）的历史 MUST 只允许追加：向这三类分支推送时，MUST NOT 使用强制推送，MUST NOT 通过 rebase 改写已推送提交。main 的内容只允许来自两个途径——开发版本分支的集成到主干，以及 release 维护分支的向上合并；开发版本分支的内容只允许来自特性分支的 rebase 合入、主干同步合并与修复补丁合入；release 维护分支的内容只允许来自 fix 分支的合入与向上合并承接。允许强制推送的分支类型仅为 feat 分支与 fix 分支。

#### Scenario: 强制推送主干被拒绝
- **WHEN** 任何流程或人员对 main 发起携带强制标志的推送，客户端守卫或远端拒收规则任一生效
- **THEN** 该推送不生效；main 头保持在原提交，操作者收到改写被禁止的说明

#### Scenario: 维护分支滚动补丁保持历史只追加
- **WHEN** `release/5.7.x` 已发布 `v5.7.9` 后，后续补丁提交继续在该分支上追加并发布 `v5.7.10`
- **THEN** `v5.7.9` 标签及其指向的提交在分支历史中原封不动，新补丁位于其后；对 `v5.7.9` 的事后重建与核验仍然成立

#### Scenario: feat 分支是强制推送的唯一豁免
- **WHEN** 开发者对 `feat/5.9.x-search` 执行带 lease 保护的强制推送，同时对 `dev/5.9.x` 尝试同类操作
- **THEN** 前者成功（个人工位分支允许整理历史），后者被拒绝并说明开发版本分支只允许追加

### Requirement: release 维护分支自集成后的主干头切出且每系列唯一
每个已发布的 `<主>.<次>` 系列 MUST 有且仅有一条 release 维护分支，切出时机为该系列开发版本分支完成集成到主干之后，切出基点为集成后的 main 分支Head；切出时该系列的首发裸号版本（`<主>.<次>.0`）在维护分支头建立 release 标签。同一系列重复切出维护分支、或在维护分支存在期间对同系列再次发起"集成到主干"的尝试，MUST 被拒绝。

#### Scenario: 首发按序完成切分支、建标签、发制品
- **WHEN** `dev/5.8.x` 完成集成到主干后，发布者执行切维护分支任务并随后以 `5.8.0` 发布
- **THEN** `release/5.8.x` 自集成后的 main 头出现，`v5.8.0` 标签建立，制品进入发布仓；此三者对账一致

#### Scenario: 重复切出被拒绝
- **WHEN** `release/5.8.x` 已存在时再次对 5.8 系列执行切维护分支任务
- **THEN** 任务拒绝执行，错误信息说明每系列唯一并指向既有分支
