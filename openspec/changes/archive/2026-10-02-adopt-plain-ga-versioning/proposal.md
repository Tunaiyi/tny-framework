# Proposal

## Why

当前发布体系存在两类会持续腐坏的事实缺口。其一，正式发布（GA）的版本串携带 `-RELEASE` 后缀（例如 `5.5.0-RELEASE`）：该后缀不是 Maven 内建限定符，依赖升级助手与安全扫描类工具无法解析这种版本形态；并且 Maven 的排序规则把 `RELEASE` 限定符与无后缀裸号做了等价特判，一旦同一个版本号以两种形态进入仓库，版本比较将不可推理。其二，发布标签（tag）断代：仓库的 tag 账本停在 `v3.4.1-RELEASE`，此后 4.x 与 5.x 世代的发布（例如 `4.1.0`、`5.5.0`）只留下 `.release` 分支而没有对应 tag，分支头会随后续操作前进，导致"某个已发布版本出自哪个提交"这一问题如今无法可靠回答。两个缺口都随时间变差而不是变好，宜在本框架 5.7.x 线继续发布更多版本之前修复。

## What Changes

- 正式发布版本的版本串去掉 `-RELEASE` 后缀，改为裸三段号 `N.M.K`（**BREAKING**：下游业务工程升级时坐标形态改变，但公共 API 本身不变）。
- 每次发布成功后必须在发布提交上创建名为 `vN.M.K` 的附注标签并推送远端，标签自本次变更起恢复为发布事实的存证。
- 发布门禁从"版本后缀与分支名比对"升级为"分支形态判定"：名为 `N.M.x` 的开发线只允许发布快照版本，名为 `N.M.K.release` 的发布分支只允许发布裸号正式版，其余一切分支执行发布任务时直接拒绝。现状存在 feature 分支（例如 `5.0.x.net`）可以照常发布快照的漏洞，本条将其封堵。
- 新增同号黑名单断言：历史上已以 `-RELEASE` 形态发布过的版本号记入清单文件，裸号形态与清单冲突时发布被拒绝，防止同一版本号两种形态共存导致排序纠缠。
- 快照坐标的滚动形态保持不变（`5.7.x` 开发线持续发布 `5.7.x-SNAPSHOT`），并在文档中确立消费契约：快照坐标只允许精确锁定，禁止进入版本区间表达式，禁止交给自动升级工具跟踪。
- 仓库运维侧两项策略作为前置条件记录在文档（不在本次代码变更范围内执行）：发布仓库禁止重复部署同一版本，快照仓库配置按天数的保留清理。

## Capabilities

### New Capabilities

- `release-versioning`：版本串的派生规则、发布门禁的分支形态判定与拒绝行为、发布标签的存证要求、下游消费方所见的制品坐标形态契约。

### Modified Capabilities

（无。既有 spec 目录中不存在与发布版本相关的 capability，`benchmark-harness` 与 `integration-testing` 均不涉及版本派生行为，本变更不修改它们的需求。）

## Impact

- 构建脚本：`gradle/git.gradle`（版本派生函数与后缀常量的语义调整）、`gradle/publications.gradle`（发布门禁断言重写并新增黑名单与分支白名单检查）。
- `gradle/tny-module.gradle` 把 `project.version` 写入 jar 清单的 `Implementation-Version` 属性，版本串形态改变会随之影响所有构件的清单值；全仓库源码中没有读取该清单属性的代码，因此无运行期行为受影响（grep 取证：`getImplementationVersion` 零命中）。
- 全部已发布模块（50 余个 `tny-game-*` 与 `tny-game-starter-*`）的制品坐标形态与清单版本值受版本串变化影响；模块源代码与公共 API 均不修改。
- 下游业务工程：升级到新形态后，GA 依赖坐标从带后缀写法改为裸号写法；快照消费方式不变。
- 文档：消费契约三条与发布流程步骤记入 README 或 docs 目录。
- 不受影响：CI 的 bench 双通道与测试工程、`openspec` 流程本身、Nexus 服务器配置（运维侧另行执行）。
