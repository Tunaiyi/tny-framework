# Design

## Context

本变更的动机与现状缺口见 proposal.md 的 Why 一节。此处记录约束设计的技术事实。

**版本派生现状**（`gradle/git.gradle`）：`parseProjectVersion` 把分支名映射为版本串——以 `.release` 结尾的分支去掉后缀并追加 `-RELEASE`，其余分支追加 `-SNAPSHOT`。派生结果经 `build.gradle:87` 供给全部子模块，另有三处消费者（grep 取证）：`gradle/publications.gradle:63-65` 引用三个后缀常量做发布断言；`gradle/tny-module.gradle:7` 把 `project.version` 写入 jar 清单的 `Implementation-Version` 属性；全仓库源码检索 `getImplementationVersion` 零命中，即清单版本没有运行期读取方，版本串形态变化不构成运行期行为变化。爆炸半径说明：本仓库的 codegraph 索引只覆盖 Java 源码，`parseProjectVersion` 等 Gradle 脚本符号不在图内（符号检索返回均为无关基准类），因此上述 grep 结果是本分析的取证来源，这是本节方法的已知限制。

**发布门禁现状**（`gradle/publications.gradle:51-95`）：`validatePublishConsistency` 以"版本后缀与分支名、目标仓库类型三者比对"的形式存在，能拦截发布分支错发快照，但无法拒绝名单外分支（feature 分支按其名称派生出的仍是合法的 `-SNAPSHOT` 版本，可照常发布）。

**排序行为实测**（maven-artifact `ComparableVersion`，本次会话实验验证）：字母段与数字段比较时遵循"非零数字段大于字母段、字母段大于零或缺省段"的规则，即 `5.7.0` 小于 `5.7.x` 且 `5.7.x` 小于 `5.7.1`；同时 `RELEASE` 限定符与裸号在排序上被等价特判。前者意味着滚动快照坐标 `N.M.x-SNAPSHOT` 的排序位置不可直觉推理，只能用"精确锁定、禁入区间"的消费契约回避；后者意味着同号的两种形态一旦共存必然乱序，必须靠黑名单封堵。

**存证现状**：仓库标签账本止于 `v3.4.1-RELEASE`，其后的 `4.1.0.release`、`5.5.0.release` 两个发布世代没有标签；`git.gradle` 中的 `gitTag` 闭包用 `describe` 匹配 `*.release` 形态标签，与现存 `v*-RELEASE` 命名大小写与后缀均不符，当前恒返回空值，是版本链上的死代码。

## Goals / Non-Goals

**Goals:**
- 让正式版版本串成为合法且工具可解析的裸三段号，且同号两种形态在制度上不可共存。
- 让发布门禁把"谁有资格发布、发布什么形态"收紧到分支形态白名单，堵住 feature 分支误发。
- 让每一个已发布的正式版在任何时刻都能通过远程标签账本回答"出自哪个提交"。
- 保持快照消费通道对下游零改动。

**Non-Goals:**
- 不引入候选版本（rc/milestone）发布通道；未来出现外部灰度需求时另立变更。
- 不改为由标签推导滚动快照号的全 SemVer 方案；触发线是"快照通道出现第一个外部消费者"，届时另行提案。
- 不修改 Nexus 服务器配置；仓库不可变与保留策略作为运维前置条件写入文档，不在本次代码变更内执行。
- 不删除历史化石分支；标签恢复后删除不再有审计损失，另行低风险清理。

## Decisions

### D1 保留"分支即版本"派生机制，仅修正 GA 形态（P11 合同三问全过；先例：已归档变更 `centralize-java-version-property` 的同族"单一事实源"手法）
版本事实源继续是分支名，`parseProjectVersion` 只改发布分支分支：去掉追加 `-RELEASE` 的一行，直接返回裸号；快照派生不动。备选方案是业界默认的"版本文件声明加 Release 插件流"，否决理由：每次发布向历史追加两条 bump 提交，本仓库多条平行线并行时噪音与冲突面放大；现有断言体系（后缀与分支与仓库三方比对）正是为分支派生设计的，文件声明制下它失去意义；文件、分支、标签三个事实源的可漂移面反而更大。

### D2 快照坐标维持 `N.M.x-SNAPSHOT` 滚动形态，用消费契约回避排序问题（P11 例外，理由：快照不是合同，消费契约由 spec 明确其为内部集成通道）
备选方案是"由行内最大标签推导 `N.M.(K+1)-SNAPSHOT`"，否决理由：每个正式版发布都会让快照坐标跳一格，下游开发线必须随之改 pin，摧毁内部集成的稳定性；推导依赖标签集合与可达性，引入边界复杂度；而外部工具链只消费正式版坐标，滚动形态的排序缺陷不随 GA 形态外溢。实测的排序怪异性通过 spec 中"禁入区间、禁自动升级"的条款封闭在设计层面。

### D3 标签先行、发布在后的顺序（P13 可验证性：不变量"每个已发布正式版必有同名同指向标签"由门禁直接断言；P4 保护不变量而非流程约定）
发布裸号前，门禁校验远程已存在 `vN.M.K` 附注标签且指向当前构建提交，缺失即拒绝。备选方案是"发布成功后补打标签"，否决理由：发布与打标签之间存在崩溃窗口，一旦中断就留下无存证的孤儿制品，恰是本变更要修复的断代事故的形成机制。代价是可能出现"有标签无制品"的孤儿标签，该状态无害：补打标签后重试即自愈，spec 的 R5 错误场景对此有明确预期。

### D4 同号黑名单用版本库内清单文件，构建期读文件比对，不查询制品库（P13：该断言可被无网络的本地测试证明；先例：`tny-bench/build.gradle` 的 `benchRoutineClasses` 声明清单与目录双向对账手法，同一问题的框架内已有解法，M1 先例优先）
新增 `gradle/released-legacy.txt`，逐行列出历史上以 `-RELEASE` 形态发布过的裸号（初版由制品库管理端导出发布清单核对后一次性生成并提交）。备选方案是发布前实时查询制品库该坐标是否存在，否决理由：引入网络依赖与凭据面，本地测试无法覆盖，且制品库历史数据本身没有防误删保证，查询结果的可信度不高于入库清单。

### D5 发布门禁改为分支形态白名单判定，替代后缀比对（P4 不变量收紧；先例：`tny-bench` 的 `jmhSuiteVerify`"空匹配不得静默绿"的显式判红纪律）
门禁先判定当前分支属于开发线形态或发布分支形态，名单外直接拒绝并给出分支名与合法形态说明；名单内再按形态校验版本串与目标仓库的匹配。备选方案是维持后缀比对仅增补一条 feature 检查，否决理由：后缀比对下 feature 分支派生的本身就是合法后缀的快照串，检查项会退化为对派生结果的自我循环验证，无法从根上表达"谁有资格发布"。

### D6 把现有 `gitTag` 闭包修复为裸号形态的标签账本查询设施（P5 职责划分：派生与校验各自成函数；M1 先例优先：不新写标签查询逻辑，复活既有设施）
将其 `describe` 的匹配模式改为匹配 `v[0-9]*` 形态，并保留"本地找不到则查远程标签列表"的语义。备选方案是删除该闭包并在门禁内重写，否决理由：同一问题框架内已有设施，重写只是搬家，修复 glob 失配一处即让死代码转为活路径。

实施补记（verify 阶段修订本决策的记录）：规格 R5 要求校验的是"远程仓库已存在"附注标签，本地 `describe` 账本天然覆盖不了远端状态，因此 D3 门禁的实际数据源是 `git ls-remote`（附注标签含 `^{}` 解引用记录，指向比对用解引用后的提交）。`gitTag` 闭包按本决策修复为严格的裸号形态查询（宽 glob 加严格正则过滤，过渡期局限已注释在代码内），探针验证通过后作为本地标签账本与构建溯源的查询设施保留，不再声称充当 D3 输入。

### D7 门禁作用范围谓词按尾缀 `ToMavenLocal` 排除整条本地发布链（verify 阶段回写；P4 保护不变量：门禁守护的不变量是"共享仓发布必须合规"，本地发布不触及该不变量）
`publishesToSharedRepository` 原判断只排除 `publishToMavenLocal` 任务本身，其依赖任务 `publishMavenJavaPublicationToMavenLocal` 仍命中"以 publish 开头"而被挂上门禁。7.1 端到端空跑实测暴露：发布分支缺远端标签时本地发布被连带拒绝，"本地坐标直通"的上游意图落空。修复为按尾缀 `ToMavenLocal` 排除整条链。备选方案是保留原谓词让本地发布也受标签门禁约束，否决理由：本地发布不改变制品库事实，要求远端存证既无保护对象，又把本机环境问题（PATH 上的 git 二进制与守护进程架构不匹配）放大为阻塞；规格与任务文本（"合法裸号经 publishToMavenLocal 产出本地坐标"）均以本地直通为前提。

## Risks / Trade-offs

- 下游业务工程未察觉 GA 形态切换，升级时按旧后缀写法找不到制品。→ 形态变化只影响"新发布的版本"，历史制品不受影响；首个裸号版本发布时在变更日志与 README 消费契约段落同时声明，且门禁错误信息不涉此路径（下游是消费侧，无法用门禁拦截），最终靠文档与通知。
- 黑名单初版清单漏项，同号复用防线的地基不完整。→ 生成初版时从制品库发布仓全量导出坐标清单，与 `git tag` 账本及 `.release` 分支头互相对账，三方一致后提交；tasks 中把对账列为显式任务。
- "标签先行"改变发布人员的操作顺序习惯。→ 发布流程四则写入文档（见 tasks），门禁拒绝信息明确提示"先创建并推送标签 vN.M.K"。
- `Implementation-Version` 清单值随形态改变，未来若有代码开始读取该属性并依赖后缀。→ 全仓库当前无读取方（grep 取证），spec 已将裸号形态固化为外部契约，读取方出现时按裸号解析。
- 回滚窗口不对称：门禁、白名单、黑名单均可整体 revert 单函数恢复原状；但裸号一旦发布进不可变仓，GA 形态就是单向门，回滚只能回到"停止发布等新机制修复"而非"退回旧后缀"。→ 首次裸号发布前先在预发或本地图文校验流水上空跑一次 publish，确认派生与门禁行为后再真实发布。

## Compatibility Impact

公共 API（`com.tny.game.*` 类型、报文协议格式）零变化，P11 三问中"旧调用是否仍可编译运行"与"报文格式是否向后兼容"两问天然通过。受影响的是制品坐标形态：升级到新正式版（例如 `5.7.8`）的下游必须把依赖版本从带 `-RELEASE` 后缀的写法改为裸号写法，该动作本来伴随每次版本升级发生，形态变化被升级动作吸收；快照坐标 `5.7.x-SNAPSHOT` 及 `groupId`、`artifactId`、包结构均不变，开发线下游零感知。jar 清单 `Implementation-Version` 的值形态随之变为裸号，已核实无运行期读取方。历史制品（含 `5.5.0-RELEASE` 等）在仓库中保持原样，锁死旧版本的老工程不受任何影响。

## Migration Plan

1. 门禁先行合入：黑名单文件生成与对账、白名单判定、标签校验三项断言先落地并配测试，此时 GA 派生仍是旧形态，一切行为向后兼容（无发布分支真正走完新流程前不会产生拒绝）。
2. 派生切换合入：`parseProjectVersion` 返回裸号；在本地或预发通道空跑一次发布任务验证版本串与门禁，不留真实制品。
3. 下一个正式版本（例如 `5.7.8`）按新流程执行：切发布分支、建标签推送、发布、merge-back，四则流程文档同步交付。
4. README 消费契约三条落地（快照精确锁定、正式版裸号升级规则、弃用宽限）。
5. 回滚策略：第 1、2 步各自独立可 revert；第 3 步执行后 GA 形态不可逆，回滚方案仅为"暂停发布直至修复"，故第 2 步的空跑验证是关键闸门。
