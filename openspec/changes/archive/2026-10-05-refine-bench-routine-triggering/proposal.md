# Proposal

## Why

基准执行通道现在对每一次进入 main 或 5.7.x 的提交都跑约二十分钟的完整计时并自动回写结果文件，而进入这两条分支的提交里相当一部分是文档、openspec 案卷和工作流脚本自身——它们不会改变任何框架代码的行为，为它们计时没有观测价值。2026-10-01 晚间的实况是：六轮推送触发六轮计时，分支上追加了六个自动回写提交，其中一轮因为执行窗口内分支被无关提交前进而发生了回写被拒的竞态。另一方面，合入反馈的速度也被全程计时拖累：三十七个参数组合里有二十四个是加密装配矩阵，当天合入的反馈并不需要它们，真正回答"主干性能有没有被打坏"的只有十三个组合。还有一个 split-bench-suites 变更留下的隐性债务：执行通道从"只有夜间定时（只在默认分支生效）"扩展到"两条分支的每次合入"之后，main 与 5.7.x 两套代码基线的性能数据点会被记进同一组历史曲线，两条线演进不同步时，劣化告警会因基线切换而误触发。

## What Changes

- 执行通道增加**内容门禁**：只有触及框架行为的合入才触发计时——判定标准是本次提交改动了模块源码目录、任一 Gradle 构建脚本、根目录版本配置或基准模块代码；纯文档、案卷、流水线脚本的合入不计时、不回写、不在分支上产生自动提交。定时与手动触发不受门禁约束，永远执行。
- 计时拆分为**两个规模**：合入时执行速览面（报文全管线编解码、发送缓存队列、RPC 响应配对、设施探针，共十三个参数组合，全程约七至九分钟）；夜间定时与手动触发执行完整面（三十七个组合，含加密装配矩阵，维持现状时长）。矩阵级退化由夜间兜底，最迟半天内可见。
- **历史曲线按触发分支与计时规模分组**，告警比较只发生在同组序列内部，消除 main 与 5.7.x 基线混杂带来的误报。
- 结果产物的文件名指纹增加规模标识，逐版对比要求同规模成立。
- 保持不变（明确非目标）：评审通道的零计时契约、回归判定的人裁决纪律、基线测量参数（fork 数与迭代轮数不降精度）、单元与集成测试通道的触发规则、bench-compile 评审作业的全触发属性。草稿 PR 跳过 CI 属另议项，不在本变更内实施。

## Capabilities

### New Capabilities

（无——本变更全部落在既有 capability 内。）

### Modified Capabilities

- `benchmark-harness`：
  - **修订 Requirement**「CI 双通道职责边界」——执行通道的触发由"主干与维护分支的一切合入"收窄为"可能改变框架代码行为的合入"，并把合入场合的执行规模明确为速览面、定时与手动场合明确为完整面；新增曲线序列按分支与规模分组的约束。
  - **修订 Requirement**「结果产物结构化可对比」——产物文件名指纹增加计时规模标识，逐版对比与同日期覆盖语义限定在同规模之内。

## Impact

- `.github/workflows/build.yml`：新增一个数秒级的内容判定作业；`bench-routine` 作业增加放行条件并按触发场合向计时命令传递规模参数；曲线存储步骤的序列分组名增加分支与规模。
- `tny-bench/build.gradle`：新增速览面清单声明（常规基准族的子集，与既有族清单同处集中声明）；计时入口支持规模选择；结果导出任务按规模区分产物文件名。基准缺省本地执行行为不变。
- `tny-bench/README.md`：执行面章节改写为两规模口径，产物引用约定增加规模标识，时长预算更新为实测值。
- **零公共 API、零报文协议变更——非 BREAKING**；不受影响的部分：单元/集成测试、发布装配线、`:tny-bench` 零发布守卫、`jmhSuiteVerify` 族属对账（速览面是常规族的子集，族属声明结构不动）。
- 与在途变更的边界：`consolidate-ci-it-lanes` 的提案明确声明 bench 作业不在其范围，`fix-ci-unit-flakes` 只动 unit 作业——本变更只动 bench-routine 链路，三方在 `build.yml` 上无同段冲突。
- 运行成本预期：文档类合入的基准机器时间降为零；框架合入的单轮计时从约二十分钟降到七至九分钟；夜间与手动保持完整覆盖。
