# Design

## Context

动机与核对结论见 proposal.md - Why。此处只交代改写设计所需的现状约束：主账本 `central-publishing` 五条需求现文（其中两条带双通道计数措辞）、`github-packages-mirror` 已独立成文镜像全部行为契约、`docs/release-process.md` 有两处同步计数句、两处归档 tasks 有待注销的登记条目。

## Goals / Non-Goals

**Goals:**

- 账本计数措辞与三目的地现实对齐，且不改任何发布行为义务。
- 能力边界清晰：`central-publishing` 陈明目的地与独立性，`github-packages-mirror` 陈明镜像行为——互不吞并。
- 两处归档登记待办以引用注记注销，账本闭环无悬挂。

**Non-Goals:**

- 不改任何代码、CI、门禁与发布行为（纯措辞维护）。
- 不改 `central-publishing` 其余三条需求与 `release-versioning`、`github-packages-mirror` 任何条文。
- 不重写归档文件原文（注销以追加注记形态）。

## Decisions

### D1 改题需求以差量"删除加新增"成对表达，另一条走真 MODIFIED

**决定**：两条需求均改题并以差量 REMOVED（含 Reason 与 Migration 指新题）加 ADDED（新标题全文）成对表达："双仓并行发布相互独立"改题"多目的地并行发布相互独立"；"快照构件发布到 Central 快照仓"改题"快照构件多目的地并行发布"。初稿曾拟第二条保留标题走 MODIFIED，严格校验裁定不可——MODIFIED 整块替换不得更名或删除主账本既有场景（"双通道"计数嵌在原场景名"快照双通道分发"中），成对改题是唯一不留计数失真的合规路径。

**依据**：openspec 差量按需求标题匹配主账本，改题若只写 MODIFIED 会在归档时旧条目残留、新旧并存——此机制约束由上一变更（open-github-packages-snapshot-mirror）的三对成条差量入账实践验证。

**被否决的备选**：第二条保留标题、场景名同步保留旧"双通道"字样而正文写三目的地。否决理由：标题与场景名的计数失真仍在，且义务句与场景名互相矛盾，等于没核对。

### D2 扩写为"同时发布至三个目的地"的肯定枚举，并各加能力边界句

**决定**：两条需求正文均把目的地枚举写全（正式版三、快照三），同时新写边界句声明"本需求仅陈明目的地枚举与独立性语义，各通道自身契约归各自条文"，并在快照需求中补一句镜像的参与方式（每日定时、本机不扇出）以防读者把三目的地误读为"本机 publish 会推镜像"。

**依据**：核对的两个候选结论（扩写/记录式关单）中用户裁决扩写；边界句防止未来第四目的地出现时两个能力互相争夺枚举权威，镜像参与方式句直接引 `github-packages-mirror` 已成的定时契约，不重复立法。

**被否决的备选**：其一，只在旧句后补"另有镜像"式的括号补丁。否决理由：计数措辞（双仓/两通道）仍在句中，失准未消除。其二，把镜像的独立性与判读义务也抄写进 central-publishing。否决理由：与 `github-packages-mirror` 条文重复，两处立法必有漂移日。

### D3 文档联动限于两处计数句，指路不复制

**决定**：`docs/release-process.md` Central 发布节仅改 CI 通道句"两通道分步独立执行"与快照通道句"双目的地"两处为三目的地现文，镜像细节以指路（"见 GitHub Packages 镜像通道一节"）表达。

**依据**：镜像节已成完整现文，文档同信息只允许一处权威（P5 单一变更原因的文档对应物）；其余段落（Nexus 前置条件、阶梯、体量）无计数失真不动。

**被否决的备选**：文档全节重写对齐。否决理由：超出核对所需，触碰即改精神反对无关清扫。

### D4 归档待办以追加引用注记注销

**决定**：在 `archive/2026-10-06-add-github-packages-channel/tasks.md` 与 `archive/2026-10-06-open-github-packages-snapshot-mirror/tasks.md` 的登记段落末尾各追加一行"已由 align-central-publishing-channel-enumeration 于 2026-10-06 核对并扩写"的引用注记，不改写任何原文。

**依据**：归档不可篡改的既有纪律（本仓归档目录只在引用改指时被动编辑）与 open 变更归档时为 add 变更追加引用注记的先例一致。

**被否决的备选**：删掉归档待办条目。否决理由：抹除登记历史，复诊线索断裂。

### 适用范围声明

原则卷 P 编号与模式卷针对 Java 代码结构，本变更零代码产出，逐条不适用；codegraph 无符号可分析（纯 markdown 规格维护），影响面即 proposal.md - Impact 清单。

## Risks / Trade-offs

- [改题需求的归档匹配错误（REMOVED 标题与主账本现文有出入即合并失配）] → 实施任务内置机械核对：差量 REMOVED 标题须与主账本 `grep '^### Requirement:'` 逐字一致后才允许归档。
- [边界句写得过窄，未来第四目的地再次失准] → 边界句采用"仅陈明枚举与独立性"的角色声明句式而非穷举承诺，第四目的地出现时仍按本先例扩写枚举即可，语义不碎。

## Migration Plan

实施顺序：写差量（已完成于本变更目录）→ 文档两处 → 归档注记两处 → `openspec validate --strict` → 归档同步入账。回滚：本变更全部为文本改动，revert 提交即净。
