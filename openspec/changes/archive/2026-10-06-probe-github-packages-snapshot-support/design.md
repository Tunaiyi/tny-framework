# Design

## Context

动机见 proposal.md - Why。此处只钉实验所需的技术现状与约束：

- 既有证据分层：Gradle 上传快照可行与 curl 探测字面名 404 已实证（归档目录 `openspec/changes/archive/2026-10-05-add-github-packages-channel/verification/sandbox-probe.md` 结论 1、2）；消费端工具解析行为与注册表服务端对客户端自造 unique 快照布局的受理性未测，是本调查的两个目标。
- 注册表快照协议参照（消费端应有的行为，实验要钉死 GitHub 上实际发生哪条）：Maven 消费方解析快照坐标时先取 `{baseVersion}-SNAPSHOT/maven-metadata.xml`，若其含 `<snapshot><timestamp><buildNumber>` 块则拼装带时间戳文件名取构件；若无该块则退回字面名请求。Gradle 消费方同类但历史版本对非 unique 快照仓的支持形态不一，需实测。生产者侧 Maven 官方部署工具（`mvn deploy`）发布的就是"时间戳文件加目录级快照元数据"这套 unique 布局——实验二用手工 PUT 复刻该布局，以把注册表服务端能力与发布工具链选择解耦。
- 环境事实：本机无 Maven 可执行文件（`which mvn` 未命中）；Docker 29.4.0 可用；Gradle 8.14.5 经本仓 wrapper 可得；gh 登录态 classic 令牌含 `repo` 与 `write:packages`，不含 `delete_repo`（上一轮实测确认，沙箱清理需用户网页端协助或先补 scope）。
- 上一轮沙箱的全部实测手法（最小发布工程、守卫属性注入、GraphQL/REST 查询）已归档可复用。

## Goals / Non-Goals

**Goals:**

- 把"镜像上的 Gradle 快照消费方不可用"从 curl 推断升级为 Gradle 与 Maven 两个真实消费端的请求序列级实证。
- 判定 GitHub Packages 注册表服务端是否接受客户端自造的 unique 快照布局（目录级含 `<snapshot>` 块的元数据加带时间戳构件），以及接受后两种消费端能否据此解析成功。
- 产出三出口判定表对应的裁决建议，登记为未来变更的输入材料。

**Non-Goals:**

- 不修改本仓任何生产文件（构建脚本、CI、文档、主账本），不开放快照通道——通道开通由调查结论驱动的独立变更裁决。
- 不引入本机常驻工具链（不安装 Maven）；容器化 Maven 仅在调查期间存在。
- 不测试 SNAPSHOT 之外的版本形态（alpha/rc 等不在本框架发布形态内）。

## Decisions

### D1 沙箱载体：新建一次性私有仓库 `Tunaiyi/gpr-snapshot-spike`

**决定**：实验全部在新建私有沙箱仓库的 Packages 内进行，调查结束删除整个仓库。

**依据**：与上一变更 D10 同理——实验会制造需要删除的垃圾版本与可能被服务端改写的元数据，不能落在生产命名空间；创建与删除成本均为一分钟级。

**被否决的备选**：其一，复用已删除的 `gpr-sandbox`。不可行（仓库已删）。其二，在生产仓库以保留号段试点。否决理由：本轮实验可能反复触发服务端元数据改写行为，生产命名空间承受未验证写入的风险高于一次性沙箱，且试点痕迹清理依赖 `delete_repo` 权限缺口。

### D2 Gradle 消费端实验：独立工程加显式解析触发

**决定**：在 `/tmp` 建独立消费者工程，仓库声明指向沙箱镜像地址（凭据经属性注入、元数据来源用默认 `mavenPom`），以自定义任务调用 `configuration.resolve()` 触发真实下载；分别记录对"Gradle 发布的普通快照坐标"（实验一阶段）与"自造 unique 布局坐标"（实验二阶段）的解析结果与请求序列（配合 `--info` 抓取 HTTP 层日志存档）。

**依据**：`resolve()` 的失败形态（哪个 URL、哪个状态码）就是消费端协议的第一手证据；`--info` 日志可完整还原请求序列。

**被否决的备选**：用编译期依赖隐式触发解析。否决理由：失败信息混入编译报告，请求序列不可读，取证质量低。

### D3 Maven 消费端实验：Docker 容器运行官方 Maven 镜像

**决定**：本机不安装 Maven；用 `docker run maven:3.9-eclipse-temurin-21` 执行 `dependency:get -DremoteRepositories=https://maven.pkg.github.com/<沙箱路径> -Dartifact=<快照坐标>`，凭据经挂载的一次性 `settings.xml`（server id 与 remote id 匹配，文件置于临时目录，实验结束删除）。

**依据**：本机无 mvn（Context 已证）；容器镜像是 Maven 官方发行版，消费端行为即标准协议；Docker 是本机既有工具链，无环境副作用。

**被否决的备选**：`brew install maven`。否决理由：为一次性调查引入常驻环境变更，越出调查边界。

### D4 unique 布局自造方式：先经 Gradle 产出真实构件，再改名 PUT

**决定**：实验二先用 Gradle 对同一坐标发布一次（取得内容合法的 jar 与 pom 字节），随后把构件复制为带时间戳文件名（`{artifact}-{base}-{yyyyMMdd.HHmmss}-{buildNumber}` 形态），与手工生成的目录级 `maven-metadata.xml`（含 `<snapshot><timestamp><buildNumber><lastUpdated>`）一并 PUT 至快照目录；每步 PUT 记录 HTTP 状态与响应体摘要。

**依据**：构件内容合法性与布局实验无关，复用 Gradle 产物省去手工造字节；PUT 的每一个响应就是服务端态度的直接证据。

**被否决的备选**：直接编写微型 pom 与空 jar 上传。否决理由：合法内容经 Gradle 现产更省事，且保留"同一内容经两种发布端形态"的对照能力。

### D5 服务端接管观测：PUT 前后与滚动前后的元数据字节对比

**决定**：每次元数据 PUT 后立即 GET 目录级 `maven-metadata.xml` 并存档全文，做三方对比——发送内容、返回内容、既有自动维护内容；随后执行第二次 PUT（新时间戳、buildNumber 递增），再观察服务端是保留客户端值、重写、还是拒绝。这组对比本身构成"注册表能否承载外部 unique 快照发布者"的核心判定证据。

**依据**：上一轮实测已知注册表会自动维护 artifact 级元数据（`lastUpdated` 自动推进、versions 列表自动收录），目录级快照元数据的接管行为未知，正是要测的。

**被否决的备选**：只测一次 PUT 成功与否。否决理由：单轮结果无法区分"接受""接受后改写""接受但消费端读不到"三种状态，判定表要求滚动轮次与消费端复核两轮证据。

### D6 判定表与结论出口

**决定**：实验结果按下表裁决，结论报告（`verification/snapshot-spike.md`）必须落进其中一格并给出对应后续路线：

```
                        服务端对 unique 布局    消费端解析同一坐标     结论与出口
 E-A 两列皆成立          接受且不改写元数据      Gradle 或 Maven 成功    技术上可开通快照通道；
                                                                   另立变更评估发布端成本
                                                                   （Maven 工具链或生成任务）
 E-B 服务端否决          拒绝 PUT 或立即改写掉    不适用                主账本"快照不进镜像"获
         <snapshot> 块                                             得终局实证，归档注记收尾
 E-C 接受但消费失败      接受且保留              两端仍失败            同 E-B 出口，另附协议
                                                                   层证据说明失败请求序列
```

**依据**：调查的价值在可裁决——预先钉死出口避免"测完仍要开讨论会"。

**被否决的备选**：只出数据不出判定。否决理由：数据没有出口就不是调查材料而是日志堆。

### D7 凭据处理纪律

**决定**：GitHub 侧写操作一律用本机 gh 登录态令牌经环境变量临时注入（`ORG_GRADLE_PROJECT_*` 与前缀 `x-access-token` 风格不参与设计），任何脚本与记录文件不落令牌明文；容器挂载的 `settings.xml` 置于 `/tmp` 临时目录并在清理任务中删除；实验记录中的 HTTP 请求行如含 Basic 头一律脱敏后存档。

**依据**：项目 GitHub 操作规则禁止 Agent 保管凭据；上一轮实测已按同纪律执行。

**被否决的备选**：新建专用短期令牌。否决理由：gh 登录态已具备全部所需 scope（读包、发布、GraphQL 删除版本），再造令牌只增加管理面。

### 适用范围声明（design 规则的形式交代）

原则卷 P1-P13 与模式卷决策表针对 Java 代码结构设计，本变更不产出任何生产 Java 代码或构建脚本改动，逐条不适用；codegraph 爆炸半径分析无对应符号（生产代码零触碰），影响面已在 proposal.md - Impact 以清单交代。实验工程（`/tmp` 下一次性消费者与发布者工程）不受本仓代码规范约束，随沙箱消亡。

## Risks / Trade-offs

- [gh 令牌缺 `delete_repo`，沙箱删除会 403] → 清理任务预置双出口：命令行失败即转用户网页端删除（上一轮已演练此路径），并把"沙箱存续期间勿向生产仓库发布"写入任务注意事项。
- [Docker 容器访问 GitHub 网络不通或需要代理] → 实验前置一条容器内 `curl -sI https://maven.pkg.github.com` 连通性检查，不通即暂停上报，不带病跑实验。
- [服务端对目录级元数据的接管行为可能导致实验二出现"PUT 成功但内容被改写"的中间态] → D5 的字节对比正是为捕获此形态而设，属观察对象而非风险；报告如实记录三态之一。
- [Gradle 消费端对非 unique 快照仓的行为随版本漂移] → 实验钉在本仓 wrapper 的 Gradle 8.14.5 与容器内 Maven 3.9 固定执行，版本写入记录；其他版本行为不外推。
- [实验期间沙箱包占用的坐标与未来生产坐标同名] → 沙箱坐标使用 `io.sandbox.snap` 组号与 `gpr-snap` 构件名，与生产坐标（`com.tnydev.game`）永不冲突；实验结束删仓即净。

## Migration Plan

执行顺序即依赖顺序：

1. 建沙箱仓库；跑容器与 Gradle 消费端连通性前置检查。
2. 生产侧：Gradle 最小工程发布 `0.1.0-SNAPSHOT` 与 `0.1.0`（正式版本作对照组），存档注册表落库形态（目录清单与两级元数据）。
3. 实验一：D2 与 D3 对普通快照坐标各跑一次消费端解析，取证失败形态；对照组（正式版本坐标）两端应成功。
4. 实验二：D4 手工 PUT unique 布局，D5 记录服务端接管三态；再次跑 D2 与 D3 消费端解析取证；执行滚动轮 PUT 与复核。
5. 结论按 D6 判定表落 `verification/snapshot-spike.md`（含每条证据的请求序列、状态码、元数据字节对比），给出裁决建议。
6. 清理：删除沙箱仓库（命令行受阻则请用户网页端执行）、删除临时消费工程与挂载凭据文件。

**回滚**：本变更无生产改动，回滚等于删除沙箱与临时文件；主账本维持原样即天然回滚态。

## Open Questions

- 若结论落入 E-A（可开通），unique 快照发布端选型（Maven 工具链引入与 gradle-build-style 的关系、或本仓 Gradle 任务自生成时间戳布局）属后续变更的设计议题，本调查不预支。
- 实验是否补充校验和文件随 unique 布局 PUT（先不带，若消费端因缺校验和失败再补一轮）属执行期可自决的细节。
