**存量 5.7.8 的实测分叉（verify 轮发现，修正本册早期声明）。** 远端 `5.7.8.release` 头
（`3c8e723d`）与标签 `v5.7.8^{}` 解引用（`7a2a287d`）指向不同提交——旧机制在其发布后移动过
容器头，容器、标签、制品三方对账已经分叉。本变更按"旧机制末例"处置：不追溯、不重构历史，
5.7.8 的出处以标签为准记档；该分叉恰是新律"容器与标签一经创建不可移动"必要性的活证据。

**main 的实测状态与转正推论。** `github/main` 头为 2024-01-11 的提交 `315f54bf`，落后
`github/5.7.x` 129 个提交、领先 0 个——`main` 是 `5.7.x` 的严格祖先，自身零独有内容。
由此得到一个无需任何豁免的对齐动作：`git push github 5.7.x:main` 是一次普通快进，
非快进会被服务端天然拒绝。GitHub API 确认 `default_branch: "main"`（转正后无需改设置）；
本地 `master` 与 `main` 同头（化石，删除项）；远端无 `master`。

**规格与规则约束。** 本变更修改 `gradle/release.gradle`，按 `gradle-build-style` 需求
第八条的渐进条款，该文件全文须满足其八条需求。`release-versioning` 既有五项需求判定输入
不变；本变更以差量新增"发布容器与标签一经创建不可移动"一条，四个场景在三层形态下逐字
成立（差量文件不随本次工件修订改动）。main 不发布制品由既有白名单需求覆盖（main 不属于
两种可发布形态），无需新增校验。

**爆炸半径分析（codegraph 记录）。** 按项目规则先跑 `codegraph_symbol_search` 检索
`releaseRebaseBack`：命中的全部是 Java 产品代码里的 `release` 系列符号——codegraph 索引
不覆盖 `.gradle` 脚本与 Gradle 任务名。因此爆炸半径以上文 grep 全量清单为准，封闭在
构建脚本、两份文档、两个工作流文件与 GitHub 仓库设置内，无产品代码触点。

**方法论两卷检索结论。** 模式卷第二节决策表的先例全部是 Java 对象层模式（策略、适配器、
职责链、Context、门面等），对"构建脚本编排与 git 分支流"没有对口先例；按模式卷 M2 条款
（一次设计引用 0 至 2 个模式是正常的），本设计不引用任何模式，原则引用落在下列决定中。

## Goals / Non-Goals

**Goals:**

- 分支体系三层定形：特性只进 main，冻结线只做维护与滚动快照，发布层（容器加标签）不可
  移动；补丁号对下游诚实——发布为补丁版本的内容里不再出现新特性。
- 发布容器分支与其标签在创建推送后成为不可移动对象，使标签、容器头、制品三者对账恒等，
  并让"对容器分支事后重放构建"成为永远可通过门禁的动作。
- 常规发布与 hotfix 收拢到同一条三步工具路径（切支、打标签、合回），消除命令文档里
  "hotfix 不要用工具"的特例。
- 七条分支生命周期流程白纸黑字化（创建与使用特性分支、rebase 特性分支、开特性版本线、
  发布特性版本、创建与 rebase fix 分支、同步 fix 提交），每节可被未参与读者一遍读懂。
- `main` 转正为开发顶点：默认分支、PR 底分支、CI 恒常基线三个入口与内容事实对齐，
  不引入任何同步镜像义务。

**Non-Goals:**

- 不改发布门禁五重校验与版本派生逻辑（`buildSrc/src/main/groovy/tny.publish.gradle`、
  `tny.git.gradle` 与 `GitFlow` 类零改动）。
- 不建跨线下传的工具任务；不实现 `release.published` 触发器的自动化（留开放问题）。
- 不给 main 提供发布通道（main 上的构建只跑 CI，不出制品）。
- 不处理"发布操作应在独立 worktree 执行"的操作纪律（另行决定）。
- 不清理 5.7.x 之外的历史线分支；不在本变更里归档 `migrate-git-calls-to-grgit`
  （归档由用户在门户命令中完成，本变更仅宣告其目标终结）。

## Decisions

**D1：合回唯一原语为"重放到所属线头加普通推送"，容器永不移动。**
依据 P5（按变更原因划职责：容器记录发布事实、几乎不变；开发线记录维护推进、常变；现行
变基机制把两者绑成同一变更原因）与 P6（"一次性发布容器"的书面承诺必须被机制兑现，重写
后再用注释自圆就是打折）；依据 P12（该承诺先以新增需求入账，代码对照需求实现）。
被否决备选：
（a）保留变基加解释性文档——标签与容器头和 CI 三方对账仍分叉，事后重放构建永远被自家
门禁拒绝，否决；
（b）`merge --no-ff` 合回——引入合并提交，违背开发者已拍板的开发线线性历史要求，否决；
（c）合回后即删容器分支——hotfix 场景仍需要容器作为修复落点与人追溯工位，省一个分支不是
收益，否决。

**D2：任务面拆为 `releaseCut`、`releaseTag`、`releaseMergeBack` 三个动作，标签时点等于
制品定型时点。**
依据 P5（切支因版本号分配而变、打标签因制品证据而变、合回因维护推进而变，三个变更原因
三个任务）与 P13（每步的验证手段独立可答：cut 后查远端容器头、tag 后查标签解引用、合回后
核对三方一致性）。常规发布是"切支后立即打标签"的退化形态，hotfix 是"修复定型后打标签"，
同一代码路径。被否决备选：单任务加 `-PtagMode` 开关——参数组合状态比拆分任务面更大，
命令文档仍需分场景描述，且干跑预览无法分别展示两个外向动作，否决。

**D3：hotfix 切基必须显式 `-PreleaseFrom=v<上一版本>`（工具接受标签、分支、提交三种来源，
但不自动推断上一版本号）。**
理由：上一版本号的推断在"补丁号有空洞、维护线与当前线并存"的现实下不可靠，推断错了会把
发布基切错地方；P13 的判据是人显式输入可被门禁二次核对，自动推断无法自证。
被否决备选：按 `git tag --sort=-v:refname` 自动取最近裸号标签——错误推断的爆炸半径是一整次
错误发布，且多线并存时"最近"本身有歧义，否决。

**D4：传播与同步立为"最上游优先、每笔修复最多两站"的手工纪律，不建工具任务。**
规则本体：修复原型在 main 产生（常规路径，特性与通用缺陷同处演进前沿）；波及维护线时把
该提交按序重放到每条受影响线的线头（第一站），某线需要立即发布时照走容器三步（重放同时
经容器进线，仍是每线一站）；例外是线原生缺陷（main 已无该代码路径）——修复原型直接落
该线，完成后必须把同一提交重放上收到 main（反向补到顶点），否则 main 静默失真。波及线
清单与"判定不波及"的理由都写在修复 PR 描述里，作为对账账本；`git cherry <老线> <新线>`
提供补丁级只读对账。依据 P5（判定职责在人、复制原语在机器）。业界印证：Linux/JDK/Spring
采用的正是"修复先合主干、再以 cherry-pick 逐维护线下传"的同一纪律。被否决备选：
（a）`releaseBackport` 任务——为单一未见过的场景预建抽象，波及判定也无法工具化，否决；
（b）Chromium 式"最老分支先行、逐级向上合并滚动"（与用户原始 B 案配套的传播方向）——
修复第一落点要每次回答"该 bug 从哪版存在"，且新代码常与老修复冲突，冲突被集中到最新侧，
否决。

**D5：`main` 转正为开发顶点而非冻结落地页。**
一次性快进对齐（`git push github 5.7.x:main`，main 是 5.7.x 严格祖先，实测成立），此后
main 只向前生长（实施时实际经历"先快进、后遭 bench 回写 rebase 重写本地链、再以
cherry-pick 把账本提交上收 main"两段，形态偏差与证据见 D10 与
`verification-findings-2026-10-04.md`）；GitHub 默认分支保持 main（新访客与贡献者第一眼即顶点）；`build.yml` 的
main 触发项由死配置转活；本地 `master` 删除。main 不发布制品，由既有分支形态白名单天然
保证，零门禁改动。被否决备选：
（a）落地页冻结方案（本提案上一版）——main 空位不解决贡献入口与 CI 基线问题，且默认分支
继续展示两年前的内容或需改设置，否决；
（b）把线与容器内容定期合并进 main 做聚合镜像——形成第三本账，与标签、线两账必然漂移，
否决；
（c）main 上启用发布通道（如 `main-SNAPSHOT`）——main 名字不携带版本，与 C2"版本语义住
在分支名"冲突，且下游并无对未发布特性制品的既证需求，否决。

**D8：三层形态裁决——采纳 C 案（main 顶点＋冻结线＋不可动发布层）。**
三个候选：A 案＝现行模型（线兼任特性推进与补丁发布，5.7.k 可含新特性）；B 案＝用户提议的
补丁分支链（`5.7.[0-n]` 每补丁一分支，修复在最老受影响分支产生后逐级向上滚动合并）；
C 案＝本设计定形。裁决：A 案否决——补丁号携带特性对下游 semver 说谎，而下游兼容性是
本项目硬约束，这是本次重新思考击中的第一真痛点；B 案否决——补丁分支发布后必须继续前进
（为下一补丁备料），分支头与其同名标签必然分叉，"分支名等于已发布版本"变成半真陈述，
刚立的容器不可动律要弱化为"仅标签不可动"，证据柱子从两根减为一根；每补丁一分支的
数量与逐级滚动合并的站数成本，买到的是"修复从最老处生长"的方向，而该方向把冲突集中到
最新代码侧且贡献者每次先答"从哪版存在"，代价高于收益；C 案采纳——保留已定案的容器、
标签、重放原语与三步任务全部机制（零弱化），只加一层 main 顶点即同时满足 semver 纯度与
贡献入口两需求。依据 P5（层的划分按变更原因：特性演进、维护推进、发布事实是三个变更
原因）、P10（不为未见场景预建补丁链层）、P6（分支名一旦承诺版本语义不得半真）。

**D9：分支生命周期与强推白名单。**
特性分支与 fix 分支（个人工位）：允许自由 rebase、允许对**仅自己推送过的**远端工位分支
force-push；就绪后以 rebase-merge 方式进 main（保持 main 线性，squash 可选）。
冻结线、容器、标签：任何时刻任何人不强推、不 rebase、不移动；线的推进只接受快进推送
（普通提交、重放提交）与 PR 合入。全仓承诺从"不存在 force-push"精确化为"force-push 仅
存在于个人工位分支，且其产物永远不进入发布链的可信路径（进入 main 前必经 rebase-merge
重铸）"。七条流程文档按此展开：创建特性版本分支（从 main 切 5.8.x 并推送，附开线仪式
清单：CI 线入口登记、旧线维护态声明、主版本号另附兼容性评估）；创建特性分支（基=main 头，
命名自由）；rebase 特性分支（定期 `git fetch && git rebase origin/main`，PR 前收尾）；
发布特性版本（5.8.0＝在 5.8.x 线头走容器三步，合回零提交跳过）；创建 fix 分支（基=main，
main 无该代码路径时基=受影响线头）；rebase fix 分支（同上，最终 rebase-merge 进 main 或
线）；同步 fix 提交（按 D4 的两站规则执行并做 `git cherry` 对账）。依据 P13：白名单的
每条禁令都对应一条可查的远端核对命令。

**D6：通道基线沿用现状——写操作走 git 子进程，只读查询走 grgit。**
证据链：5.7.8 首发的真实执行修正提交（`976896b4`）确立了写走 CLI 的已验证形态；grgit 的
写路径在本次时间线上从未完成真实执行验证（本会话早前的等价演练未提交即被现场修正覆盖）。
P13：遵循已被实战证明的路径，不再同时赌两条通道。`migrate-git-calls-to-grgit` 变更的
写通道统一目标就此终结，其实录保留在该变更目录供追溯。
被否决备选：在新脚本中改用 grgit 写路径——缺乏实战验证且与本变更主题无关的风险叠加，否决。

**D7：`buildSrc/src/main/groovy/tny.release.gradle` 按 `gradle-build-style` 八条需求整文件重写。**
该脚本属需求第一条许可的两个容身之处之一——buildSrc 约定插件脚本（多步顺序操作的收纳地），
根脚本装配线保持 `apply plugin: 'tny.release'` 单行引入不变；
三个任务全部 `tasks.register` 惰性注册；任务体内为动作期程序逻辑（合规位置）；字符串纪律
（无插值一律单引号）、区块顺序（常量、原语、步骤闭包、任务装配）、注释只写原因与规格出处、
文件头让三十秒扫读者能答"本文件固化了哪三个发布动作、为什么"。
被否决备选：拆成多个脚本文件——总量可控，拆分只增加导航面，否决。

**D10：verify 轮修复清单（2026-10-04 独立审查确认项的处置）。**
依据 P6（"全体保持原状"等契约文案不许打折）与 P13（每条修复附可运行的验收），
九项修复及验收如下，实施后对应任务按新验收重做：
（一）重放失败的状态保全协议：`releaseMergeBack` 在检出线之前记录线原头（本地存在取
`rev-parse line`，本地缺失取 fetch 后的 `remoteName/line`）；任一 `cherry-pick` 失败时依序执行
`cherry-pick --abort`、`reset --hard <原头>`、`switch <容器>`，然后抛错——此前只 abort 当前一笔，
先前成功的重放永久落在本地线上，与规格场景"全体保持原状"不符。验收：多笔重放中后笔冲突的
演练断言线头回到原头。
（二）`rev-list` 与 `git cherry` 检查退出码：非零即抛（含 stderr），失败不得被空输出伪装成
"已全部上线，跳过"。验收：坏 baseRef 的参数注入演练报"命令失败"而非"跳过"。
（三）`releaseCut` 补回本地同名标签撞名检查（拒绝文案沿用旧"同号发布禁止重复建标"）。
验收：本地预置未推送同名标签后 `releaseCut -PdryRun` 即被拦。
（四）预览路径纯净化：`dryRun` 判断提前到 fetch 与 rev-list 之前，预览分支不得触任何 CLI
与本地引用变更（远端存在性判断改用 grgit 查询）。验收：本机 PATH 坏 git 且不带
`-PgitExe` 时三任务 `-PdryRun` 全部成功；`[dryRun] 未做任何变更` 横幅下确无本地 ref 变动。
（五）`releaseTag` 重跑幂等：本地已存在同名标签且解引用指向当前 HEAD 时跳过创建、仅补推送
（推送失败的恢复路径按文案可重跑）。验收：制造推送失败后重跑成功且标签对象字节不变。
（六）`releaseFrom` 推断收窄为仅开发线形态：删除容器形态的缺省推断分支（设计 D3"hotfix
必须显式上一版本标签"字面成立）。验收：站在旧容器上不带 `-PreleaseFrom` 执行 `releaseCut`
被指引文案拒绝。
（七）`tny.release.gradle` 压缩回 `gradle-build-style` 需求七的 250 行硬界线以内（现役 273 行；
压缩注释冗余，不牺牲需求六"只记原因"的信息）。验收：`grep -c ""` 不超 250 且八条自查过。
（八）文档四处修复：流程七的验证命令方向改为 `git cherry <新线> <老线>` 为空（现写法在

## Risks / Trade-offs

- [任务更名使进行中的 `central-publish-tnydev-group` 验证账本仍引用旧名] → 该账本属另一
  会话、不代改；`docs/release-process.md` 保留旧任务名到新任务的映射一行，一次检索可对齐。
- [下游把 `5.7.x-SNAPSHOT` 内容口径收窄感知为功能退步] → 契约变更在 proposal 已标
  BREAKING；任务 5.4 要求在首个次版本发布就绪时投递书面迁移说明（含 `5.8.x-SNAPSHOT`
  启用时点），且坐标字符串不变、既有锁定无需改依赖声明。
- [main 转正后贡献者（含 AI 会话）惯性把特性 PR 发向 `5.7.x`] → 默认分支已是 main，PR
  创建页默认正确；文档在冻结线角色一节明写"此线拒绝特性 PR"；门禁白名单保证即使线被
  误合特性，产出的仍是 5.7 快照（不污染补丁号），危害降级为口径纠偏。
- [并行 `gradle-build-style` 清理与本变更组 1 修改同一文件] → 实施顺序上让清理先行合入
  （其改动以行为等价重构为主）；本变更组 1 以当时工作区形态为起点，演练与冒烟覆盖回归。
- [GitHub Actions 分支通配符语义若与预期不符，`build.yml` 线入口调整失效] → 实施任务里
  以真实 push 验证 main 与线各一次；不成立则显式列举现役线并在开线仪式清单补登记步骤。
- [hotfix 拖延过久导致重放冲突面大] → 设计上接受：冲突自动中止保持三方原状，错误信息
  给出人工等价命令，人工兜底是规格场景之一。
- [标签时点后移引入"忘记 releaseTag 就 publish"的新失误面] → 门禁第 5 重校验原样兜底
  （拒绝文案即"请先建标签"），无新增风险敞口。
- [重写脚本引入行为回归] → 演练复用临时 bare 仓库基础设施，对三步序列与"合回后三方一致"
  断言先行验证；所有对外文案在评审中逐字对照旧文。

## Migration Plan

1. 前置已核销（开工时确认）：`migrate-git-calls-to-grgit` 已于 2026-10-03 归档，
   `gradle-build-style` 清理与 buildSrc 插件化已合入 HEAD。
2. 重写 `buildSrc/src/main/groovy/tny.release.gradle` 与根脚本引用注释；改写
   `docs/release-process.md` 与 `.claude/commands/tny/release.md`。
3. 临时 bare 仓库演练三步序列（含 hotfix 形态：标签在修复提交之后）与合回后三方一致断言。
4. 仓库运维（人工确认后执行）：`git push github 5.7.x:main` 一次性快进转正；删除本地
   `master`；`build.yml` 触发清单核对并以真实 push 验证 main 与现役线各一次。默认分支
   与 main 的历史内容无需任何处理（快进后 main 即顶点）。
5. 切换点：自下一个发布（5.7.9 起）按新流程执行；特性开发区自运维步骤 4 完成后即 main。
6. 契约变更通知：首个次版本线（5.8.x）开线后，任务 5.4 的迁移说明投递下游；在流程文档
   "首版验收"句补记。
回滚：各文件独立成提交，`git revert` 即恢复旧任务形态；main 快进无法"反向快退"但无害
（main 头此后照常向前演进即可，不产生需要抹除的历史）。
