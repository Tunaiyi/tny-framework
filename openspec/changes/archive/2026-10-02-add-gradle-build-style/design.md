# Design

## Context

动机见 proposal.md 的 Why 一节。本变更的改动对象是规格账本与根 `CLAUDE.md` 的文本分工，不触及任何 Java/Groovy 运行代码，也不改变构建行为；因此本仓库已建的 codegraph 符号级爆炸半径分析在本变更没有适用对象（改动集合中没有函数、类或接口符号），此限制如实记录于此而非留空。设计方法论两卷中，原则卷 P1 至 P10 约束 Java 代码结构，本变更不涉及代码结构；可迁移引用的是一条原则卷条目与其精神：P5（单一职责按"变更原因"划分）与 P12（行为变更先于代码变更，即先改契约再动实现）。规格账本的先例参照：`release-versioning` 能力把发布行为契约全文放在 `openspec/specs/`，根文档不重复正文；`central-publishing` 变更确立的"组号单一事实源"是构建侧"一个事实只声明一次"的在册先例。

当前共存状态：本会话已把规则全文写入根 `CLAUDE.md` 的"Gradle 构建脚本规则"一节。进行中的 `central-publish-tnydev-group` 与 `migrate-git-calls-to-grgit` 两个变更正在修改 `gradle/` 下的脚本，若本变更做全文件重写会与它们产生改动竞争。

## Goals / Non-Goals

**Goals**
- 规则的唯一权威文本落在 `openspec/specs/gradle-build-style/spec.md`（经归档流程后），评审、验证、后续变更引用规格编号而不是引用会话内文本。
- 明确 `CLAUDE.md` 与规格账本的分工：前者收缩为指针与执行要点，后者承载规范性需求与场景。
- 定义渐进落地方式与人工验收手段，使规则在不建设自动工具的前提下可检查。

**Non-Goals**
- 不清扫存量违例脚本（`build.gradle` 的 projectsEvaluated 对账块、spread 赋值、`settings.gradle` 注释残留等均维持原样，等待各自被触碰时修正）。
- 不新建 lint 或校验任务来自动检查脚本书写形态。
- 不修改任何 `.gradle` 文件的构建语义。

## Decisions

**D1：规则正文的唯一权威出处放在 openspec 能力规格，根 `CLAUDE.md` 该节收缩为指针加执行要点。**
依据 P12（行为变更先于代码变更）的精神推广到契约文本：契约只在账本声明一次，工作规则文件引用它，不在两处维护两份正文（先例：文字规则一节虽全文在 `CLAUDE.md`，但它约束的对象本来就是"一切文本"而无法被构建评审引用；构建脚本形态恰恰需要可引用的验收编号）。
否决的备选方案：
- 全文留在 `CLAUDE.md`、规格只写摘要——否决理由：摘要与正文两个版本随时间漂移，评审时无法裁定以哪份为准。
- 放 `docs/` 下单独成文——否决理由：`docs/design` 是方法论卷而非行为契约账本，openspec 的归档同步与验证机制覆盖不到它，规则会脱离"每条需求必须有场景"的质量约束。

**D2：生效方式为"触碰即改"的渐进制，全仓清扫另行立项。**
理由：全仓约六十个 `.gradle` 文件若一次性合规化，产生的纯文本差异会与两个进行中改 `gradle/` 脚本的变更直接竞争，且回归排查时无法区分"风格改动引入的行为变化"与"功能改动引入的行为变化"。
否决的备选方案：立即全仓清扫——否决理由如上述竞争与归因困难；这也符合仓库上下文"逐步还债"的既有纪律。
依据 P5 的划分精神：风格清扫与功能变更的"变更原因"不同，不应合并在同一个变更里。

**D3：验收手段定为人工评审加静态检索清单，本变更不建设自动化检查任务。**
理由：八条需求中至少"注释解释来由""扫读测试""条件化配置须附注释"三条需要语义判断，grep 与解析类工具无法覆盖；工具自身又是一个必须遵守本节规则的构建脚本，建设它会把变更范围从立规矩扩大到写脚本。
否决的备选方案：随变更交付一个 Gradle 校验任务自动判红违例形态——否决理由：覆盖面不足会给出"已通过机器检查"的错误安全感，且违背克制原则 P10 的精神（抽象与设施要等重复需求出现再建，目前规则尚未在真实评审中反复使用）。风险条目"规则失守靠评审自觉"见下文缓解。
若日后自动化检查立项，应作为独立变更引用本能力的规格编号。

**D4：能力命名 `gradle-build-style`，范围只约束构建文件的书写形态，不触碰发布与验证的行为契约。**
依据 P5：书写形态与发布行为是两种变更原因——改一条语言纪律不该牵动发布门禁的规格评审。`release-versioning` 与 `integration-testing` 两个既有能力约束的是"发布出什么版本串""集成测试怎么跑"这类行为结果，与本能力的文本形态契约互不重叠。
否决的备选方案：把规则并入 `release-versioning`（同为构建侧约束）——否决理由：该能力的 Purpose 明确限定在版本派生与门禁，混入脚本书写需求会让其场景清单不再可用同一评审视角读完。

## Risks / Trade-offs

- **两份文本漂移**：`CLAUDE.md` 指针化后若仍残留具体规则句，会与规格正文各自演化。缓解：指针节只保留适用范围、权威出处与"触碰即改"一句总纲，具体形态全部以规格为准；apply 任务里包含逐条比对。
- **并行变更与触碰即改的差异竞争**：两个在途变更正改 `gradle/` 脚本。缓解：本变更自身不修改任何 `.gradle` 文件，只立契约；触碰即改的适用范围限于各变更自己的改动区域，规则第"存量违例按触碰即改"需求已写明不得超范围清扫。
- **无自动工具导致执行靠自觉**：缓解：规格每条需求配了正常与违例两个场景，评审可按场景编号逐条核对；grep 清单（旧式 `task ` 声明、`*.options*` spread、分号结尾行、`////include`）列入 tasks 作为可机械执行的最低检查面；工具化留给后续独立变更。
- **长度界线与存量文件冲突**：`gradle/publications.gradle` 现有 257 行，已超 250 行界线。缓解：界线只约束"新增与本次修改后的形态"，存量按触碰即改渐进回到界线内，规格文本未要求即刻达标。

## Migration Plan

1. apply 阶段执行 tasks.md：先把 `CLAUDE.md` 相应节收缩为指针，再跑校验与 grep 清单确认本次改动未新增违例。
2. 归档阶段由 openspec 档案流程把差量同步进 `openspec/specs/gradle-build-style/spec.md`，自此主账本生效。
3. 回滚策略：本变更的可逆面是 `CLAUDE.md` 一节与新增文件，恢复该节原文并删除变更目录即可完全回退，不存在构建行为回滚需求。
