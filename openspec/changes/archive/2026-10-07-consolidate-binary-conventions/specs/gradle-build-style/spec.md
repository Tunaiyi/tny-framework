# gradle-build-style 差量（consolidate-binary-conventions）

## ADDED Requirements

### Requirement: 约定插件接线规则按载体定
约定插件之间的组合形态 SHALL 由载体决定：二进制形态的约定插件（实现类）之间 MUST 允许直接相互引入，并允许以按插件类型或按插件 id 的反应式接线（`plugins.withType` / `plugins.withId` 形态的"在位才配置"）组织装配次序；预编译脚本插件之间在过渡期内 MUST NOT 相互嵌套引入（嵌套引入触发类加载器服务缺失缺陷，Gradle 8.5 发现、Gradle 8.14.5 复测仍复现，复测记录见归档变更目录 `openspec/changes/archive/2026-10-07-pilot-binary-build-conventions` 的 design 记录），因此在最后一个预编译脚本插件退役之前，工程构建脚本 MUST 继续按依赖顺序对每个脚本形态约定插件各用一行引入语句装配。二进制实现类内按插件 id 引入第三方插件时，其实现类的类路径供给 MUST 落在两处之一：根构建脚本的插件声明块（带版本、`apply false` 形态），或 buildSrc 依赖声明；同一插件的实现类 MUST NOT 同时在这两处各带版本号（版本声明唯一落点）。

#### Scenario: 二进制插件间反应式组合得到通过
- **WHEN** 一个二进制约定插件在装配逻辑中引入另一个二进制约定插件，并以按类型反应式接线在目标插件在位时补配置
- **THEN** 同一工程两插件都生效且重复引入幂等（已应用者不二次应用），装配合法；读者从入口类目录页即可读出组合全貌

#### Scenario: 脚本插件嵌套引入被判违例
- **WHEN** 某变更让一个预编译脚本插件嵌套引入另一个预编译脚本插件
- **THEN** 评审判定违例（配置期即抛类加载器服务缺失错误），要求把该组合改到二进制载体上，或回到工程构建脚本逐行引入的过渡期形态

#### Scenario: 第三方插件版本双声明点被判违例
- **WHEN** 某第三方插件的 jar 已经由 buildSrc 依赖声明供给，根构建脚本的插件声明块又对同一插件带版本号声明
- **THEN** 评审判定违例（版本出现两处声明点，违反单一事实源在本面的延伸），要求退役其中一处并核对应用行为与产物零漂移

## MODIFIED Requirements

### Requirement: 工程配置写声明式语句，程序性行为限定容身之处
仓库内全部 `.gradle` 文件 SHALL 以声明式语句描述工程配置：每一行陈述"某项东西被配置成什么"，配置阶段（脚本求值生成任务图的阶段）MUST NOT 出现循环、分支、中间变量逐步累加等程序性控制流。确需条件化配置时，只允许"属性的取值按条件选择"与"布尔条件守卫单条声明语句"两种形态，且 MUST 附一行注释说明条件的来由。命令行调用、跨项目对账校验、多步顺序操作等程序性行为属于任务动作而不属于工程配置，MUST 限定在两类位置：任务注册闭包内的动作块（如执行期才运行的动作代码），或 buildSrc 约定插件的载体——预编译脚本插件文件、其二进制实现类，以及由实现类直接调用、不单独注册插件 id 的扩展类与支撑类（"同一插件 id 二选一，MUST NOT 并存"只约束脚本文件与实现类两种可被引入的形态；扩展类与支撑类本无插件 id，是实现的组成部分，工程构建脚本 MUST NOT 直接引用它们）——根构建脚本与模块构建脚本 MUST NOT 书写此类行为，对约定插件的引用 MUST 只有一行插件引入语句。多个装配线共用的同一段配置 MUST 收编为可组合的共享约定插件，MUST NOT 在两个及以上插件载体中逐字复制同一配置块；确有差异的近似块 MUST 在注释写明差异来由。

#### Scenario: 声明式主体与编排脚本分离得到通过
- **WHEN** 评审一位未参与过程的新增脚本：模块构建文件逐行为配置声明，git 发布编排位于 `tny.release` 约定插件，根构建文件只有一行插件引入
- **THEN** 该脚本符合本需求，读者顺着读下来即可理解全部配置意图，无需跟随控制流还原语义

#### Scenario: 配置阶段写入过程式对账被判违例
- **WHEN** 某变更把带循环、分支与异常抛出的跨模块对账校验直接写进根 `build.gradle` 的配置阶段
- **THEN** 评审判定违例，要求把该逻辑移入约定插件载体（脚本或二进制实现类）或独立任务的动作块，工程脚本保留单行引入

#### Scenario: 共享配置块逐字复制被判违例
- **WHEN** 两条装配线的约定插件各自抄写同一段仓库与镜像路由配置，评审发现两处内容逐字相同
- **THEN** 判定违例，要求把该段收编为独立的共享约定插件供两线组合引入；若两处实为"形同而义异"，须按注释写明差异后方可保留

#### Scenario: 同一插件 id 双形态并存被判违例
- **WHEN** 某插件 id 同时存在预编译脚本文件与 gradlePlugin 注册的二进制实现类
- **THEN** 评审判定违例并要求二者取一，因为并存时解析次序不可预期，读者无法从任一处读全该插件行为

#### Scenario: 判定逻辑收进支撑类得到认可
- **WHEN** 某装配入口的实现类把一项对账判定与一段 POM 配置分别委托给同目录内未注册插件 id 的支撑类与扩展类
- **THEN** 符合本需求：委托对象同属二进制形态载体的容身之处；若工程构建脚本出现对支撑类的直接引用，则改判违例，要求引用回到插件引入行

### Requirement: 扫读测试与长度界线作为验收标准
每个 `.gradle` 文件 SHALL 通过扫读验收：未参与变更的读者用三十秒扫读后，应当能答出该文件所辖模块依赖什么、用什么编译、发布到哪里；回答需要跟随控制流或打开其他文件才能成立的，脚本 MUST 重排结构。长度界线：模块 `build.gradle` 与根 `build.gradle` MUST NOT 超过 80 行（根脚本是配置说明书的目录页，只承载插件引入与身份声明），约定插件脚本 MUST NOT 超过 250 行；二进制形态的每个类——装配入口实现类、其调用的实现单元类、扩展类与支撑类——各自 MUST NOT 超过 250 行，界线按单类计量、MUST NOT 以"实现单元聚合行数"跨类合并计算或反向豁免。对一个模块行为跨多个类分散的装配单元，三十秒扫读的替代判据为：总装配入口类的头注释 MUST 提供该单元全部配置行为的清单式目录（每项行为指名其所在类——实现类、扩展类或支撑类），读者从目录页出发两跳内可定位任一行为的实现处。版本目录不受行数界线约束，但 MUST 按依赖族分组并以注释标明各族职责。超过界线的变更 MUST 把该拆的逻辑拆到独立类、独立分域插件或收进任务动作块之后才能合入。

#### Scenario: 三十秒答出模块三问
- **WHEN** 一位未参与过程的读者拿到 `tny-game-net/build.gradle`，扫读三十秒
- **THEN** 他能说出该模块依赖哪些兄弟模块与第三方件（具名访问器）、以哪条装配线约定插件编译、经发布插件的通道发布，无需打开其他文件

#### Scenario: 超长脚本拆分后才可合入
- **WHEN** 某装配线约定插件因新增验证与任务逻辑增长到超过 250 行
- **THEN** 评审拒绝按现状合入，要求把验证逻辑移入独立分域插件或改为任务动作块，使文件回到界线之内

#### Scenario: 跨类装配缺目录页被判违例
- **WHEN** 某装配单元的读者需要打开三个以上类才能拼出该单元的完整配置行为，而总装配入口类头注释没有行为目录
- **THEN** 评审判定违例，要求在总装配入口类 javadoc 补齐行为清单（每项指名所在类），或合并过度碎裂的类

#### Scenario: 单类计量的装配单元得到通过
- **WHEN** 某装配单元的入口实现类与十余个协作类各自都在 250 行界线之内、合计远超 250 行，且入口类头注释目录页完整
- **THEN** 符合本需求：长度界线只以单类计量，聚合行数不构成违例；违例判据始终是"某一个类越过界线"或"目录页缺失"
