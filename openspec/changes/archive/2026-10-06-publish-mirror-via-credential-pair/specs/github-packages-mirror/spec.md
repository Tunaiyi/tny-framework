# Spec Delta

## REMOVED Requirements

### Requirement: 镜像通道按凭据密钥在位守卫声明且未配置机器行为不变
**Reason**: 用户 2026-10-06 复裁把镜像凭据从单密钥属性改回用户名与令牌两属性成对判定，且"凭据只在持续集成注入"义务反转为允许发布者本机配置——标题内嵌的"凭据密钥"随之失真，成对改题。
**Migration**: 见本差量 ADDED 条目"镜像通道按凭据对在位守卫声明且未配置机器行为不变"，未配置机器行为不变式原样承接，凭据形态与注入位置按新拍板改写。

### Requirement: 正式版本与快照镜像由持续集成独立执行并全量继承发布门禁
**Reason**: "新构建进入镜像的唯一来源 MUST 是持续集成运行，发布者本机 MUST NOT 执行镜像发布"的义务被 2026-10-06 复裁推翻（本机持凭据对时可发布镜像），标题内嵌"由持续集成独立执行"随之失真，成对改题。
**Migration**: 见本差量 ADDED 条目"镜像由本机与持续集成双来源执行并全量继承发布门禁、通道相互独立"，门禁全量继承与通道独立义务原样承接，来源约束改为本机与持续集成双源并存。

### Requirement: 快照构件进入镜像通道并随重发滚动到最新构建
**Reason**: 正文含"快照镜像 MUST NOT 由发布者本机执行"句子且场景名内嵌"凭据密钥"字样，双源与凭据对两项复裁都无法在保留标题与场景名的正文修改中表达，成对改题。
**Migration**: 见本差量 ADDED 条目"快照构件经双来源进入镜像并随重发滚动到最新构建"，滚动、独立编号、权威归档、不清理声明与门禁不减免义务原样承接，来源义务按双源改写。

## ADDED Requirements

### Requirement: 镜像通道按凭据对在位守卫声明且未配置机器行为不变
构建系统在 GitHub Packages 镜像的两个凭据属性 `githubPackagesUsername` 与 `githubPackagesToken` 成对在位时，SHALL 为纳入镜像范围的模块把 GitHub Packages 的 Apache Maven 注册表仓库（地址 `https://maven.pkg.github.com/tunaiyi/tny-framework`，URL 的属主段按注册表命名规则全小写）加入发布目的地集合，工程版本为裸号正式版本形态或开发线快照形态均在声明之列；版本形态的发布资格甄别由发布门禁的分支形态白名单与版本形态一致性断言承担，声明守卫不参与甄别。两个凭据属性 MUST NOT 写入仓库内任何文件；可注入持续集成执行环境，亦可配置于发布者本机用户级构建文件。凭据未成对非空在位（含只配置其中一个的半配置态与任一属性值为空的态样——空值或缺失均视同不在位）时，该目的地与其全部发布任务 MUST NOT 出现，其余构建与发布命令的行为 MUST 与本变更实施前逐任务一致，配置阶段 MUST NOT 因缺失或半配置凭据报错。Basic 认证的用户名由配置方提供与令牌对应的 GitHub 账户名（持续集成以工作流运行账户填充）。

#### Scenario: 未配置镜像凭据对（含半配置）的机器行为不变
- **WHEN** 未成对配置镜像凭据的开发者在任意构建与 `./gradlew publish` 中执行（未配置、只配置其中一个属性、任一属性值为空三种情形）
- **THEN** 任务图中不存在任何指向 GitHub Packages 的发布任务，发布产物与失败行为和本变更实施前逐任务一致，配置阶段不因缺失或半配置凭据报错

#### Scenario: 凭据对在位时任一发布形态目的地被声明
- **WHEN** 构建环境（持续集成注入或发布者本机用户级配置）成对在位两个镜像凭据属性，并在发布分支形态或开发线形态上执行构建
- **THEN** GitHub Packages 进入发布目的地集合，逐仓镜像发布任务可用；未成对在位时该目的地不被声明且配置阶段不报错

### Requirement: 镜像由本机与持续集成双来源执行并全量继承发布门禁、通道相互独立
正式版本形态与开发线快照形态的构件镜像均有两类合法来源：发布者本机在镜像凭据对成对在位时经 `./gradlew publish` 扇出；持续集成独立步骤（正式版本：release 事件与指定发布分支的人工触发；快照：定时计划每日执行当前开发线一次，选线以线谱系登记的状态为唯一依据，维护态与退役线不在定时范围、仅经人工指定线名的补跑触发）。通道相互独立：一个通道失败 MUST NOT 撤回或污染已成功通道的已发布内容，一个通道重试 MUST NOT 重推已成功通道。本机与持续集成对同一正式版本号先后发布时，MUST 按需求"同号正式版构件一次成型且重复上传可判读"的判读义务处置（重复上传拒绝按"构件已在镜像中"的存证判读，持续集成对应步骤的失败可按发布流程文档忽略），不引入新的来源互斥机制。镜像发布任务 MUST NOT 减免发布门禁的任何一项：四项发布凭据属性断言、分支形态白名单、版本形态与仓库路由一致性、同号历史黑名单、发布标签远端存证核对、发布依赖形态核对在两种形态、两类来源的镜像运行上照常先行执行；其中同号历史黑名单与发布标签远端存证两项按自身适用规则只对发布分支形态发生作用，属适用范围的一致表达而非对快照形态的减免。

#### Scenario: 镜像步骤失败不累及其他通道
- **WHEN** 一次正式版发布中内网仓库与 Central 步骤先成功，随后镜像步骤因网络故障失败
- **THEN** 内网与 Central 的构件保持已发布状态，构建报告独立呈现镜像通道的失败与原因，处置者可以只重试镜像步骤而不重跑其余通道

#### Scenario: 缺发布标签存证的正式版镜像被拒绝
- **WHEN** 远端不存在附注标签 `v<版本>` 时执行正式版本的逐仓镜像发布任务（本机或持续集成发起均同）
- **THEN** 镜像被一致性门禁以标签存证缺失拒绝，GitHub Packages 上不会出现该版本的任何构件，发布纪律不因新通道或新来源出现旁路

#### Scenario: 快照镜像步骤失败不累及其他快照通道
- **WHEN** 一次开发线快照的持续集成发布中，内网快照仓与 Central 快照仓分发成功，随后快照镜像步骤因网络故障失败
- **THEN** 两条既有通道的快照构件保持已发布状态，构建报告独立呈现镜像步骤的失败与原因；处置不需要升号或删除动作，下一次快照发布（任一来源）自然补齐镜像缺失的构建

#### Scenario: 本机持凭据对的快照发布扇出镜像
- **WHEN** 发布者本机成对配置镜像凭据，在开发线执行 `./gradlew publish`
- **THEN** 快照构件在同一次发布中进入内网快照仓、（Central 凭据在位时的）Central 快照仓与 GitHub Packages 镜像；其与每日定时镜像的共存重发属常态新鲜度维护，各构建时间戳文件名互不相同、互不冲突

### Requirement: 快照构件经双来源进入镜像并随重发滚动到最新构建
开发线形态（分支 `<主>.<次>.x`、版本 `<主>.<次>.x-SNAPSHOT`）的快照构件 SHALL 镜像进入 GitHub Packages 的 Apache Maven 注册表通道，收录的模块范围与正式版本同一边界（见需求"镜像构件边界与消费方凭据要求"）。注册表服务端为每次快照上传分配带构建时间戳的存储文件并自动维护该快照坐标的元数据，消费方携有效凭据按快照坐标解析 MUST 能取得最近一次发布的构建（缓存刷新后滚动到最新，重发后旧构建仍按其时间戳标识可取回）；同一快照坐标的重复上传 MUST NOT 被按重复拒绝——各次构建文件名互不相同，不构成覆盖，重发是快照镜像维持新鲜度的常态手段，不适用同号一次成型义务（见需求"同号正式版构件一次成型且重复上传可判读"的适用范围限定）。同一快照构建的文件字节在镜像与内网两侧一致，但该坐标的时间戳与构建号标识由每个仓库各自独立编号，消费方以所在仓库的解析结果为准选取最新构建。快照的权威归档继续由内网快照仓库与 Maven Central 快照仓库承担，镜像是携凭据的补充消费通道；注册表对历史时间戳构建无自动清理记载，镜像侧随重发单调累积，项目方 MUST NOT 对外承诺回收，如需清理由运维按发布流程文档成文的包版本删除手段处置。快照镜像的来源为持续集成定时与发布者本机凭据在位时的发布两类，两来源并存重发均为常态新鲜度维护；快照镜像运行 MUST NOT 减免发布门禁。

本需求前身"快照构件不进入镜像通道"的排除依据句（注册表不生成含快照时间戳块的元数据、不提供目录列举、消费方按快照坐标解析必然失败、上传产物是不可被任何构建工具发现的孤儿文件）系失实陈述，随 2026-10-05 开放快照的改写删除：首轮沙箱实测只检查了构件级元数据而漏检版本目录级元数据，得出错误结论（记录见归档目录 `2026-10-05-add-github-packages-channel` 的 `verification/sandbox-probe.md` 结论 2，已被复测勘误）；复测以真实 Gradle 与 Maven 消费端证明注册表服务端会自动为 Gradle 上传的快照维护含时间戳与构建号的目录级元数据，消费端可解析同一快照坐标并随重发滚动到最新构建（取证 S1 至 S8，记录见归档目录 `2026-10-06-probe-github-packages-snapshot-support` 的 `verification/snapshot-spike.md` 现文）。用户先于 2026-10-05 裁决开放发布快照（持续集成单来源形态），又于 2026-10-06 复裁加入本机来源并改回凭据对形态，本条为该两次裁决后的现行契约。

#### Scenario: 开发线快照经重发在镜像滚动到最新构建
- **WHEN** 开发线已先后两次把快照构建镜像发布至 GitHub Packages（任一来源），第三次快照发布完成后，消费方携有效 classic 令牌按坐标 `<主>.<次>.x-SNAPSHOT` 解析并强制刷新依赖缓存
- **THEN** 解析取得的构件属于第三次构建（其文件名时间戳与构建号为该坐标当前最新），前两次构建按各自时间戳标识仍可取回，无需消费方更换坐标字面量

#### Scenario: 未配置镜像凭据对的本机快照发布不扇出镜像
- **WHEN** 开发者在未成对配置镜像凭据的本机开发线分支执行 `./gradlew publish`
- **THEN** 任务图中不存在任何指向 GitHub Packages 的发布任务，快照构件只进入内网快照仓库与（Central 凭据在位时的）Central 快照仓库，本机行为与凭据对在位配置前逐任务一致，配置阶段不因缺失凭据报错

#### Scenario: 快照镜像失败不阻断后续补齐
- **WHEN** 某次快照镜像（任一来源）失败导致镜像缺失该构建，随后一次快照镜像成功
- **THEN** 镜像该快照坐标解析结果为最新成功构建，缺失的历史构建无需人工补发即被滚动超越；消费方不因该次缺失取到错误坐标——快照坐标解析永远返回该仓库当前最新时间戳构建

#### Scenario: 发布分支形态不得执行快照镜像
- **WHEN** 在发布分支形态（版本为裸号）的执行环境中请求把快照形态构件发布到镜像目的地
- **THEN** 该请求被发布门禁的分支形态与版本形态一致性断言拒绝，镜像中不出现与发布分支形态错配的快照构件（快照坐标只出自开发线形态，与 release-versioning 需求"快照坐标形态跨发布期保持稳定"一致）
