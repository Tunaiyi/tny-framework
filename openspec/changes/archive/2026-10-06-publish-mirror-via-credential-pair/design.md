# Design

## Context

动机与复裁沿革见 proposal.md - Why。现状约束：镜像落地不足一日（2026-10-05 至 2026-10-06），`GITHUB_PACKAGES_KEY` 单键仅存在于两处 CI env 注入、插件守卫与账本条文，无外部配置方；发布者本机 `~/.gradle/gradle.properties` 已持有初版双属性两行（现为死配置）；正式版与快照的发布资格甄别已由 `tny.publish` 门禁全量承担（守卫自 open 变更起不再看版本形态）；"同号一次成型与 409 判读"契约已成文且覆盖持续集成重跑场景。

## Goals / Non-Goals

**Goals:**

- 凭据配置面回到用户名与令牌两属性（与发布者本机既有配置对齐），半配置防线恢复。
- 本机成为镜像的合法第二来源：开发线 publish 即扇出镜像快照；正式版本机先发与 CI 步骤的冲突由既有 409 判读承接。
- 账本三条需求按新契约成对改题，场景名不再残留"凭据密钥/仅持续集成"字样。

**Non-Goals:**

- 不为单密钥形态保留兼容读取层（存在时间不足一日且无外部使用方，双轨命名徒增认知负担）。
- 不引入本机与持续集成的来源互斥锁、时间窗或额外开关属性（冲突面已被既有判读机制与时间戳文件名语义覆盖）。
- 不改门禁条文、正式版发布流程推荐顺序（推荐仍为持续集成统一发正式版，写入文档而非机制）。

## Decisions

### D1 三条需求全部成对改题（含本可留标题的第三条）

**决定**：差量对守卫声明、CI 执行、快照滚动三条需求均以 REMOVED+ADDED 成对表达；"同号一次成型"与"构件边界"两条不动。

**依据**：三条的标题或场景名内嵌被推翻字样（"凭据密钥""由持续集成独立执行""凭据密钥…不扇出"），而严格校验裁定 MODIFIED 整块替换不得更名或删除既有场景——align 变更刚踩过同一约束。成对改题后场景名得以按新语义重命名。

**被否决的备选**：第三条保标题走 MODIFIED、场景名"未配置镜像凭据密钥的本机快照发布不扇出镜像"原样保留。否决理由：场景名残留"密钥"字样即本次要消灭的失真本身。

### D2 无双键兼容层，一次性切换

**决定**：删除 `GITHUB_PACKAGES_KEY` 读取路径，不保留"任一形态在位即声明"的兼容判定。

**依据**：单键形态从插件落地到本变更不足一日，注入方仅本仓两个工作流（同批切换），账本与文档同批换版——兼容层的受益方不存在，留下反而使守卫谓词多一条永不消失的枝。

**被否决的备选**：双属性或单键任一满足即声明。否决理由：两条命名体系并存，未来删除任何一条都要再走一次变更，等于把今天的改名推迟成两次。

### D3 正式版本机双发的处置复用 409 判读，不加互斥机制

**决定**：本机持凭据对在发布分支执行 `publish` 属合法行为（标签存证门禁照常把关）；若因此使持续集成 `publish.yml` 第三步骤收到 409，按既有需求"同号正式版构件一次成型且重复上传可判读"判读为存证、忽略该步骤失败。文档在触发形态段与正式版发布建议中写明"正式版本发布推荐由发布者单机或持续集成其一统一执行"。

**依据**：判读阶梯、只读核对与"重跑 409 属已存在"语义全部已成文且经生产复现（open 变更 task 5.2 实证），本机先发的冲突面恰好落在既有义务覆盖内——新增互斥锁是为一次性低概率事件造永久机制。

**被否决的备选**：其一，正式版目的地仅在检测到 CI 环境变量时声明。否决理由：给守卫引入运行环境嗅探枝（providers 读 CI 变量），违反声明式配置直觉且 CI 环境标记不可靠。其二，本机仅允许扇出快照（守卫看版本形态）。否决理由：版本子句刚从守卫删除（甄别职责在门禁），为限制本机来源把它加回来等于撤销门禁与守卫的职责划分。

### D4 守卫恢复双属性双判的半配置防线

**决定**：守卫条件为 `hasProperty('githubPackagesUsername') && hasProperty('githubPackagesToken')`，与 credentials 取值键一致；缺任一即不声明且配置期不报错。

**依据**：初版对抗验证定级的 blocker——断言与取值必须同键集，半配置机器在每次 Gradle 调用配置期报红的事故已证；本次恢复该防线是双属性形态的必然配套。

### D5 本机快照扇出与每日定时共存无需协调

**决定**：接受两来源对同一快照坐标的并存重发；不引入错峰、开关或补跑判重。

**依据**：各构建时间戳文件名互异（复测 S2、S6 与本机三连发实证），服务端元数据自动推进；并发窗口（夜间定时 vs 白天人工发布）下目录级元数据一致性未实测——发布登记为风险与首观察项，若并发异常再立维护变更，不预支机制。

### D6 关联变更的边界句同步

**决定**：在途 align 变更差量中"镜像快照参与方式"句（"本机不持凭据、不随本机 publish 扇出"）随本变更规划同步改写为双来源表述；两变更对 `github-packages-mirror` 无交集（align 只动 central-publishing），归档顺序无依赖。

**依据**：align 差量引用镜像契约句若不同步，其归档入账即制造账本自相矛盾——正是本话题线反复消灭的账目错位形态。

### 适用范围声明

原则卷 P 编号针对 Java 结构（P5 归一在此的对应物是"单一事实源不双轨"，已在 D2 依据中引用其思路）；本变更零 Java 代码，codegraph 无符号可分析，影响面即 proposal.md - Impact 清单。

## Risks / Trade-offs

- [本机正式版先发导致持续集成步骤 409 红] → 既有判读义务与文档阶梯覆盖；文档推荐句降低发生率；发布监控观察首季。
- [令牌写入本机用户级文件的凭据面扩大] → 用户级文件在仓库之外、不入库不变（门禁断言与文档重申"禁止提交"）；提醒发布者使用可撤销的 classic PAT 并按仓库最小 scope。
- [两来源并发写同坐标目录级元数据未实测] → 首观察项（本机扇出首发后与首个定时周期交叉时只读核对元数据 buildNumber 单调性），异常另立维护变更。
- [第三次凭据命名改动的账本抖动] → 三条成对差量集中一次完成，历史沿革句保留在快照需求内，归档记录可溯。

## Migration Plan

插件守卫与注释 → 两工作流 env（一换二）→ 文档三处（触发形态、本机配置反转、tny.release 注释）→ README 与 config.yaml 复核 → 本地回归（半配置不声明、双配置开发线出现、发布形态出现、dry-run 门禁前置）→ 经用户批准的本机首发验证（真实扇出，验证与内网/Central 三通道共存与元数据推进）→ validate。

**回滚**：revert 本变更提交即回到单密钥形态；本机扇出的构件无需回收（快照滚动语义下旧构建自然被超越）。

## Open Questions

- 正式版发布是否未来收紧为"仅持续集成"的机制强制（当前为文档推荐），观察本机来源使用频率后裁决。
