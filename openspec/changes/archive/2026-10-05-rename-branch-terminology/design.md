# Design

## Context

术语现状三套并存：规格账本用"开发线分支/发布分支"（`release-versioning` 第一、二、七条
原文）；`docs/release-process.md` 与脚本文案用改造期间引入的"冻结线/发布容器"；
`docs/branch-model.html`（未跟踪）已按用户拍板的新口径"版本开发分支/版本发布分支"撰写。
本册把后两者收敛到拍板口径。grep 基线：`docs/` 19 处、命令文件 10 处、发布插件 22 处，
零散注释若干；`openspec/changes/archive/` 命中不算残留。

## Goals / Non-Goals

**Goals:** 一个概念一个词，全仓现行文本（文档、命令、脚本文案）与拍板口径一致；HTML 页入库。
**Non-Goals:** 不改规格账本条文用语；不回改归档卷宗；不动任务名、参数名、判定逻辑。

## Decisions

**D1：拍板口径为终态术语，规格条文不随之改写。**
理由：规格是行为契约账本，其"开发线分支/发布分支"用词语义无歧义，为措辞开 MODIFIED 差量
违背"规格只记可观察行为"的记账原则；采用"文档新词＋首次出现处对照规格原词"的映射方式
（例："版本开发分支（规格条文中称开发线分支）"）。依据 P12（行为未变故不动账本）、
P13（映射写进文档即机器可 grep 验证）。被否决备选：把规格条文同步改词——为措辞制造
一次伪需求差量，否决；保留"冻结线/容器"仅在文档中另立术语表——双词并存正是本次要消灭
的状态，否决。

**D2：脚本文案随文档同步改词，改后文案逐字评审。**
可观察文本变更单独立册即为本册存在的理由。规则：报错与计划文案仅替换名词（"容器"改
"版本发布分支"、"发布容器"同），句式、判定点、顺序不动；英文 description 中 container
branch 改 release branch，任务名参数名零改动。验收用 dryRun 输出前后对照（除名词外逐行
一致）。依据 P6（对外说过的话要与名字一致）；被否决备选：只改文档、脚本文案留旧词并加
"脚本文案的容器即版本发布分支"注记——把双词并存写进制度，否决。

**D3：工位命名模板入文档两处即可，不做工具校验。**
`feat/<主>.<次>.x-<名>` 与 `fix/<主>.<次>.<补丁>-<名>` 以文档示例形态固化（流程一、
流程三），不加任务名校验或 CI 检查——工位命名属自由区纪律，工具强制违反
`gradle-build-style` 的克制精神也无治理收益。依据 P10（无治理需求不建机制）。
被否决备选：门禁拒绝不合名分支——门禁只管发布形态分支，扩大它管不了也管不着的辖区，否决。

**D4：`docs/branch-model.html` 随本册提交入库。**
页面内容已是新口径；若脱离本册单独提交，会造成"文档改词前 HTML 已用新词"的中间态窗口，
并入本册原子收口。被否决备选：留在工作区等下次——未跟踪文件是丢失源（本会话已验证
/tmp 现场会漂移），否决。

## Risks / Trade-offs

- [grep 替换误伤"容器"在非分支语义处（如 Docker 容器）] → 替换只认"发布容器/容器分支/
  冻结线"词组白名单，逐文件人工过目，禁全词盲替换；CI/测试文档中的 container 字样属
  他义，验收含 `grep -n 容器 docs/*.md` 应只剩他义命中或零。
- [文案变化打断依赖旧报错字段的既有习惯（命令文档示例、人工肌肉记忆）] → 命令文件同册
  同步；报错语义句只换名词。
- [规格与文档用词分叉留存] → 由 D1 的映射行收敛，属有意为之的最小代价。

## Migration Plan

单提交（或文档/脚本两提交）落地；revert 即回旧词，无数据迁移。归档卷宗不回改。
