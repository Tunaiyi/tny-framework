# Design

## Context

动机见 proposal.md - Why。现状事实：`tny.subprojects-baseline.gradle` 第 38-39 行是全仓唯一一处 `tny.catalog.CatalogCoord.coord(...)` 调用（循环内按名字取"组:名:版本"字符串）；该插件脚本自 2026-10-03 起可用官方版本目录访问器（`libs.xxx` 形式，IDE 有补全）；`io.spring.dependency-management` 插件的集中声明接口只接受字符串（2026-10-03 的验证试验证实：直接传依赖对象会报"找不到匹配的方法"）。

爆炸半径核查（按设计规则以 codegraph 分析并如实记录）：`.gradle`/`.groovy` 构建代码不在 Java 符号图内，无适用符号节点；本变更亦不触碰任何 Java 源码。真实消费面经引用扫描确定为一处调用点；删除对象类无其他引用者。

两卷方法论检索（M1 条款要求）：模式卷决策表面向运行时对象模式，无构建脚本行；本案对应的是原则卷 P5（同一份事实只保留一种读取实现）与 P10（自写解析当初是"拿不到官方能力"的一次性绕行，绕行前提消失后抽象即成负债）。框架内先例：目录读取一律走官方访问器（java-module、integration-test 已是该形态），本变更把最后一个例外也归入先例，不构成另起炉灶。

## Goals / Non-Goals

**Goals:**

- 版本目录的读取通道在 buildSrc 内归一为官方访问器一种；删除自写 TOML 解析代码。
- 行为零差异：集中声明的每个"坐标+版本"串逐字节不变。

**Non-Goals:**

- 不改列表循环的形态（condense-managed-coordinates 刚收敛的写法保持）。
- 不动版本目录文件、settings.gradle 的目录注册、依赖管理插件本身。
- 不顺手处理集中声明之外的事项（即使出现别的 coord 相似调用点也不扩面，先报告）。

## Decisions

**D1 按名字动态取官方访问器，实施阶段先做一步小验证再全量替换。** 循环里的别名是字符串（`'commonsIo'` 等 20 个），官方访问器是编译期生成的属性（`libs.commonsIo`）。Groovy 的动态属性写法 `libs."$alias"` 在生成的访问器对象上应当能命中对应 getter，但这是待验证假设：实施第一步先只对 `commonsIo` 一项改走该写法并解析比对（备份-恢复纪律），确认成立再替换整个列表；若不成立，回退形态为 20 行显式 `libs.xxx` 逐条声明（放弃循环内动态取名，保留删解析类的目标）。依据：P13——假设带验证路径与回退形态，不赌。被否决备选：保留自写解析直到官方支持动态取名——否决：官方本就提供按别名取值的公开接口（`VersionCatalog.findDependency(alias)`，与动态属性取生成访问器二选一，实施第一步一并验证），无需等。

**D2 字符串按公开属性逐段拼接，不依赖对象的 toString。** 辅助方法取到依赖信息对象后，用其公开属性逐段拼 `"${group}:${name}:${version}"`；不使用"整个对象转字符串碰运气等于目标格式"的写法——2026-10-03 的验证试验里错误信息恰好显示过 `commons-io:commons-io:2.8.0` 形态，但错误信息的渲染格式不是受支持的公开承诺，随 Gradle 版本可变。逐段拼接用的是版本目录访问器文档化的公开属性。依据：P4（不建立在未承诺行为上）。被否决备选：`"${对象}"` 直接插值——否决理由同上。

**D3 辅助方法就地放在消费插件脚本内，不新建共享类。** 全仓仅一处消费（proposal 已核），一个三行本地方法足够；为其新建类文件等于复制我们正要消除的"专用小机制"模式。若未来第二处需要（目前看不到），届时按三次法则提取。依据：P10。被否决备选：把 CatalogCoord 改造成访问器包装类保留——否决：单点消费下是空转抽象。

**D4 版本为空串的条目不兜底。** 集中声明列表的 20 个条目在目录里全部带版本（逐条核过），"版本为空"不属于本列表的可达状态；若未来有人往列表加了无版本条目，得到的字符串会以冒号结尾、被依赖管理接口拒绝——这比静默无版本更可诊断，不加特判。依据：需求六"错误要报得出来"的构建域同类精神。

## Risks / Trade-offs

- 【动态属性取名在生成访问器上失败】→ D1 已内置先验证后替换与回退形态，风险不扩散。
- 【toString 假设被误用】→ D2 明确排除。
- 【逐段拼接与旧解析器在某条目格式上结果不一致（例如带分类器的 netty 分类件）】→ 分类件条目不在本列表内（列表只含集中声明的 20 项，分类件由模块直接以访问器声明）；四报表比对覆盖全部 20 项的最终效果。
- 【删除类后 buildSrc 残留空目录 tny/catalog】→ 一并移出（不留空壳），沿用隔离目录做法。

## Migration Plan

单批次：D1 验证（单项改、解析比对、恢复现场）→ 全量替换辅助方法 + 删类 → 验收（四模块依赖解析报告、两份 POM、构件清单对基线零差异；全量构建；`grep` 确认无 CatalogCoord 残留引用）。回滚即恢复两文件。

## 实施修正注记

- D1 与 Migration Plan 描述的"列表加循环、按名字动态取名"形态，实施后被用户两次定稿取代为 20 项显式逐条书写（`dependency dependencyNotation(libs.<别名>)`）；辅助方法名经选项对齐最终定为 `dependencyNotation`（notation 是 Gradle 官方文档对"组:名:版本"这种声明形式的称谓）。复验结论不变：四报表、两份 POM 零差异。过程记录见 verification-notes.md 相应两节。
