# Spec Delta

## Purpose

定义 TnyFramework 向 GitHub Packages 的 Apache Maven 注册表镜像发布构件的行为契约：镜像目的地按版本形态与凭据守卫的声明规则与未配置机器的行为不变式、正式版本镜像的持续集成独立执行与发布门禁全量继承、同号正式版构件的一次成型与重复上传判读、快照构件进入镜像通道的排除边界，以及镜像构件范围与消费方凭据要求。供所有涉及发布通道、制品取用文档的变更引用。

## ADDED Requirements

### Requirement: 镜像通道按版本形态与凭据密钥在位守卫声明且未配置机器行为不变
构建系统在同时满足以下两个条件时，SHALL 为纳入镜像范围的模块把 GitHub Packages 的 Apache Maven 注册表仓库（地址 `https://maven.pkg.github.com/tunaiyi/tny-framework`，URL 的属主段按注册表命名规则全小写）加入发布目的地集合：其一，工程版本为不带任何后缀的裸号正式版本形态；其二，镜像凭据密钥属性 `GITHUB_PACKAGES_KEY` 在位。凭据密钥属性 MUST 只在持续集成执行环境中注入，MUST NOT 写入仓库内任何文件；Basic 认证的用户名由构建系统以该仓库属主对应的 GitHub 账户名填充（发布身份本就是该账户，配置方无需提供用户名）。两个条件任一不满足时，该目的地与其全部发布任务 MUST NOT 出现，其余构建与发布命令的行为 MUST 与本变更实施前逐任务一致，配置阶段 MUST NOT 因缺失凭据报错。

#### Scenario: 未配置镜像凭据密钥的开发机行为不变
- **WHEN** 一位未在持续集成环境注入镜像凭据密钥的开发者在本机执行任意构建与 `./gradlew publish`
- **THEN** 任务图中不存在任何指向 GitHub Packages 的发布任务，发布产物与失败行为和本变更实施前逐任务一致，不出现任何与镜像凭据相关的报错

#### Scenario: 正式版形态且凭据密钥在位时目的地被声明
- **WHEN** 构建环境注入镜像凭据密钥属性，并在发布分支形态（版本为裸号）上执行构建
- **THEN** GitHub Packages 进入发布目的地集合，逐仓镜像发布任务可用；未注入凭据密钥时该目的地不被声明且配置阶段不报错

### Requirement: 正式版本镜像由持续集成独立执行并全量继承发布门禁
裸号正式版本构件 SHALL 由 GitHub Actions 工作流中的独立步骤镜像至 GitHub Packages；该步骤与既有内网仓库步骤、Maven Central 步骤相互独立——一个通道失败 MUST NOT 撤回或污染已成功通道的已发布内容，一个通道重试 MUST NOT 重推已成功通道。镜像发布任务 MUST NOT 减免发布门禁的任何一项：四项发布凭据属性断言、分支形态白名单、版本形态与仓库路由一致性、同号历史黑名单、发布标签远端存证核对、发布依赖形态核对在镜像任务上照常先行执行。

#### Scenario: 镜像步骤失败不累及其他通道
- **WHEN** 一次正式版发布中内网仓库与 Central 步骤先成功，随后镜像步骤因网络故障失败
- **THEN** 内网与 Central 的构件保持已发布状态，构建报告独立呈现镜像通道的失败与原因，处置者可以只重试镜像步骤而不重跑其余通道

#### Scenario: 缺发布标签存证的正式版镜像被拒绝
- **WHEN** 远端不存在附注标签 `v<版本>` 时执行正式版本的逐仓镜像发布任务
- **THEN** 镜像被一致性门禁以标签存证缺失拒绝，GitHub Packages 上不会出现该版本的任何构件，发布纪律不因新通道出现旁路

### Requirement: 同号正式版构件一次成型且重复上传可判读
GitHub Packages 对已存在的构件文件拒绝覆盖上传（重复上传同名文件返回 HTTP 409；该行为官方文档未记载，多个项目的实测一致）。进入镜像的正式版本构件 SHALL 视为一次成型：对同一版本重跑镜像 MUST NOT 作为常态的新鲜度维护手段；操作者与持续集成在收到重复上传拒绝时，MUST 能够把它判读为"构件已在镜像中"的存证而非新故障，判读方法 MUST 在发布流程文档中成文；需要修正已镜像正式版构件时 MUST 优先采取提高补丁号重新发布并走完整发布流程的路线，而不是删除版本重发。

#### Scenario: 重跑已镜像版本的工作流按存证判读
- **WHEN** 对一次已镜像成功的发布，人工重新触发同一发布分支的工作流
- **THEN** 镜像步骤对已上传构件收到重复上传拒绝而失败，其余通道不受影响；错误输出与发布流程文档共同指向"构件已存在"的判读方法与只读核对版本清单的步骤，处置者不会误入删版本重发的默认补救

#### Scenario: 修正正式版缺陷走升号路线
- **WHEN** 发现已镜像的正式版本构件存在缺陷，需要发布修正
- **THEN** 按既有流程切出新的补丁号发布分支并完整发布，新版本构件进入包括镜像在内的全部通道，镜像中旧版本构件保持原样不删除

### Requirement: 快照构件不进入镜像通道
快照形态的构件 MUST NOT 进入 GitHub Packages 镜像通道——沙箱实测证明（2026-10-05，记录见本变更目录 `verification/sandbox-probe.md`）：Gradle 发布机制上传的快照文件在注册表中以带时间戳的文件名存储，注册表不生成含快照时间戳块的元数据，也不提供目录列举，消费方按快照坐标解析必然失败，上传产物是不可被任何构建工具发现的孤儿文件。快照的历史可追溯与滚动分发继续由内网快照仓库与 Maven Central 快照仓库承担，镜像目的地按版本形态守卫从声明层面排除快照。

#### Scenario: 开发线即便凭据在位也不声明镜像目的地
- **WHEN** 在开发线分支形态（版本为 `<主>.<次>.x-SNAPSHOT`）构建，且构建环境注入了镜像凭据密钥属性
- **THEN** GitHub Packages 目的地不被声明，任务图中不存在任何指向镜像的发布任务，快照构件不会进入注册表

#### Scenario: 镜像仓库中不出现快照形态版本
- **WHEN** 本变更实施后的任意时刻检视镜像仓库中任一构件的版本清单
- **THEN** 清单中只存在裸号正式版本，不存在任何以 `-SNAPSHOT` 结尾的版本条目

### Requirement: 镜像构件边界与消费方凭据要求
镜像通道 SHALL 收录 java 线全部发布模块与平台约束模块的发布构件，其坐标与附属构件清单与内网仓库通道逐件一致；Gradle 插件模块的构件 MUST NOT 收录（其插件标记构件的构件名含点号，官方 Maven 注册表的构件命名条文只列举小写字母、数字与连字符，点号形态的可接受性未经验证）。镜像仓库的消费方下载 MUST 携带 GitHub 访问凭据——GitHub Packages 对公开包同样不开放匿名解析；接入文档 MUST 写明该事实、所需凭据类型（personal access token 的 classic 形态，fine-grained 形态截至 2026-10-05 不能访问 Packages）与所需权限；免凭据的公开分发通道仍由 Maven Central 承担。

#### Scenario: java 线与平台约束构件跨仓一致可解析
- **WHEN** 一次正式版发布镜像成功后，消费方配置镜像仓库地址并携带有效 classic 令牌凭据解析任一发布模块与平台约束模块
- **THEN** 取得的 POM、jar 及附属构件与内网仓库同版本构件逐件等价，平台约束可正常导入

#### Scenario: 匿名解析被拒绝且指路可达
- **WHEN** 消费方声明了镜像仓库地址但未配置任何凭据执行依赖解析
- **THEN** 解析因认证被拒而失败，错误与接入文档共同指向凭据创建与配置路径，该现象在文档中作为注册表规则成文而非事故
