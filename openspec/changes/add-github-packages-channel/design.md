# Design

## Context

发布链路的现状与约束（完整事实清单与出处见仓库根目录 `PLAN-发布构件到GitHub-Packages-2026-10-05.md` 第二、七节，本文不重复其逐条引用）：

- 构建侧：`tny.publications` 约定插件负责 POM 元数据、GPG 签名与发布目标仓声明（内网 Nexus 仓按版本后缀三目路由；centralSnapshots 仓按"快照且 Central 凭据在位"条件守卫声明）；`tny.publish` 约定插件承担双层拦截——四项 Nexus 属性非空断言加 `checkPublishPrerequisites`（全量 check 与五项一致性核对），其共享仓谓词按任务名匹配（`publish` 开头且非 `ToMavenLocal` 结尾即命中）。发布构件形态：java 线模块为主 jar、sources jar、javadoc jar、POM、Gradle 模块元数据 `.module`、逐构件 `.asc` 签名（仅发布分支形态必签）；BOM 为 POM 加元数据加签名；组号单一事实源 `com.tnydev.game`。
- 规格侧：`gradle-build-style` 十一项需求约束全部 `.gradle` 书写形态（配置期声明式；程序性行为只进任务动作块或约定插件；条件声明的合规先例即 centralSnapshots 的守卫形态）；`release-versioning` 以泛称"与版本形态匹配的目标仓库"表述路由约束，不钉死目的地清单。
- 注册表侧的三项原先无记载行为已全部经沙箱实测裁决（2026-10-05，记录见本变更目录 `verification/sandbox-probe.md` 与 `verification/logs/`）：快照重复上传统一被接受（Gradle 实际使用带时间戳的文件名，每次构建都是新文件名），但快照对消费方不可解析（字面名文件不存在、元数据无快照时间戳块、注册表无目录列举端点）；正式版同号重传返回 HTTP 409；删除版本经 GraphQL 全局节点 ID 对内置 `GITHUB_TOKEN` 与含 repo scope 的 classic PAT 两条路都可行，删除后同号可立即重传。
- 爆炸半径核对：codegraph 对根 `build.gradle` 改动落点（java 线装配线块）的变更影响分析返回直接冲击零个图符号、风险等级低——本变更不触碰任何 Java 符号，构建脚本改动的影响面表现为发布任务名与门禁谓词命中关系，该推演已由对抗验证逐条完成（本文 D4 引用其结论）。
- 环境侧已核实：仓库公开、默认分支 main、账户名下无生产坐标占号包（立项时核实为空；沙箱探针包已随任务 5.4 删仓连带清理并于 2026-10-05 复查为空）、Actions 已启用且允许全部动作、操作者 classic PAT 已含 `write:packages`。

用户拍板的决定（不再重新论证，只论设计与机制）：镜像一律由 CI 执行；包挂 `Tunaiyi/tny-framework`；CI 凭据用内置 `GITHUB_TOKEN`；Gradle 插件模块首批排除。最初拍板"快照与正式版都进镜像、快照由人工 workflow_dispatch 触发"，经沙箱实测证明快照在注册表中无法被消费方解析后，用户于 2026-10-05 复裁撤回该决定：**快照不进镜像**（D2）。同日追加拍板：镜像凭据属性由双属性改为单一密钥属性 `GITHUB_PACKAGES_KEY`（D3、D6）。

## Goals / Non-Goals

**Goals:**

- 在不改动任何既有门禁文件的前提下，让 GitHub Packages 成为第三个发布目的地，且新通道任务自动继承双层拦截与五重门禁。
- 让"未配置镜像凭据的机器行为与本变更前逐任务一致"成为可机器验证的不变式（守卫声明形态，而非运行时分支）。
- 把快照能否进镜像交由沙箱实测先行裁决（实测置于实施序列最前）：实测证明快照不可被消费方解析，据此将其排除出镜像通道（D2），防止设计带病落地。
- 把重复上传拒绝（HTTP 409）的判读与处置成文进发布流程文档，使镜像通道对既有发布纪律（标签存证、升号路线）零旁路、零稀释。

**Non-Goals:**

- 不改变门禁语义：四项属性断言不按目标仓归属拆分（镜像任务继续为 Nexus 属性付断言代价），拆分属门禁设计变更，另行立项。
- 镜像通道不收快照构件（实测排除，见 D2）；快照的历史可追溯与滚动分发仍由内网快照仓与 Maven Central 快照仓承担。
- 不将 Gradle 插件模块纳入首批镜像，也不在本册内裁决其未来纳入（含点号构件接受性数据已在沙箱采集，裁决留给后续变更）。
- 不引入新的发布触发哲学：正式版镜像仍由 release.published 与指定发布分支的人工 workflow_dispatch 触发，不设 push 自动通道。

## Decisions

### D1 承载形态：新建独立约定插件 `tny.github-packages.gradle`

**决定**：镜像通道的仓库声明收在 buildSrc 新建的约定插件文件内，java 线经根 `build.gradle` 装配线加一行 `apply plugin: 'tny.github-packages'` 引入，BOM 经自身 plugins 块加一行 `id 'tny.github-packages'` 引入。

**依据**：`gradle-build-style` 需求一"多个装配线共用的同一段配置 MUST 收编为可共享的约定插件"；形态即仓库既有的"一个关注点一个插件"先例（`tny.publications`、`tny.central`、`tny.release` 各司一职），符合 P5 单一职责——通道集合因"新增目的地"这一原因变化时只改这一个文件；P3 开闭原则——未来插件线纳入或目的地调整只需增删引入行，不改插件本体。

**被否决的备选**：其一，直接写在 `tny.publications.gradle` 的 repositories 块内。否决理由：该插件的职责文本是"发布元数据与签名"，把第三个通道塞入使同一文件承担两个变更原因（P5），且触碰既有文件将把 centralSnapshots 区域拉入"触碰即改"评估区，扩大回归面。其二，在根 `build.gradle` 以 `configure(javaProjects + bomProjects)` 逐仓声明。否决理由：根脚本按需求一要求保持装配线纯声明，仓库配置细节属约定插件领地；且根脚本现值 65 行逼近八十行界线。

### D2 快照通道取舍：实测裁决为排除（原拍板撤回）

**决定**：快照构件不进入 GitHub Packages 镜像通道，守卫按版本形态从声明层面排除快照。

**实测依据（2026-10-05，`verification/sandbox-probe.md`）**：最初的拍板决定是快照与正式版都进镜像、以人工触发维持新鲜。沙箱实测给出决定性事实：其一，Gradle 8.14.5 上传 `-SNAPSHOT` 构件实际使用带时间戳的唯一文件名（如 `gpr-sandbox-0.0.1-20261005.042623-2-javadoc.jar`），每次构建文件名不同，注册表一律接受同一快照版本的再次上传（调研期"同名文件二次上传必 409"的推断被修正为"文件名不冲突故可上传"）；其二，消费侧完全不可用——注册表不生成含 `<snapshot>` 时间戳块的元数据，字面名 `-SNAPSHOT.jar`、`.pom`、`.module` 全部 404，且没有任何目录列举端点可让构建工具发现时间戳文件，Maven 与 Gradle 消费方解析快照坐标必然失败，上传只造出不可发现的孤儿文件；其三，删除版本技术上可行（内置令牌与 classic PAT 两条路均实测成功，删除后同号可立即重传），但删除孤儿快照版本属于运维负担而非消费价值。

**裁决**：把快照上传进注册表而没有任何消费者能取用，是给权威账本制造垃圾而不是建通道。用户据此复裁撤回原决定，快照不进镜像；规格需求"快照构件不进入镜像通道"按此书写。

**被否决的备选**：其一，维持快照上传作纯归档形态。否决理由：产物不可解析，归档价值为零，且占用版本号空间。其二，改用 Maven 部署工具链生成 unique 快照。否决理由：为单一镜像通道引入第二套发布工具链，违背全仓 Gradle 一致性原则，官方 Maven 工具在 GitHub Packages 上的快照行为同样无记载，投入无保证。

### D3 守卫形态：版本形态与两凭据属性的三重合取

**决定**：新插件内仓库声明的守卫条件是两条子句的合取：其一，`project.version` 不以 `-SNAPSHOT` 结尾（快照排除，依据 D2 实测裁决）；其二，单一凭据密钥属性 `GITHUB_PACKAGES_KEY` 存在（`project.hasProperty` 判定）。任一子句不满足即整体不声明；Basic 认证的用户名由插件固定填仓库属主账户名 `Tunaiyi`（发布身份与令牌属主恒为同一账户，沙箱实测该形态对内置令牌与 classic 令牌两条路均上传成功），配置方只提供密钥一个值。（2026-10-05 命名修订：初版为 `githubPackagesUsername` 与 `githubPackagesToken` 双属性成对守卫，经用户复裁改为单密钥形态，半配置窗口自此不存在。）

**依据**：守卫手法与 `tny.publications` 第 76 行 centralSnapshots 先例同源（"布尔条件守卫单条声明语句"是 `gradle-build-style` 需求一明列的合规条件化形态；先例只收快照、本仓只收正式版，覆盖面互补）；守卫断言与取值必须指向同一个键，因为 credentials 闭包内的 `providers.gradleProperty(...).get()` 在配置期求值，断言与取值不一致的形态会让半配置机器在每一次 Gradle 调用（包括 `./gradlew help`）的配置期抛 MissingValueException——这是对抗验证定级的 blocker 级事故；初版用双属性双判根除，单密钥形态下断言与取值同键，事故窗口从结构上消失。开发线上版本子句先行生效：即便误配凭据，快照形态也不会声明镜像目的地。

**被否决的备选**：其一，撤掉版本子句、形态选择全交给 CI 步骤编排。否决理由：D2 裁决快照不进镜像后，版本子句是契约（规格需求"快照构件不进入镜像通道"场景一）的直接落实，缺它则本机误配凭据叠加异常版本形态仍可能把快照送进注册表。其二，保留用户名与令牌两个属性。否决理由：用户 2026-10-05 复裁认为配置面应只有一个秘密值；发布身份恒为本仓属主账户，用户名没有独立信息量，双属性反而引入"两个键要记住配对"的负担——沙箱实测确认固定用户名形态可用后，该备选失去唯一保留理由（用户名可自由填写的场景在改挂其他仓库时才成立，那属 D7 所述另一设计决策）。

### D4 门禁继承：零改动，靠任务名自动命中

**决定**：`tny.publish.gradle` 与 `tny.publications.gradle` 一个字符不动。新仓名 `githubPackages` 派生的逐仓任务（`publishMavenJavaPublicationToGithubPackagesRepository` 与 `publishAllPublicationsToGithubPackagesRepository`）按名字规则命中共享仓谓词的通配分支（`publish` 开头且非 `ToMavenLocal` 结尾），自动挂载四项属性断言与 `checkPublishPrerequisites`；`tasks.matching` 是活视图，后加入的任务无需门禁文件感知。仓库路由核对（`validateRepositoryRouting`）对新 URL 的推演结果：URL 不含 `releases`、`-release/`、`snapshots` 任何关键字，两种分支形态下均放行。

**依据**：模式卷 M1 先例优先——发布资格治理已有完整机制（双层拦截），新通道作为其管辖对象接入，而不是另起一套镜像专用校验。镜像必须为 Nexus 属性断言付费（CI 镜像步骤因此注入 `ORG_GRADLE_PROJECT_NEXUS_*`），这是"不拆分断言"（Non-Goals 第一条）的明示代价。

**被否决的备选**：为新通道在门禁谓词里加豁免名单。否决理由：豁免等于旁路，规格需求"全量继承发布门禁"明令禁止；且门禁文件本身已达长度界线，能不动就不动。

### D5 CI 步骤拓扑：追加一个独立步骤，任务名取逐仓聚合形态

**决定**：`publish.yml` 现有 Nexus、Central 两个步骤保持原样（不注入镜像凭据，故聚合 publish 扇出不含镜像——拍板决定"镜像仅由 CI 执行"的直接落实）；追加第三个步骤"发布正式版本至 GitHub Packages"，调用逐仓聚合任务 `publishAllPublicationsToGithubPackagesRepository` 而不是聚合 `publish`；触发沿用现有事件（release.published 与指定发布分支的人工 workflow_dispatch），workflow_dispatch 输入语义不变。快照形态因 D2 裁决没有对应步骤，工作流不新增分支形态互斥逻辑。

**依据**：通道隔离语义与在途变更 central-publishing 需求"双仓并行发布相互独立"同构（扩写衔接见 D9）：Gradle 单命令首错即停，若镜像与 Nexus 同处一条 `./gradlew publish` 扇出，镜像半途失败会连带撤停同命令中尚未执行的 Nexus 上传；独立步骤 + 逐仓任务名同时消除"重推已成功通道"与"失败传染"两个问题。

**被否决的备选**：其一，扩展第一步的凭据让 `publish` 自动扇出镜像。否决理由：首错即停的失败传染面与重跑重推问题（正式版 409 使重跑必然半红），对抗验证已定级为与隔离条文冲突。其二，拆入新建的独立 workflow 文件。否决理由：镜像步骤要复用的检出、环境、凭据注入骨架与 publish.yml 完全同构，拆两个文件造成流程文档双处维护；同文件第三步让一次发布的全部目的地在同一页可见，符合发布纪律的存证价值。

### D6 凭据注入：环境桥属性，键名无点号

**决定**：镜像步骤经 `ORG_GRADLE_PROJECT_GITHUB_PACKAGES_KEY: ${{ secrets.GITHUB_TOKEN }}` 注入单一凭据密钥（2026-10-05 命名修订后形态；初版为两个属性分别注入用户名与令牌）。属性键名不含点号——Gradle 环境桥拒绝含点属性名经 `ORG_GRADLE_PROJECT_*` 注入，该实测教训已成文于 `tny.publications.gradle` 签名段注记（第 96 至 97 行），本案直接规避。凭据值不进命令行与日志（runner 对 secrets 脱敏，既有手法）。

**依据**：与 Nexus、Central 凭据的注入手法完全一致（模式复用，M1）；大写下划线键名与 `NEXUS_USERNAME`、`RELEASE_REPOSITORY_URL` 既有属性风格对齐。

**被否决的备选**：`GITHUB_ACTOR`/`GITHUB_TOKEN` 环境变量直读（Gradle 官方示例的形态）。否决理由：`System.getenv` 直读违反 `gradle-build-style` 需求二的 providers 惰性读取取向，且与本案既有属性风格分裂；属性形态还天然支持"缺属性不声明"的守卫（环境变量直读做不到声明期条件化）。

### D7 包归属与地址形态

**决定**：地址钉死 `https://maven.pkg.github.com/tunaiyi/tny-framework`，URL 的属主段取全小写（GitHub 账户名 `Tunaiyi` 本身含大写，注册表要求折小写，此为官方《Working with the Gradle registry》页明文；与 POM scm 段页面地址的大小写形态不同属有意为之，两处用途不同）。包挂在源码仓库本体——内置令牌的权限规则（只能发布与运行工作流的仓库相关联的包）使这成为零 secret 路线下的唯一选项。

**被否决的备选**：挂独立构件仓库。否决理由：必须弃用内置令牌、新建对该仓库有写权限的 classic PAT secret 并管理轮换，与拍板决定四冲突；若未来需要（例如源码仓库转私有或改名），改挂与令牌路线绑定为一个后续决策，不在本案预支。

### D8 收录边界：java 线与 BOM 收录，插件模块排除

**决定**：根脚本只对 `configure(javaProjects)` 块加引入行，`gradleProjects` 装配线（即 `tny-game-doc-gradle`）首批不加；BOM 模块经自身 plugins 块加入。

**依据**：插件标记构件的 artifactId 由 Gradle 机制固定生成为含点号形态（如 `com.tny.game.gradle.plugin`），官方构件命名字符集条文只列举小写字母、数字与连字符，点号形态虽经沙箱实测可上传（`verification/sandbox-probe.md` 结论 8），但该模块构件无签名、POM 无元数据组，镜像面貌与主通道不一致，插件 id 坐标体系又独立于主组号。BOM 必须纳入：下游以 import 方式取平台约束依赖的正是这份 POM，镜像缺它则纯 GitHub 生态消费方不可完整用帧。

**被否决的备选**：先纳入插件模块再靠实测撤回。否决理由：撤回窗口内的失败会落在生产命名空间（沙箱实测的结论届时才拿到），顺序倒置。沙箱实测已采集含点号构件数据（接受，结论 8），未来纳入决策的证据已备一份，裁决仍归独立变更。

### D9 立项与账本衔接

**决定**：新能力命名 `github-packages-mirror`，差量全部为 ADDED（不修改主账本任何既有条文）；归档时序钉死为在途变更 `central-publish-tnydev-group` 先归档、本册后归档（proposal.md 已载约束与理由）。本册需求"正式版镜像由持续集成独立执行"与在途增量"双仓并行发布相互独立"的衔接方式：本册不动对方文本；在途变更归档后，其该条需求在主账本的通道枚举（现为 Central 与内网两个）由后续对账动作核对是否需按"各目的地独立"口径扩写，核对结论若需要，落为一个极小的规格维护变更。

**依据**：对尚不存在的账本条目做 MODIFIED 差量会造成归档期基线覆盖，这是 openspec 流程的红线；泛称表述的条文（`release-versioning` 的路由需求）天然容纳新目的地，不动它就是最小的改动面。

**被否决的备选**：把镜像契约并进 central-publishing 能力（作为其增量的增量）。否决理由：该能力现文本只覆盖 Central 语义（准入完整性、命名空间验证），GitHub Packages 镜像的新鲜度、判读、边界问题是另一契约族，混入会让能力语义膨胀；独立能力名也与 `openspec/specs/` 既有的按通道命名风格（`release-versioning`）对齐。

### D10 实测场地：专用沙箱仓库（已完成，2026-10-05）

**决定与执行**：快照重复上传行为、正式版重复上传行为、删除版本的两条凭据途径（内置 `GITHUB_TOKEN` 与 classic PAT）与删后同号重传、含点号构件接受性、元数据与校验和形态，全部在一次性私有沙箱仓库 `Tunaiyi/gpr-sandbox` 内的最小工程实测完成，生产命名空间零测试标签。原始日志存本变更目录 `verification/logs/`。

**依据**：在生产命名空间实测意味着制造需要删除的垃圾包版本，而"删除是否可行、删后能否重发"恰是当时待实测的未知项——用未知手段清理测试痕迹是循环依赖；测试标签还会进入 `git tag` 账本污染发布存证。私有沙箱按官方计费条文在免费额度内（测试构件体量 MB 级以下），沙箱整体由任务 5.4 删除。

**被否决的备选**：直接在生产仓库以 `5.7.99` 之类远端未占号做一次真实试点。否决理由：一次性试点即永久占号（不可覆盖规则的镜像侧体现），且失败清理依赖当时未实测的删除能力；沙箱成本（一个私有空仓库加一个三十行工程）远低于该风险。

## Risks / Trade-offs

- [注册表官方未记载的行为（快照消费形态、删除接口、元数据维护）日后可能变更] → 设计前提全部附 2026-10-05 实测存证（`verification/sandbox-probe.md`）与核实日期；若官方日后支持 Gradle 快照的完整消费形态，重新纳入快照走独立变更裁决；规格文本按行为义务书写，机制变化不碎契约。
- [正式版镜像步骤独立执行一次 Gradle 调用，`checkPublishPrerequisites` 连带全量 check 重跑，发布流水线时长约增一半] → 明示代价换取通道隔离与门禁不旁路（D5）；豁免测试依赖属门禁语义变更，Non-Goals 已排除。若时长不可接受，处置是与断言拆分（Non-Goals 第一条）一并归入未来门禁变更，不在本案夹带。
- [GitHub Packages 的速率限制与单文件大小上限条文未与本仓体量逐项比对（六十余模块全量构件族加校验和的上千次 PUT）] → 任务册未设独立的体量比对步骤，该项已作为遗留观察项登记在 `verification/scenario-coverage.md`（如需上线前预检，取本仓 javadoc 与 fat jar 最大体积对照官方 usage limits 现文属只读动作，可在任务 5.5 首发批准前后顺带执行）；首批全量上传即速率观察点，限流类失败（HTTP 429 或超时）与 409 的判读差异写入文档阶梯，处置是分批补传而非升号。
- [重跑工作流或本机误配凭据后的 409 被误读为新故障] → 规格需求"同号正式版构件一次成型且重复上传可判读"把判读义务落到文档与错误输出双侧；拍板决定零（本机不持凭据）从源头消灭本机扇出与 CI 的重叠双发。
- [快照不进镜像后，纯 GitHub 生态消费方的快照需求无镜像答案] → 文档新节明写"本通道不收快照，快照解析走 Central 快照仓或内网仓"并给出两条消费路径；该边界已写成规格需求"快照构件不进入镜像通道"，属契约而非缺口。
- [正式版构件在镜像中半途失败后，已上传部分不可覆盖] → 实测确证 409 与删除重发两条路（含内置令牌删除成功），处置阶梯成文于 `docs/release-process.md`：只读查存证、升号优先、删后重发为例外路线且需核对下载量删除限制（公共包单版本下载超 5000 次即不可删，官方条文）。
- [组织/账户级 Packages 设置与 workflow 令牌权限基线可能限制 packages: write 生效] → 已核实 Actions 总开关与允许动作为全开；余下"Settings → Actions → General → Workflow permissions"基线一项列为实施前置只读核对任务（gh api 可查 `repos/.../actions/permissions/workflow`），不绿则先改基线再上线步骤。

## Migration Plan

实施顺序（任务册的分组骨架，顺序即依赖）：

1. 沙箱实测与裁决回填（已完成，2026-10-05）：实测记录与原始日志存 `verification/sandbox-probe.md` 与 `verification/logs/`；裁决结论为快照不进镜像（D2），生产仓库在本组零触碰。
2. 构建配置：新建插件文件、根装配线一行、BOM 一行；本机以 dummy 属性注入做声明/不声明与半配置不报红的回归验证（零真实外发）。
3. CI 与文档：publish.yml 权限与正式版镜像步骤、`docs/release-process.md` 新节与两处联动、`README.md` 消费约定第四条与计数词、`openspec/config.yaml` 发布句；工作流文件过静态校验。
4. 只读环境核对：workflow 令牌权限基线经 gh api 确认；命名空间占号复查（立项时核实为空；任务 5.4 沙箱清理完成后复查确认账户级 Maven 包清单为空，2026-10-05；真实首发前后再以只读查询各确认一次）。
5. 真实首发（需用户单独批准）：正式版镜像随下一个自然发布周期在 release.published 触发时首次发生，或经用户批准在发布分支试点逐仓任务。失败即停、绝不自动重跑同号，处置按发布流程文档阶梯执行。

**回滚策略**：构建层回滚是删三行引入（根脚本、BOM、插件文件本体），未声明凭据的机器本无行为差异；CI 层回滚是移除新步骤与 `packages: write` 权限行。已镜像构件无需也无法"退回"（注册表不可覆盖是外部事实），回滚语义仅为"此后不再产生新镜像构件"——镜像定位是尽力副本，权威账本始终在内网仓与 Central，回滚不影响任何既有通道的消费。
