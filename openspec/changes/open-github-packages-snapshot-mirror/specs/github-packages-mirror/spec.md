# Spec Delta

## Purpose

定义 TnyFramework 向 GitHub Packages 的 Apache Maven 注册表镜像发布构件的行为契约：镜像目的地按凭据密钥守卫的声明规则与未配置机器的行为不变式、正式版本与快照构件镜像的持续集成独立执行与发布门禁全量继承、同号正式版构件的一次成型与重复上传判读、快照构件进入镜像通道的准入与随重发滚动契约，以及镜像构件范围与消费方凭据要求。供所有涉及发布通道、制品取用文档的变更引用。

## REMOVED Requirements

### Requirement: 镜像通道按版本形态与凭据密钥在位守卫声明且未配置机器行为不变
**Reason**: 开放快照镜像后，守卫的"工程版本为裸号正式版本形态"排除子句删除，声明条件收敛为凭据密钥单一条件，原标题中的"按版本形态"不再描述正文行为，按标题匹配机制整体改题。
**Migration**: 见本差量 ADDED 条目"镜像通道按凭据密钥在位守卫声明且未配置机器行为不变"，版本形态的发布资格甄别移交发布门禁的分支形态白名单与版本形态一致性断言。

### Requirement: 正式版本镜像由持续集成独立执行并全量继承发布门禁
**Reason**: 义务扩展覆盖快照形态的持续集成执行，标题"正式版本镜像"改题。
**Migration**: 见本差量 ADDED 条目"正式版本与快照镜像由持续集成独立执行并全量继承发布门禁"，原两个场景语义并入新条目并保持。

### Requirement: 快照构件不进入镜像通道
**Reason**: 该需求的排除依据句（注册表不生成含快照时间戳块的元数据、消费方按快照坐标解析必然失败、上传产物为孤儿文件）经复测证伪——首轮实测漏检版本目录级元数据；用户已于 2026-10-05 裁决开放发布快照。复测记录见 openspec change 目录 `probe-github-packages-snapshot-support` 的 `verification/snapshot-spike.md`（取证 S1 至 S8）。
**Migration**: 见本差量 ADDED 条目"快照构件进入镜像通道并随重发滚动到最新构建"，义务由禁止翻转为准入并附滚动与门禁契约。

## ADDED Requirements

### Requirement: 镜像通道按凭据密钥在位守卫声明且未配置机器行为不变
构建系统在镜像凭据密钥属性 `GITHUB_PACKAGES_KEY` 在位时，SHALL 为纳入镜像范围的模块把 GitHub Packages 的 Apache Maven 注册表仓库（地址 `https://maven.pkg.github.com/tunaiyi/tny-framework`，URL 的属主段按注册表命名规则全小写）加入发布目的地集合，工程版本为裸号正式版本形态或开发线快照形态均在声明之列；版本形态的发布资格甄别由发布门禁的分支形态白名单与版本形态一致性断言承担，声明守卫不再参与甄别。凭据密钥属性 MUST 只在持续集成执行环境中注入，MUST NOT 写入仓库内任何文件；Basic 认证的用户名由构建系统以该仓库属主对应的 GitHub 账户名填充（发布身份本就是该账户，配置方无需提供用户名）。凭据密钥不位时，该目的地与其全部发布任务 MUST NOT 出现，其余构建与发布命令的行为 MUST 与快照镜像开放前逐任务一致，配置阶段 MUST NOT 因缺失凭据报错。

#### Scenario: 未配置镜像凭据密钥的开发机行为不变
- **WHEN** 一位未在持续集成环境注入镜像凭据密钥的开发者在本机执行任意构建与 `./gradlew publish`
- **THEN** 任务图中不存在任何指向 GitHub Packages 的发布任务，发布产物与失败行为和快照镜像开放前逐任务一致，不出现任何与镜像凭据相关的报错

#### Scenario: 任一合法发布形态且凭据密钥在位时目的地被声明
- **WHEN** 构建环境注入镜像凭据密钥属性，并在发布分支形态（版本为裸号）或开发线形态（版本为快照）上执行构建
- **THEN** GitHub Packages 进入发布目的地集合，逐仓镜像发布任务可用；未注入凭据密钥时该目的地不被声明且配置阶段不报错

### Requirement: 正式版本与快照镜像由持续集成独立执行并全量继承发布门禁
正式版本形态与开发线快照形态的构件镜像 SHALL 均由 GitHub Actions 工作流中的独立步骤执行，两种形态的触发形态在发布流程文档成文（正式版本：release 事件与指定发布分支的人工触发；快照：定时计划每日执行当前开发线一次，选线以线谱系登记的状态为唯一依据，维护态与退役线不在定时范围、仅经人工指定线名的补跑触发）；无论选定何种触发形态，新构建进入镜像的唯一来源 MUST 是持续集成运行，发布者本机 MUST NOT 执行镜像发布。镜像步骤与既有内网仓库、Maven Central 步骤相互独立——一个通道失败 MUST NOT 撤回或污染已成功通道的已发布内容，一个通道重试 MUST NOT 重推已成功通道。镜像发布任务 MUST NOT 减免发布门禁的任何一项：四项发布凭据属性断言、分支形态白名单、版本形态与仓库路由一致性、同号历史黑名单、发布标签远端存证核对、发布依赖形态核对在两种形态的镜像任务上照常先行执行；其中同号历史黑名单与发布标签远端存证两项按自身适用规则只对发布分支形态发生作用，属适用范围的一致表达而非对快照形态的减免。

#### Scenario: 镜像步骤失败不累及其他通道
- **WHEN** 一次正式版发布中内网仓库与 Central 步骤先成功，随后镜像步骤因网络故障失败
- **THEN** 内网与 Central 的构件保持已发布状态，构建报告独立呈现镜像通道的失败与原因，处置者可以只重试镜像步骤而不重跑其余通道

#### Scenario: 缺发布标签存证的正式版镜像被拒绝
- **WHEN** 远端不存在附注标签 `v<版本>` 时执行正式版本的逐仓镜像发布任务
- **THEN** 镜像被一致性门禁以标签存证缺失拒绝，GitHub Packages 上不会出现该版本的任何构件，发布纪律不因新通道出现旁路

#### Scenario: 快照镜像步骤失败不累及其他快照通道
- **WHEN** 一次开发线快照的持续集成发布中，内网快照仓与 Central 快照仓分发成功，随后快照镜像步骤因网络故障失败
- **THEN** 两条既有通道的快照构件保持已发布状态，构建报告独立呈现镜像步骤的失败与原因；处置不需要升号或删除动作，下一次快照发布自然补齐镜像缺失的构建

### Requirement: 快照构件进入镜像通道并随重发滚动到最新构建
开发线形态（分支 `<主>.<次>.x`、版本 `<主>.<次>.x-SNAPSHOT`）的快照构件 SHALL 镜像进入 GitHub Packages 的 Apache Maven 注册表通道，收录的模块范围与正式版本同一边界（见需求"镜像构件边界与消费方凭据要求"）。注册表服务端为每次快照上传分配带构建时间戳的存储文件并自动维护该快照坐标的元数据，消费方携有效凭据按快照坐标解析 MUST 能取得最近一次发布的构建（缓存刷新后滚动到最新，重发后旧构建仍按其时间戳标识可取回）；同一快照坐标的重复上传 MUST NOT 被按重复拒绝——各次构建文件名互不相同，不构成覆盖，重发是快照镜像维持新鲜度的常态手段，不适用同号一次成型义务（见需求"同号正式版构件一次成型且重复上传可判读"的适用范围限定）。同一快照构建的文件字节在镜像与内网两侧一致，但该坐标的时间戳与构建号标识由每个仓库各自独立编号，消费方以所在仓库的解析结果为准选取最新构建。快照的权威归档继续由内网快照仓库与 Maven Central 快照仓库承担，镜像是携凭据的补充消费通道；注册表对历史时间戳构建无自动清理记载，镜像侧随重发单调累积，项目方 MUST NOT 对外承诺回收，如需清理由运维按发布流程文档成文的包版本删除手段处置。快照镜像 MUST NOT 由发布者本机执行——"镜像仅由持续集成执行"的约束在快照开放后照旧成立，本机不持镜像凭据密钥时任务图中不出现任何镜像任务，从源头排除本机与持续集成对同一坐标的并发双发；快照镜像运行 MUST NOT 减免发布门禁。

本需求前身"快照构件不进入镜像通道"的排除依据句（注册表不生成含快照时间戳块的元数据、不提供目录列举、消费方按快照坐标解析必然失败、上传产物是不可被任何构建工具发现的孤儿文件）系失实陈述，随本次改写删除：首轮沙箱实测只检查了构件级元数据而漏检版本目录级元数据，得出错误结论（记录见归档目录 `2026-10-05-add-github-packages-channel` 的 `verification/sandbox-probe.md` 结论 2，已被复测勘误）；复测以真实 Gradle 与 Maven 消费端证明注册表服务端会自动为 Gradle 上传的快照维护含时间戳与构建号的目录级元数据，消费端可解析同一快照坐标并随重发滚动到最新构建（取证 S1 至 S8，记录见 openspec change 目录 `probe-github-packages-snapshot-support` 的 `verification/snapshot-spike.md` 现文）。用户已于 2026-10-05 裁决开放发布快照，原排除拍板随其失实依据一并作废。

#### Scenario: 开发线快照经重发在镜像滚动到最新构建
- **WHEN** 开发线已先后两次把快照构建镜像发布至 GitHub Packages，第三次快照发布在持续集成完成后，消费方携有效 classic 令牌按坐标 `<主>.<次>.x-SNAPSHOT` 解析并强制刷新依赖缓存
- **THEN** 解析取得的构件属于第三次构建（其文件名时间戳与构建号为该坐标当前最新），前两次构建按各自时间戳标识仍可取回，无需消费方更换坐标字面量

#### Scenario: 未配置镜像凭据密钥的本机快照发布不扇出镜像
- **WHEN** 开发者在未注入镜像凭据密钥的本机开发线分支执行 `./gradlew publish`
- **THEN** 任务图中不存在任何指向 GitHub Packages 的发布任务，快照构件只进入内网快照仓库与 Maven Central 快照仓库，本机行为与快照镜像开通前逐任务一致，配置阶段不因缺失凭据报错

#### Scenario: 快照镜像步骤失败不阻断后续补齐
- **WHEN** 某次快照镜像运行失败导致镜像缺失该构建，随后一次快照镜像运行成功
- **THEN** 镜像该快照坐标解析结果为最新成功构建，缺失的历史构建无需人工补发即被滚动超越；消费方不因此次缺失取到错误坐标——快照坐标解析永远返回该仓库当前最新时间戳构建

#### Scenario: 发布分支形态不得执行快照镜像
- **WHEN** 在发布分支形态（版本为裸号）的执行环境中请求把快照形态构件发布到镜像目的地
- **THEN** 该请求被发布门禁的分支形态与版本形态一致性断言拒绝，镜像中不出现与发布分支形态错配的快照构件（快照坐标只出自开发线形态，与 release-versioning 需求"快照坐标形态跨发布期保持稳定"一致）

## MODIFIED Requirements

### Requirement: 同号正式版构件一次成型且重复上传可判读
GitHub Packages 对已存在的构件文件拒绝覆盖上传（重复上传同名文件返回 HTTP 409；该行为官方文档未记载，多个项目的实测一致。该拒绝只发生于按坐标字面名存储文件的正式版本形态；快照构件的每次构建以带时间戳的文件名存储，同名文件不复存在，重复上传不被拒绝，故快照不在本需求的一次成型与 409 判读义务范围内，其滚动语义由需求"快照构件进入镜像通道并随重发滚动到最新构建"承担）。进入镜像的正式版本构件 SHALL 视为一次成型：对同一版本重跑镜像 MUST NOT 作为常态的新鲜度维护手段；操作者与持续集成在收到重复上传拒绝时，MUST 能够把它判读为"构件已在镜像中"的存证而非新故障，判读方法 MUST 在发布流程文档中成文；需要修正已镜像正式版构件时 MUST 优先采取提高补丁号重新发布并走完整发布流程的路线，而不是删除版本重发。

#### Scenario: 重跑已镜像版本的工作流按存证判读
- **WHEN** 对一次已镜像成功的发布，人工重新触发同一发布分支的工作流
- **THEN** 镜像步骤对已上传构件收到重复上传拒绝而失败，其余通道不受影响；错误输出与发布流程文档共同指向"构件已存在"的判读方法与只读核对版本清单的步骤，处置者不会误入删版本重发的默认补救

#### Scenario: 修正正式版缺陷走升号路线
- **WHEN** 发现已镜像的正式版本构件存在缺陷，需要发布修正
- **THEN** 按既有流程切出新的补丁号发布分支并完整发布，新版本构件进入包括镜像在内的全部通道，镜像中旧版本构件保持原样不删除

### Requirement: 镜像构件边界与消费方凭据要求
镜像通道 SHALL 收录 java 线全部发布模块与平台约束模块在正式版本与快照两种版本形态下的发布构件；对每一形态，其收录构件清单与内网仓库同形态发布运行逐件一致，同一快照构建的文件字节跨仓一致，而时间戳与构建号标识按各仓库独立编号。Gradle 插件模块的构件在两种形态下均 MUST NOT 收录（其插件标记构件的构件名含点号，官方 Maven 注册表的构件命名条文只列举小写字母、数字与连字符；沙箱实测含点号构件可上传，但该模块构件无签名、POM 无元数据组，镜像面貌与主通道不一致，纳入与否由后续独立变更裁决，该排除与版本形态正交）。镜像仓库的消费方下载 MUST 携带 GitHub 访问凭据——GitHub Packages 对公开包同样不开放匿名解析；接入文档 MUST 写明该事实、所需凭据类型（personal access token 的 classic 形态，fine-grained 形态截至 2026-10-05 不能访问 Packages）与所需权限，并写明 Maven 下游消费快照构件须在仓库声明中显式开启 snapshots（Maven 仓库声明默认不启用快照），Gradle 下游无需额外开关；免凭据的公开分发通道仍由 Maven Central 承担。

#### Scenario: java 线与平台约束构件跨仓一致可解析
- **WHEN** 一次正式版发布镜像成功后，消费方配置镜像仓库地址并携带有效 classic 令牌凭据解析任一发布模块与平台约束模块
- **THEN** 取得的 POM、jar 及附属构件与内网仓库同版本构件逐件等价，平台约束可正常导入

#### Scenario: 匿名解析被拒绝且指路可达
- **WHEN** 消费方声明了镜像仓库地址但未配置任何凭据执行依赖解析
- **THEN** 解析因认证被拒而失败，错误与接入文档共同指向凭据创建与配置路径，该现象在文档中作为注册表规则成文而非事故
