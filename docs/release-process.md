# 发布流程

本文档描述 TnyFramework 的分支模型、日常开发流程、发布流程与门禁规则。规格出处见
`openspec/specs`（capability `release-versioning`；capability `branch-integration-gates` 由变更
`redesign-devline-integration-model` 引入）。三条设计公理贯穿全文：制品坐标由分支名派生
（仓库内不存在版本文件）；release 标签是发布事实的唯一永久存证；main、开发版本分支与
release 维护分支只追加不改写——main 每次集成到主干产生一枚合并提交，first-parent 日志即集成账本。

> **切换进度注记**：本文档正在按变更 `redesign-devline-integration-model` 重写。术语表与分支角色
> 总表已是目标模型定稿；下文各流程条目仍描述现行模型，按该变更任务组 7 切换，切换前以术语表
> 定义为准、以流程条目标注的现行形态为操作依据。

## 术语表（目标模型权威定义）

| 术语 | 定义 |
|---|---|
| 开发版本分支 | 形态 `dev/<主>.<次>.x`（如 `dev/5.8.x`）。一个次系列的特性开发场所，自 main 分支头切出，首发前持续接收特性；构建派生 release 维护分支快照坐标 `<主>.<次>.x-SNAPSHOT`（坐标字符串不含 `dev/` 前缀，与历史坐标完全一致）。完成集成到主干后删除该分支。 |
| release 维护分支 | 形态 `release/<主>.<次>.x`（如 `release/5.7.x`）。每个已发布次系列唯一一条，自该系列集成后的 main 分支头切出，此后只接收补丁修复，滚动发布 `N.M.0、N.M.1、……`；不产快照。 |
| feat 分支、fix 分支 | 形态 `feat/…`、`fix/…`。单次工作的暂存分支，是全仓唯一允许强制推送的分支类型，且必须使用 `--force-with-lease`。 |
| 集成到主干 | 把某个开发版本分支并入 main 的固定顺序动作：先把 main 合并同步进该开发版本分支，再以产生合并提交的方式将该分支整体并入 main，合并提交说明按固定格式 `integrate dev/<N.M.x> to main: <版本>` 记录，随后删除该开发版本分支。低编号开发版本分支未集成前，高编号不得集成（开发版本分支集成顺序检查）。 |
| 向上合并 | 把源分支的补丁内容带到更新的 release 维护分支与 main 的动作，机制为整条分支合并（英文注记 merge-forward 只表方向，不表逐笔复制）。目标分支因此完整包含源分支历史，"补丁是否已到达"以祖先判定为权威。解决冲突后、提交前必须通过合并结果完整性检查。 |
| 合并结果完整性检查 | 向上合并产生提交之前的强制检查：对本次搬运的每个缺陷编号在合并结果的全部文件内容中检索，任一缺失即中止提交并列出缺失清单。 |
| cherry-pick 例外登记 | 整条分支向上合并因代码位置分叉无法机械解决时的例外制度：改用 cherry-pick 复制单个修复提交，提交说明必须记录来源提交哈希（`cherry picked from` 尾注）与判定记录（判定人、日期、原因），且该补丁随目标分支下一版发出。 |
| 源分支 | 一笔补丁最初落位的分支，即最老的仍在接收补丁的 release 维护分支（仅影响未发布代码时为对应开发版本分支）。 |
| release 标签 | 发布流程经 releaseTag 任务创建的、名为 `v<主>.<次>.<补丁>` 的 git 附注标签对象。一经推送永不移动；版本号、制品内容与代码提交位置三者对账以其解引用记录为权威依据。历史 `-RELEASE` 后缀标签称"历史遗留标签"，不在本定义内；提及平台功能时使用全称 GitHub Releases。 |
| release 标签核验 | 发布门禁对 release 标签执行的检查动作（远端存在、附注形态、指向当前构建提交）。"存证"描述标签的身份，"核验"描述门禁的动作，两个角色不混用。 |
| 下一补丁号校验 | release 维护分支发版时的强制校验：目标版本号前两段与分支编号一致，且第三段恰为该分支已发布标签的最大补丁号加一。 |
| 补丁影响清单 | 修复类 PR 描述必填字段，完整行文为"该补丁影响到的 release 维护分支清单"；判定不受影响的分支须逐条写明理由。特性类 PR 不声明该清单。后续向上合并与退役核对以本清单为准。 |
| 退役 | 分支终止维护的手续：删除分支之前检查该分支上已提交但尚未进入 main 的提交（未集成提交），确需保留的完成向上合并，判定废弃的逐笔写明理由并登记；此后该系列历史经 release 标签账本完整还原。 |
| 分支头 / 该分支的最新提交 | 指顶端指针时写"分支头"，指提交对象时写"该分支的最新提交"；`HEAD` 一词只保留给 git 的符号引用。 |
| 祖父条款登记 | `gradle/branch-legacy-registry.txt` 登记的旧形态分支（首条为 `5.7.x`），按登记身份获得对应发布资格；新形态自 5.8 系列启用。 |

词表纪律：以下旧词与比喻不再进入文档、代码注释与汇报——工位、电梯、升梯、登车、早切晚锁、
发布容器、清账、补账、硬锚、编年史、断代、基取、落点、上合、下传、在役、让位，以及一切
"坟场"类修辞。

## 三个上行动作判定表（何人把何内容经何机制移到何处）

| 动作 | 谁发起 | 搬运内容 | 机制 | 去处 |
|---|---|---|---|---|
| 集成到主干 | 发布首发时 | 整个开发版本分支（特性与首发前修复） | 先同步 main，后产生合并提交 | main；完成后删开发版本分支 |
| 向上合并 | 补丁发布后与退役前 | 源分支全部补丁（整条分支） | git merge 逐级向上，提交前过合并结果完整性检查 | 更新的 release 维护分支，最后到 main |
| cherry-pick 例外登记 | 整条合并不可行时 | 单个修复提交 | cherry-pick 加来源与判定登记 | 目标分支，随其下一版发出 |

## 分支角色总表（目标模型）

| 对象 | 命名形态 | 职责 | 允许的操作 | 禁止 |
|---|---|---|---|---|
| main | `main` | 集成主干：只接收集成到主干与向上合并两类内容；GitHub 默认分支 | 接收以上两类合并；正常推送 | 直接开发提交、rebase、强制推送 |
| 开发版本分支 | `dev/<主>.<次>.x` | 一个次系列的特性开发场所；发 `N.M.x-SNAPSHOT` 快照 | feat 分支 rebase 合入、main 同步合并、补丁合入、集成到主干后删除 | 强制推送、改写历史 |
| release 维护分支 | `release/<主>.<次>.x` | 已发布系列的补丁滚动：发 `N.M.K` 裸号，每系列唯一 | fix 分支 rebase 合入、向上合并承接、打 release 标签并推送 | 接收特性、强制推送、rebase、改写历史 |
| feat 分支 / fix 分支 | `feat/…`、`fix/…` | 单次工作暂存 | rebase；`--force-with-lease` 强制推送（全仓唯一豁免） | 直接发布（不在白名单） |
| release 标签 | `v<主>.<次>.<补丁>`（附注） | 发布事实的存证与三者对账权威 | 创建后单独推送 | 已推送即永不移动、永不删除 |
| 祖父登记线 | 如 `5.7.x`（登记于 `gradle/branch-legacy-registry.txt`） | 现行 5.7 系列维护与快照的过渡载体，至该系列退役 | 按登记身份执行对应旧/新流程 | 新增登记条目（豁免只减不增） |
| 其他分支 | 例如 `5.0.x.net` | — | — | 门禁拒绝发布 |

**全仓铁律**：main、开发版本分支与 release 维护分支只追加不改写——禁止对这三类分支的
强制推送与历史改写；main 接收的整体合并以"集成到主干"与"向上合并"两种动作为限，其余
方向（旧分支向更旧分支、分支向 main 的绕行合并）一律禁止。release 标签一经推送永不移动。
允许强制推送的分支类型仅为 feat 分支与 fix 分支，且必须使用 `--force-with-lease`。

## 契约变更声明（BREAKING，2026-10 生效）

自本模型起，`5.7.x-SNAPSHOT` 的含义从"线上最新一切内容"收窄为"**5.7 系列的最新维护态**"：
新特性不再进入补丁版本，也不进入版本开发分支快照，特性只随次版本线（下一个是 `5.8.x`，其滚动坐标
`5.8.x-SNAPSHOT` 于开线当晚生效）到达下游。依赖滚动坐标的下游**无需修改任何坐标声明**，
需要持续吃特性的下游应改锁新次版本线坐标。5.7.8 首发按旧语义发布，属历史事实；自下一个
次版本线起执行新语义。（本段为 2026-10-04 发布时的原文存档，其中"版本开发分支"在新模型
条文里按语境对应"开发版本分支"或"release 维护分支"，新条文一律使用新词。）

第二波契约变更（2026-10-06，变更 `redesign-devline-integration-model`）：开线形态自
5.8 系列起改用 `dev/` 与 `release/` 前缀分支；正式版发布载体由一次性发布分支
（`<V>.release`，此后不再产生）改为常驻 release 维护分支滚动；补丁到达主干的通路
合法化为"集成到主干"与"向上合并"两个正式动作，main 的 first-parent 日志自此成为
集成账本。快照坐标字符串保持 `N.M.x-SNAPSHOT` 字面形态不变，**下游继续零坐标改动**。
`5.7.x` 以祖父登记线身份过渡（登记于 `gradle/branch-legacy-registry.txt`），该系列
退役后登记表清空，旧形态随之消失。

## 流程一：创建 feat 分支（特性工作开始）

- **前提**：目标次系列的开发版本分支 `dev/<主>.<次>.x` 已存在（不存在时先走流程五）。
- **命令**：`git switch -c feat/<主>.<次>.x-<名> github/dev/<主>.<次>.x`（起点为该开发
  版本分支的分支头；示例 `feat/5.8.x-actor-pool`）。
- **验证点**：`git merge-base --is-ancestor github/dev/<主>.<次>.x HEAD` 成立的反向检查——
  feat 分支基提交在开发版本分支祖先链上。
- **禁止**：以 main 为特性基线（main 不接收直接开发）；以 release 维护分支为特性基线
  （维护分支只收补丁）。

## 流程二：feat 同步与合入开发版本分支

- **触发**：开发版本分支前进后同步 feat 分支，或 PR 前收尾。
- **命令**：`git fetch && git rebase github/dev/<主>.<次>.x`；feat 分支自身允许
  `git push --force-with-lease github feat/<名>`（允许强制推送的仅此一类分支）。
- **合入**：向开发版本分支发 PR，GitHub 以 rebase-merge 方式合入——先变基再快进，
  开发版本分支不产生合并提交。
- **禁止**：对 main、开发版本分支、release 维护分支执行 rebase 或强制推送。

## 流程三：创建 fix 分支（源分支判定）

- **触发**：缺陷修复工作开始。
- **源分支判定（二选一）**：
  1. 缺陷存在于已发布系列：源分支为**最老的仍在接收补丁的 release 维护分支**，
     `git switch -c fix/<主>.<次>.<补丁>-<名> github/release/<主>.<次>.x`
     （祖父轨过渡期该分支为登记的 `5.7.x`）。
  2. 缺陷只存在于未发布代码：源分支为所在开发版本分支。
- **补丁影响清单**：修复 PR 必须按模板声明"该补丁影响到的 release 维护分支清单"——
  逐分支标"需要收到"或"不受影响＋理由"；"不受影响"须可复核（如在目标树检索缺陷
  代码签名得空）。该清单是流程七向上合并与退役核对的账本依据。
- **禁止**：在维护分支上直接编辑提交（必须经 fix 分支）；把源分支定在更高编号分支上
  （补丁会失去谱系来源）。

## 流程四：fix 同步与合入源分支

- **命令**：`git fetch && git rebase github/<源分支>`；fix 分支自身允许
  `git push --force-with-lease`。
- **合入**：向源分支发 PR，rebase-merge 合入后源分支普通推送。
- **验证点**：合入不产生合并提交，源分支保持线性。
- **禁止**：把 fix 分支变基到源分支以外的分支。

## 流程五：创建开发版本分支（开新线）

- **触发**：值得开一个新次系列；主版本升级须先附协议与公共 API 兼容性评估。
- **命令序列**：
  1. 确认 main 的 CI 为绿（`gh run list --branch main --limit 1` 对照）。
  2. `git switch -c dev/<主>.<次>.x github/main && git push -u github dev/<主>.<次>.x`。
  3. CI 触发与快照镜像选线随线谱系登记走；状态列措辞与工作流解析器同批改，二者不可
     分两天改（首跑教训记在合并后 `publish.yml` 的 route 作业注释）。
  4. 开线记录：线谱系登记表追加一行（线名、开线提交、日期、当时上一线最新标签、状态）。
- **验证点**：`dev/5.8.x` 首次构建派生 `5.8.x-SNAPSHOT`（坐标字符串不含 `dev/` 前缀，
  下游既有坐标声明无需任何修改）。
- **禁止**：从维护分支的分支头切新开发版本分支（内容前沿在 main）；跳过中间次编号开线
  （5.7 之后直接 5.9）而不按改号跳号程序登记注销。并行孕育多条开发版本分支合法，
  但集成到主干必须按版本顺序排队（流程六）。

## 流程六：系列首发（集成到主干到发布 5.8.0）

- **触发**：开发版本分支的特性集合达到发布标准。
- **命令序列**（gradle 任务建议在独立完整克隆执行并带 `-PgitExe=/usr/bin/git`；`-PdryRun`
  预览不触 CLI；下文不再逐步重复标注）：
  1. 在 `dev/5.8.x` 上 `./gradlew integrateMain -PreleaseVersion=5.8.0`——顺序检查
     （低编号在途开发版本分支存在即拒绝）→ 同步合并 main → 整体合入 main 产生合并提交
     （说明固定格式 `integrate dev/5.8.x to main: 5.8.0`）→ 推送 → 删除该开发版本分支。
  2. 在 main 上 `./gradlew releaseCut -PreleaseVersion=5.8.0`——自 main 分支头切出该系列
     唯一的 `release/5.8.x` 维护分支并推送；不建标签。
  3. `git switch release/5.8.x` 后 `./gradlew releaseTag -PreleaseVersion=5.8.0`——
     远端头对齐与下一补丁号校验通过后建附注标签 `v5.8.0` 并推送；标签先于制品。
  4. `./gradlew publish`——七项门禁通过后制品入内网正式仓；Central 正式版通道按
     "Central 发布"一节执行；GitHub Packages 正式版镜像由 publish.yml 第三步骤执行
     （本机配置成对凭据时亦扇出，见镜像一节）。
- **验证点**：`v5.8.0` 标签、`release/5.8.x` 分支头、制品构建提交三者同值；标签此后
  永不移动；main 的 first-parent 日志可枚举行 `integrate dev/5.8.x to main: 5.8.0`。
- **禁止**：先 publish 后 releaseTag；在维护分支切出前向 main 直提首发提交（首发提交
  由 integrateMain 一步完成）。

## 流程七：维护分支滚动发布与向上合并

- **触发**：在服的 release 维护分支收到已定型补丁（如 5.7.10、5.8.1）。
- **命令序列**：
  1. 按流程三、四把修复合入源分支并推送。
  2. `./gradlew releaseTag -PreleaseVersion=<号>`——下一补丁号校验保证补丁号连续、
     同号不复用。
  3. `./gradlew publish`——门禁七项。
  4. `./gradlew mergeUpward`——默认目标为全部更高编号 release 维护分支加 main，
     按补丁影响清单核对应有目标；整条合并进各目标，提交前执行合并结果完整性检查
     （缺陷编号在合并结果树逐个检索，任一缺失即回滚目标分支原头并拒绝），随后普通推送。
- **验证点**：`git log <目标>..<源分支>` 对每个应有目标为空（祖先判定即到达判定）；
  `git rev-list --count <分支> --grep=<缺陷编号>` 每条受影响分支大于零。
- **例外通道**：代码位置分叉导致整条合并无法机械解决时，改用 `cherry-pick -x` 复制
  单个修复提交，提交说明必须带来源哈希（`cherry picked from` 尾注）与 propagated-as
  登记（判定人、日期、原因），并随目标分支下一版发出（下一补丁号校验强制入账）。
  `git cherry` 在此场景会把已人工移植的补丁报为未移植（patch-id 分叉，假阳性），
  只能作辅助信号，权威判定看登记与祖先关系。
- **禁止**：向更旧分支传播补丁（修复自最老源分支向上，反向不存在）；向上合并之后
  移动或删除源分支与其任何标签。对外引用（工单、发布说明）一律写 release 标签，
  不写提交哈希。

## 线谱系登记

开新线时在下表追加一行（流程五步骤 4 规定的登记位），线名按分支全名书写
（`dev/5.8.x`），状态列取值：`开发版本分支（在途）`、`祖父维护线（快照在维）`、
`已退役`、`历史资产（只读）`；快照镜像选线以状态含"在途"或"快照在维"的行为唯一依据
（`publish.yml` 的 snapshot-mirror 作业解析器与本表措辞同批修改，见红线教训）。5.7.x 之前的线史不追溯登记，自本表起算。

| 线 | 开线提交 | 开线日期 | 开线时上一线最新标签 | 状态 |
|---|---|---|---|---|

## 发布门禁的校验项（按执行序）

`./gradlew publish`（以及任何共享仓发布任务）在任何模块上执行前由 `tny.publish`
约定插件的门禁任务校验，任一项不通过即整构建失败并列出全部问题：

1. 分支资格双层判定：`dev/<主>.<次>.x`（快照）与 `release/<主>.<次>.x`（裸号）两形态，
   或祖父登记表（`gradle/branch-legacy-registry.txt`）内的登记线按其登记身份；
   其余分支（含 main、feat 分支、fix 分支、未登记的旧形态线）一律拒绝并给出
   当前分支名与合法形态清单。
2. 版本形态匹配：开发版本分支版本必须恰为 `<主>.<次>.x-SNAPSHOT`（分支名去 `dev/`
   前缀）；维护分支版本必须是该系列裸三段号（由 `-PreleaseVersion` 注入并经前缀核对）。
3. 下一补丁号校验：维护分支发版号必须恰为远端该系列最大补丁标签加一（首发为零）；
   远端查询失败按无标签处理，走拒绝路径（fail-closed）。
4. 同号黑名单：目标裸号命中 `gradle/released-legacy.txt`（历史 `-RELEASE` 形态占用号）
   或远端已有同号 release 标签时拒绝，防止同号双形态共存导致排序纠缠。
5. 仓库路由一致：快照版本不得指向 release 仓 URL，裸号版本不得指向快照仓 URL。
6. release 标签核验：远端必须存在 `vN.M.K` 附注标签（含 `^{}` 解引用记录）且解引用
   指向当前构建提交；远端不可达按缺证拒绝。结果一次构建内记忆化。JGit 对附注标签
   只给"已解引用"标志不给解引用提交号，故本项维持 git CLI 实现（定案见归档变更
   `migrate-git-calls-to-grgit` 的 probe-jgit-remote.md）；`-PgitExe` 覆盖二进制路径。
7. 依赖形态核对：发布线全部构件的直接依赖坐标带预发布后缀且未登记
   `gradle/publish-prerelease-exemptions.txt` 的拒绝发布；生效豁免条目在门禁输出逐条打印。

## 恢复条目（故障手册摘录）

| 情况 | 系统表现 | 处置 |
|---|---|---|
| 忘打 release 标签就 publish | 门禁第 6 项拒绝"标签不存在" | 补跑 releaseTag，重跑 publish，无孤儿制品 |
| 标签指向错提交但**尚未推送** | 本地错标，远端无档 | 删除本地错标重建再推送——规格禁动的是"已推送"的标签，这是唯一合法重建窗口 |
| 标签指向错提交且**已推送** | 门禁拒绝（解引用不符） | 绝对不动：该号作废，提高补丁号重发（"一经推送永不移动"无例外） |
| 集成时低编号开发分支仍在 | integrateMain 顺序检查拒绝并列出阻塞分支 | 先完成低编号系列集成；确需放弃的线按改号跳号程序注销（删除分支并在提交说明登记）后重跑 |
| 向上合并发生冲突 | mergeUpward 自动 abort 并把目标分支回退原头、切回源分支，三态原封 | 人工在目标分支重做该合并，解决后自行执行合并结果完整性检查再提交，或改走例外通道登记 |
| 完整性检查拦截（标记丢失） | mergeUpward 回滚目标分支并列出缺失缺陷编号 | 重新解决冲突覆盖该修复；确属目标结构已无该代码路径时，登记豁免并在目标结构重做保护（编号加后缀如 BUG-102-13） |
| 推送 main 被拒（远端被他人推进） | 普通推送拒绝 | `git pull --ff-only github main` 对齐后重推；ff-only 失败说明 main 被并行推进，等对方动作完成后重跑 |
| 维护分支远端头与本地不一致 | releaseTag 拒绝并打印两个头指针 | 先 push 本地补丁或 pull --ff-only 对齐后重跑 |
| 远端不可达 | 门禁与校验 fail-closed 拒绝 | 网络恢复重跑 |

## 制品库运维前置条件（由运维侧执行，不在构建代码内）

1. 正式发布仓（maven-releases）禁止重复部署同一版本坐标，保证裸号正式版不可变。
2. 快照仓（maven-snapshots）配置按天数的保留清理策略：滚动快照坐标 `N.M.x-SNAPSHOT`
   每在线上执行一次 publish 即追加一份时间戳产物且永不互相顶替（内网与 Central 通道的快照
   发布是人工动作，口径见流程五；`publish.yml` 的 snapshot-mirror 作业定时只写 GitHub Packages 镜像
   通道，不产生内网或 Central 构件），无保留策略则磁盘无界增长。
3. GitHub Packages 镜像通道对同一版本的已存在文件拒绝覆盖上传（同名文件重复上传返回
   HTTP 409，本仓沙箱实测证实；官方条文未记载此规则），正式版本进入该通道因此是一次
   成型动作；失败处置按"GitHub Packages 镜像通道"一节的阶梯执行，不得以重跑全量发布
   作为默认补救。限定：快照构件以时间戳文件名存储、重发不受此限，属镜像侧常态新鲜度维护；
   镜像对历史时间戳构建无自动清理记载，累积治理见"GitHub Packages 镜像通道"体量条目。

## Central 发布（正式版第二通道）

自 central-publish-tnydev-group 变更起，正式版同时发布到 Maven Central（组号 `com.tnydev.game`）：

- 本地通道：`./gradlew publish`（Nexus，不变）→ `./gradlew publishAggregationToCentralPortal`
  （nmcp 聚合上传；`centralCheck` 前置校验分支形态与凭据，上传前逐模块校验四件套与签名配对）。
  凭据：`mavenCentralUsername/mavenCentralPassword`（Portal User Token）用户级属性 +
  签名三属性同内网通道。快照永不进 Central（非发布分支被 `centralCheck` 拒绝，
  nmcp 暴露的快照上传任务已全部禁用）。
- CI 通道：`.github/workflows/publish.yml`——release 事件（按标签推导发布分支）或
  `workflow_dispatch` 人工触发，三个目的地（内网 Nexus、Maven Central、GitHub Packages 镜像——
  镜像步骤仅收正式版本，快照镜像见"GitHub Packages 镜像通道"一节）分步独立执行、互不回滚。所需 secrets：
  `MAVEN_CENTRAL_USERNAME/PASSWORD`、`SIGNING_KEY`（armor 私钥）/`SIGNING_KEY_ID`/`SIGNING_PASSWORD`、
  `NEXUS_USERNAME/PASSWORD`。前置条件：`com.tnydev.game` 命名空间已在 Portal 完成 DNS 验证。
- 快照通道：开发线 `./gradlew publish` 自动分发**内网快照仓与 Central 快照仓**双目的地（条件=快照版本形态且本机配置 `mavenCentralUsername/Password`，缺凭据机器仅发内网；Central 快照 90 天自动清理，权威归档在内网）。快照的第三个目的地为 GitHub Packages 镜像——其参与方式（持续集成定时与本机来源的边界）以能力 github-packages-mirror 条文为准，见"GitHub Packages 镜像通道"一节。
- 首版验收：Central 检索到 `com.tnydev.game:tny-game-*:<版本>` 全模块清单后，本流程定版。

## GitHub Packages 镜像通道（正式版本与快照构件的第三目的地）

自 add-github-packages-channel 变更起，裸号正式版本构件镜像分发到
`https://maven.pkg.github.com/tunaiyi/tny-framework`（URL 的属主段按官方注册表命名规则全小写，
与 POM scm 段页面地址的大小写形态不同属有意为之，两处用途不同）。自 open-github-packages-snapshot-mirror
变更起，开发线快照构件一并进入镜像——快照最初按首轮沙箱实测被排除，该结论已被复测推翻，
勘误与裁决经过见下文"快照镜像的复测与开通裁决"条目。本通道是尽力镜像：
权威归档仍是内网 Nexus 仓与内网快照仓，免凭据的公开分发仍是 Maven Central。

- **触发形态**：有两个合法来源——持续集成：发布全链路统一在单文件 `.github/workflows/publish.yml`
  （consolidate-publish-workflows 变更后的三作业结构：route 判定链路、publish-release 作业执行
  正式版三步链、snapshot-mirror 作业执行快照镜像）——正式版镜像由 release.published 事件或
  workflow_dispatch 填 `<X.Y.Z>.release` 触发，经 publish-release 作业第三个发布步骤执行；
  快照镜像由 snapshot-mirror 作业每日定时（UTC19:23，与 build.yml 夜间作业错峰）执行当前
  快照在维线一次——选线以本文"线谱系登记"表状态含"在途"或"快照在维"的行为唯一依据，与内网快照
  发布同一口径；维护态、退役线与历史线不在定时范围，确需其镜像快照时经 workflow_dispatch
  填线名单次补跑（人工指定即授权，非法输入由 route 判 none 空转）；定时与选线逻辑以 main
  默认分支上的文件为准生效。
  本机来源：发布者成对配置镜像凭据后，`./gradlew publish` 即扇出镜像（含正式版与快照）。
  镜像凭据由 `githubPackagesUsername` 与 `githubPackagesToken` 两个属性构成（用户名即令牌属主
  的 GitHub 账户名），**成对在位且均非空**才声明目的地——空值或缺失一律视同未配置；两个属性
  任何时候不得提交进仓库文件。持续集成经 env 注入（用户名取运行账户 `github.actor`、令牌为
  内置 `GITHUB_TOKEN`）；发布者可在用户级 `~/.gradle/gradle.properties` 配置这两行发起本机镜像
  发布——快照的本机扇出与每日定时共存无冲突（各构建时间戳文件名互异）；正式版本推荐由发布者
  单机或持续集成统一其一执行，若本机已先推过同号正式版、持续集成镜像步骤随后收到 HTTP 409，
  按下方阶梯"构件已在镜像中"的存证判读并忽略该步骤失败；未成对配置的机器不声明该仓库，
  本机行为与镜像无关。
- **收录范围**：java 线全部发布模块与 BOM 模块收录，正式版本与快照两种形态均在镜像范围；
  Gradle 插件模块 `tny-game-doc-gradle` 两种形态都不收——其构件无签名、POM 无元数据组，镜像面貌
  与主通道不一致，未来纳入由独立变更裁决。镜像不减免任何门禁：四项属性断言、分支形态
  白名单、仓库路由、同号黑名单、发布标签远端存证与发布依赖形态核对在两种形态的镜像运行上
  照常先行；其中同号黑名单与发布标签存证按自身适用规则只对发布分支形态发生作用
  （快照形态无标签前置），属适用范围的一致表达而非减免。
- **快照镜像的复测与开通裁决（勘误记录）**：首轮沙箱实测（归档目录
  `2026-10-05-add-github-packages-channel` 的 `verification/sandbox-probe.md` 结论 2）只检查了构件级
  元数据、漏检版本目录级元数据，得出"注册表不生成含快照时间戳块的元数据、消费方按快照坐标
  解析必然失败"的失实结论，据此在开通时排除了快照。复测（归档目录 `2026-10-06-probe-github-packages-snapshot-support` 的 `verification/snapshot-spike.md`，取证 S1 至 S8）更正了该事实：注册表服务端自动为 Gradle 上传的
  快照维护含时间戳与构建号的目录级 unique 元数据，Gradle 与 Maven 消费端可解析快照坐标并随重发
  滚动到最新构建，快照重发因各构建时间戳文件名互异不触发 HTTP 409。用户已于 2026-10-05 裁决
  开放发布快照（变更 open-github-packages-snapshot-mirror），原排除拍板随其失实依据作废；复测报告
  中"建议维持排除"一节（价值缺口、账本负担、纪律成本三条理由）亦被该裁决推翻，其中仍成立的事实
  （免凭据消费优先 Central、镜像历史不清理）转化为本节的消费建议与体量条目。快照的权威归档仍是
  内网快照仓（开发线 `./gradlew publish`），免凭据的公开快照消费仍是 Central 快照仓。
- **同号重复上传的判读与处置阶梯**：本阶梯只适用于正式版本构件；快照构件按时间戳文件名存储，
  重发不会触发 409，属常态新鲜度维护，不适用升号优先的处置路线。注册表对已存在的（正式版）文件
  拒绝覆盖（HTTP 409），正式版本因此一次成型。重跑工作流收到 409 时先按"构件已在镜像中"的存证判读——以只读方式核对版本
  清单（包页面或 `gh api "users/Tunaiyi/packages?package_type=maven"`），不为消除报错而删版本。
  修正需要发布构件时的处置次序：① 首选提高补丁号走完整发布流程（releaseCut 至
  releaseMergeBack，与"标签一经创建不可移动"的既有纪律一致）；② 必须保留同号时，由对
  仓库有管理权限者先删除受影响版本——实测工作流内置令牌经 GraphQL `deletePackageVersion`
  即可删除（参数要用 GraphQL 全局节点 ID，REST 清单里的数字 ID 不可混用），删除后同一
  版本号可立即重新上传；注意官方限制：公共包的任一版本下载量超过 5000 次即无法删除，
  删除后 30 天内可恢复，采用本路线前以一次性测试版本确认约束满足；③ 仅部分模块已镜像时，
  可对未上传模块逐个补跑 `./gradlew :模块名:publishAllPublicationsToGithubPackagesRepository`
  ——该任务命中共享仓门禁谓词，会连带执行全量 check 与标签存证核对，并非轻量操作，且
  未配置镜像凭据的机器上该任务根本不存在。
- **消费方接入**：GitHub Packages 对公开包同样要求凭据下载，不存在匿名解析。凭据须创建
  personal access tokens (classic)（fine-grained 令牌截至 2026-10-05 不能访问 Packages，官方
  缺口清单注明"并非永久"，如日后放开以官方现文为准）并勾选 `read:packages` scope；因 Maven
  包的权限完全继承所在仓库，官方规则同时要求 `repo` scope，建议为接入本镜像单独创建最小
  用途的令牌。Gradle 下游工程把下面条目加进其依赖解析仓库的声明位置——采用集中声明的工程
  （`settings.gradle` 启用 `dependencyResolutionManagement` 的，本仓库自身即此形态）加进它的
  `repositories` 块，未采用的加进自身构建脚本的 `repositories` 块，两种形态的条目内容相同：

      maven {
          url = 'https://maven.pkg.github.com/tunaiyi/tny-framework'
          credentials {
              username = providers.gradleProperty('gprUser').get()
              password = providers.gradleProperty('gprToken').get()
          }
      }

  （`gprUser` 与 `gprToken` 写在用户级 `~/.gradle/gradle.properties`，或由 CI 经
  `ORG_GRADLE_PROJECT_*` 注入；属性键名不得含点号。两个属性任一缺失时 Gradle 在配置期
  报缺属性、错误可读，不会带着空凭据到解析期才收认证错误。）Maven 下游在 `pom.xml` 声明
  同一 URL，并在 `~/.m2/settings.xml` 配置同 id 的 server 凭据。本通道收录快照：Gradle 下游按
  默认声明即可解析正式与快照两种坐标，无需额外开关；Maven 下游若消费快照坐标，须在仓库声明中
  加 `<snapshots><enabled>true</enabled></snapshots>`（Maven 仓库声明默认不启用快照，漏配会表现为
  解析取不到快照而非通道故障）。
- **体量与速率**：公共仓库的包存储与流量免费（官方计费条文）。一次全量发布向镜像上传约
  六十余个构件族、上千次 PUT（每构件附 md5、sha1、sha256、sha512 四种校验和）。限流类
  失败（HTTP 429 或超时）与 409 的判读区别在响应正文——后者明写拒绝覆盖；限流失败的处置
  是分批补传，不是升号或删版本。快照镜像对当前开发线每日新增一组时间戳构建，注册表对历史时间戳构建
  无自动清理记载，镜像侧单调累积且项目方不作回收承诺；确需清理时按上述判读阶梯第②步的
  GraphQL 删除手段处置（公共包单版本下载超 5000 次不可删等约束与一次性验证实操同样适用）；
  快照的保留策略治理在内网快照仓（运维前置第 2 条）与 Central 快照仓（90 天自动清理）侧成文，
  镜像侧暂以已知限制记录。

## 快速通道（Gradle 任务）

发布顺序由 `tny.release` 与 `tny.integrate` 两个约定插件的四个任务固化：
`integrateMain`（开发版本分支按"同步、整体合并、下线"固定顺序集成进 main，前置
集成顺序检查）、`releaseCut`（新形态在 main 上切系列唯一的 release 维护分支；
祖父轨保留旧一次性发布分支语义）、`releaseTag`（维护分支头建附注标签并推送，含
下一补丁号校验与远端头对齐）、`mergeUpward`（源分支整条向上合并至更高编号维护分支
与 main，提交前执行合并结果完整性检查）。四任务均支持 `-PdryRun` 预览。旧任务
`releaseMergeBack` 已删除，其"把发布分支独有提交带回主线"的语义由 mergeUpward 的
整条合并取代；更早的 `releaseCutAndTag` 拆分沿革见归档变更
`revise-release-branch-flow`。通道分界（变更 consolidate-git-queries-into-gitflow 定型）：
写动作一律经 GitCli 门面执行，一切远端引用的读取与解释一律经 GitFlow 的查询方法面
（远端解析在 GitFlow.remoteRefs 单点拥有，插件脚本内不出现命令输出解析）；两者同落
git CLI 单通道（`-PgitExe` 覆盖二进制；grgit/JGit 依赖已由变更 retire-grgit-channel 退场）。提交纪律：修复类提交必须携带缺陷编号
（`.githooks/commit-msg` 钩子，安装命令 `git config core.hooksPath .githooks`，
CI 侧同规则校验），向上合并的完整性检查以该编号为检索键。

**发布与验证的执行环境**：gradle 构建对任意 git 布局开放——完整克隆、linked worktree、
子模块均可（变更 retire-grgit-channel 解除旧禁令：禁令的唯一技术理由是 JGit 不解析 linked
worktree 的 commondir 重定向，升级 6.10.1 实测证伪，证据见归档 `upgrade-grgit-for-worktrees`；
该缺陷库已随 git 能力全量 CLI 化退场）。发布快速通道操作（integrateMain、releaseCut、
releaseTag、mergeUpward、publish）仍**建议在独立完整克隆中执行**：这些任务会移动 HEAD 并
写标签/分支，与并行会话共用工作区时存在 HEAD 与 index 争用——这是运营纪律而非构建拦截。
克隆自带完整 `.git`，全链路已实测可用；代价仅为磁盘占用与首次构建缓存。
