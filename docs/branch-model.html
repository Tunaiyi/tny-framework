TnyFramework 分支模型总览

权威文本：docs/release-process.md 与规格账本 release-versioning（七条需求）。本页是导读，冲突以二者为准。

公理一
版本语义住在分支名里，仓库不存在版本文件。下游因此能锁定一个跨发布期永不改名的滚动坐标 5.7.x-SNAPSHOT。
公理二
标签是发布事实的唯一永久存证：标签先于制品，解引用恰指构建提交，推送后绝对不动。
公理三
每个对象只有一种变更原因：main 管未来（特性），版本开发分支管过去（修复），版本发布分支管那一刻（制品），三者永不互相改写。

一、分支类型

类型命名形态一句话身份
开发顶点main特性与日常修复的唯一开发区，PR 默认底，CI 恒常基线
版本开发分支<主>.<次>.x（如 5.7.x）该版本系列的维护阵地；规格条文中称"开发线分支"
版本发布分支<主>.<次>.<补丁>.release一次发布的构建载体；名字即裸号版本
发布标签v<主>.<次>.<补丁>（附注）"该版本出自哪个提交"的永久答案
特性工位feat/<主>.<次>.x-<名>单次特性草稿；版本号是目标预期，延期不改名
修复工位fix/<主>.<次>.<补丁>-<名>单次修复草稿；补丁号对应实际目标发布分支

二、职责、允许与禁止

main开发顶点

允许：正常提交；rebase-merge 合入特性与修复。
禁止：发布制品（不在门禁白名单，天然拒绝）；接收任何老线的反向合并。

5.7.x版本开发分支

允许：快进推送；修复重放落点；维护性 PR 合入；在其上执行 publish 产出滚动快照 5.7.x-SNAPSHOT。
禁止：改写历史、强推、接收特性提交（特性只进 main）。

5.7.9.release版本发布分支

允许：标签创建前快进式追加修复提交并推送（hotfix）。
禁止：任何历史改写；标签创建后一切移动。

v5.7.9发布标签

允许：创建后单独推送；先于制品存在（门禁第五重核对解引用等于构建提交）。
禁止：已推送后移动、删除、改名；未推送的本地错标可删后重建，是唯一修正窗口。

feat/...、fix/...工位

允许：rebase；对个人分支强推（全仓唯一豁免——产物入 main 或线前必经 rebase-merge 重铸）。
禁止：直接发布（形态不在白名单）。

门禁识别形态即资格

只有 N.M.x 与 N.M.K.release 两种形态有发布资格；其余形态（含 main、历史分支、四段号）一律拒绝，拒绝文案自带合法形态说明。

五、完整流程（开发 → 合并 → 发布）

日常开发
  1. git switch -c feat/5.8.x-actor-pool main —— 特性工位基取 main 头。（工位名中的版本号是目标预期；延期不强制改名，以 PR 落点为准）
  2. 开发中定期 git fetch && git rebase origin/main；个人工位允许 push --force-with-lease。
  3. 向 main 发 PR（默认底即 main），PR 描述必填波及线清单——哪些维护线受影响或为何不波及；这是跨线传播的对账账本。仓库以 rebase-merge 合入，main 保持线性。
开新线（特性攒够一个次版本）
  1. 确认 main 的 CI 为绿。
  2. git switch -c 5.8.x main && git push -u github 5.8.x —— 新线第一次构建自动派生 5.8.x-SNAPSHOT，零版本文件改动。
  3. CI 线入口由通配自动覆盖，快照发布选线随之换线（快照镜像选线同当前开发线，依据线谱系登记，开新线自动换线；旧线转维护态即退出定时）；禁止从旧线头切新线——内容前沿在 main。
  4. 线谱系表追加一行：线名、开线提交号、日期、当时上一线最新标签、状态。
  5. 普通推送同步 main（main 是线的直系后代时一条 git push github 5.7.x:main 即可）。
常规发布（如 5.8.0）——三步任务，全程可在完整克隆中执行
  1. ./gradlew releaseCut -PreleaseVersion=5.8.0：从 5.8.x 线头切出 5.8.0.release 并推送；不创建标签。
  2. ./gradlew releaseTag -PreleaseVersion=5.8.0：在该分支 HEAD 建附注标签 v5.8.0 并推送——标签即制品出生提交，先于制品。
  3. ./gradlew publish -PgitExe=/usr/bin/git：五重门禁（分支形态白名单、版本形态、同号黑名单、仓库路由、标签存证）通过后制品入正式仓；Central 聚合通道独立执行、一败一留。
  4. ./gradlew releaseMergeBack：该分支无新提交时如实报告跳过。版本发布分支与标签自此封存，标签、版本发布分支头、制品三者对账恒等（规格第七条）。
hotfix（如 5.7.9）与跨线传播
  1. ./gradlew releaseCut -PreleaseVersion=5.7.9 -PreleaseFrom=v5.7.8：基=上一版标签（制品证据点），补丁谱系绕开线的新内容；工具拒绝自动推断上一版本号。
  2. 修复提交进该分支并推送（标签创建前的合法快进追加），随后 releaseTag → publish → releaseMergeBack 与常规同路。
  3. 波及其它线：对每条受影响线 git switch <线> && git cherry-pick -x <原型> && git push；方向永远旧线→新线（或线→main 上收），绝不反向。
  4. 对账（只读）：git cherry <新线> <老线> 输出为空 = 无静默丢失；非空且非"判定不波及"= 立即补。
失败与恢复速查
情况系统表现处置
忘打标签就 publish门禁拒绝"标签不存在"补跑 releaseTag，重跑 publish，无孤儿制品
错标但尚未推送仅存在于本地删除本地标签重建后再推送（唯一合法窗口）
错标且已推送门禁拒绝（解引用不符）绝对不动：弃号、提高补丁号重发
合回重放冲突自动 abort、reset 清回线原头、切回版本发布分支，三方原状按错误信息中的人工等价命令收尾
线被他人推进普通推送被拒git pull --rebase 更新线后重跑 releaseMergeBack
远端不可达门禁 fail-closed 拒绝网络恢复后重跑
在 linked worktree 里跑 gradle守卫直接报错（JGit 上游限制，升级不解决）改用完整克隆执行一切发布操作
