# 对象设计原则（TnyFramework 方法论·原则卷）

> **本文用途**：`design.md` 生成与人工评审时的裁决依据。每条原则有编号（P1、P2…），
> 设计文档中的每个技术决定应引用所依据的编号；偏离时写明理由。
> 配套阅读：`patterns-in-tny.md`（模式地图卷——"遇到什么问题该借哪个模式"）。

---

## 第一部分：框架命脉原则

### P1 抽象与实现分离（本框架的第一原则）

抽象模块（`tny-game-net`、`tny-game-codec`、`tny-game-data`、`tny-game-expr`）
只定义契约，**MUST NOT** 依赖任何具体实现模块；实现模块
（`*-netty4`、`*-jackson`、`*-mongodb`、`*-groovy`…）依赖抽象模块。
装配方向永远是"实现 → 抽象"，由 starter 模块在应用侧完成组合。

**判据**：删掉任何一个实现模块（如 `tny-game-codec-jackson`），抽象模块 MUST 仍能编译通过。

### P2 依赖倒置：高层不依赖低层，双方依赖契约

需要外部能力时，声明**自己拥有的接口**，而不是引用提供方的类。
框架内机制：`@UnitInterface` + 类扫描装配——组件声明对契约的需求，
实现由扫描注入提供，组件之间不互相 import 具体类。

**正例**：`tny-game-net` 定义 `MessageDispatcher` 接口，netty4 实现它；
网络核心从不 import netty4 包的实现类。
**反例**：业务模块直接 `new NettyClientGuide(...)`——应当依赖契约并由装配提供实现。

### P3 面向扩展开放、面向修改关闭（OCP）

新增一种能力 = 新增一个模块/实现类，而不是修改既有类。

**正例**：新增序列化协议时，新建 `tny-game-codec-xxx` 实现 `ObjectCodec`，
经 `ObjectCodecFactory` 注册；`tny-game-codec` 抽象层一行不改。
**判据**：如果一个"新增功能"的改动落在抽象模块里，先质疑：是不是抽象契约本身要变？
若否则说明设计走偏了。

## 第二部分：通用对象设计原则

### P4 封装 = 保护不变量，不是藏字段

真正的封装是：对象内部存在"任何时候都成立的业务规则"（不变量），
构造与每个方法都维持它。没有不变量的类不需要封装——数据袋就明说是数据袋。

**应用示例**：`Session` 的不变量是"认证完成后才可能携带有效证书"，
所以认证状态与证书必须同生共死地更新，禁止暴露"单独换证书"的 setter。

### P5 单一职责（SRP）：按"变更原因"划分，不按功能划

一个类只有一个变更理由。功能相似的代码若因不同原因被修改，就分属不同职责。

**应用示例**：消息派发（`MessageDispatcher`，因路由规则变化而改）与
消息序列化（`MessageBodyCodec`，因协议格式变化而改）是两个类——
它们"功能上挨着，变更原因不同"。

### P6 里氏替换（LSP）：实现必须守约，不许打折

实现类 MUST 能被抽象契约文档承诺的语义完全替换。Lifecycle 各阶段
（`AppPrepareStart`/`AppPostStart`/`AppClosed`）的每个实现都必须服从统一的
顺序与失败语义；若某实现无法支持契约的某个方法，这是设计错误，不是 `throw new
UnsupportedOperationException` 的理由。

**判据**：verify 阶段逐 Scenario 审计时，每个契约承诺的行为在每个实现上都应有测试。

### P7 接口隔离（ISP）：小接口靠组合生长

强迫使用者依赖其不需要的方法，等于制造隐性的破坏面。契约接口按
"调用方视角的最小能力集"切分；能力扩展通过新增接口/适配器组合，而非在原接口上加方法。

**反例警示**：若把编解码、压缩、加密塞进同一个 `ObjectCodec`，
只需要 JSON 序列化的调用方就被迫关心加密——每个方法都是潜在的变更传染源。

### P8 组合优于继承

`extends` 承诺了"is-a 且语义永远跟随父类"，是**最强**的耦合。默认选组合 + 委托；
继承仅用于：① 模板方法骨架（`AbstractExpr` 之于表达式家族是正当的）；
② 真正的行为子类型且不变量可继承。

**判据**：当你想"继承来复用几个方法"时，先问——能否把这几个方法抽成独立组件，
注入进来？继承复用代码，组合复用行为。

### P9 迪米特法则与信息隐藏

对象只与"直接伙伴"交谈。`a.getB().getC().doX()` 链每多一环，
就多一处被上游重构波及的位置。框架中的 `Context` 类
（`NetBootstrapContext`、`ExprContext`）存在的意义就是把散落的协作对象收拢为
一个可测试的直接伙伴。

### P10 三次法则：抽象要等重复出现

同一问题第一次出现，直接写；第二次，容忍重复；**第三次，才抽象**。
提前抽象比不抽象更贵——错误的接口一旦发布（本框架发布到 Nexus 供下游依赖），
破坏性变更要等一个大版本。

**判据**：新抽象接口在提案前 MUST 能说出"它同时服务哪些已有或已确认即将到来的场景"；
说不出，就降级为具体类，留待证据出现。

## 第三部分：契约与兼容性原则

### P11 公共 API 是合同，不是实现细节

发布到 Nexus 的 `com.tny.game.*` 公开类型即合同。合同变更三问：
下游能否无感知升级？旧调用是否仍可编译运行？报文/序列化格式是否向后兼容？
三问任一为否 → 提案必须标 BREAKING，并给出迁移路径。

### P12 行为变更先于代码变更

任何外部可观察行为的变化，必须先以规格差量（ADDED/MODIFIED/REMOVED Requirement）
的形式被评审通过，再落进代码；代码评审人对照的是规格，不是"看起来合理"。
（此条由 `openspec/config.yaml` 的 rules 机械执行。）

### P13 为可验证性而设计

每个设计决定都应能回答"哪个测试会证明它成立"。WHEN/THEN Scenario 写不出来的
"好设计"只是偏好。热路径设计（派发、编解码、连接管理）还须回答：
该决定会引入什么额外分配/同步点，量级多大。

## 使用方式（给 AI 与评审者）

- `design.md` 的 **Decisions** 小节：每条决定标注所依据的 P 编号（如"P3、P8"），
  偏离某条原则时须显式写明"P10 例外，理由：…"。
- `proposal.md` 涉及抽象模块的新接口时：对照 P3/P7/P10 三查。
- 评审时优先质疑：引用不到任何 P 编号的决定。
